# 기능 명세서 생성 가이드

사용자가 Claude나 다른 AI 에이전트에게 “이 프로젝트 기능 명세서 뽑아줘”라고 요청하면 현재 구현을 직접 확인하고 화면 캡처가 포함된 명세서를 만든다. 루트의 `기능명세서/` 이미지는 결과 형식 참고용이며 제품 사실의 근거로 사용하지 않는다.

## 결과 위치

- 문서: `functional-spec/YYYY-MM-DD-spec.md`
- 캡처: `functional-spec/assets/YYYY-MM-DD/<screen-id>-<state>.png`
- 날짜는 요청한 날의 로컬 날짜를 사용한다.
- 같은 날짜의 문서가 이미 있으면 내용을 먼저 읽고 변경된 구현을 반영한다. 확인 없이 기존 내용을 지우지 않는다.

## 근거 우선순위

1. Playwright로 직접 확인한 현재 화면과 동작
2. `src/ui`에서 확인한 표시 조건과 사용자 입력
3. `src/plugin`과 `src/shared`에서 확인한 Figma 동작, 저장 방식과 제약
4. 제품 문서는 의도 확인에만 사용한다. 구현과 다르면 현재 구현을 적고 차이를 제한사항에 남긴다.

화면에서 보였다는 이유만으로 동작한다고 추정하지 않는다. 반대로 Figma 호스트에서만 실행되는 기능은 Playwright 확인으로 가장하지 않고 `코드 확인`으로 표시한다.

## 실행 절차

1. `npm run build`로 현재 소스가 빌드되는지 확인한다.
2. `npm run dev -- --host 127.0.0.1`로 미리보기를 실행하고 Playwright Chromium으로 접속한다.
3. Build, Flow, Spec, Settings와 세부 화면을 실제 클릭해 탐색한다. 버튼, 선택 항목, 입력, 빈 상태, 오류 상태를 확인한다.
4. Figma의 `STATE` 메시지가 필요한 화면은 Playwright에서 현재 `src/shared` 타입과 일치하는 최소 fixture를 `window.postMessage`로 주입한다. 이를 위해 production 코드를 수정하지 않는다.
5. 각 화면은 기능을 설명하는 데 필요한 대표 상태만 캡처한다. 같은 정보를 보여주는 장식용 캡처는 만들지 않는다.
6. 캡처에서 발견한 기능을 `src/ui`와 대조하고, Figma Canvas 변경이나 Prototype 연결은 `src/plugin` 구현까지 추적한다.
7. 아래 형식으로 명세를 작성한 뒤 이미지 링크와 기능 ID가 모두 유효한지 확인한다.

Chromium 실행 파일이 없는 환경에서만 `npx playwright install chromium`을 실행한다.

## 문서 형식

```markdown
# Sketchy 기능 명세서

> 작성일: YYYY-MM-DD
> 기준: commit `<short-hash>`
> 검증: Playwright 확인 / 코드 확인

## 1. 개요

- 제품 목적
- 이번 명세의 범위
- 실행 및 검증 환경

## 2. 화면 목록

| 화면 ID | 화면명 | 진입 방법 | 주요 기능 |

## 3. 화면별 기능

### SCR-01 화면명

![화면 설명](./assets/YYYY-MM-DD/scr-01-default.png)

| 기능 ID  | 기능명      | 사용자 동작     | 결과                       | 확인 방법 | 제한사항          |
| -------- | ----------- | --------------- | -------------------------- | --------- | ----------------- |
| BUILD-01 | Screen 추가 | Add screen 클릭 | Figma Canvas에 Screen 생성 | 코드 확인 | Figma 호스트 필요 |

## 4. 공통 기능

화면별 표에서 반복하지 않고 내비게이션, 선택 동기화, 오류 표시처럼 여러 화면이 공유하는 기능만 적는다.

## 5. 데이터와 상태

- 저장되는 프로젝트 데이터
- 선택 상태와 파생 상태
- Figma Plugin UI와 Runtime 사이의 메시지

## 6. 제한사항과 미지원 범위

- 구현상 지원하지 않는 기능
- Playwright만으로 검증하지 못한 Figma 호스트 동작
- 문서 의도와 현재 구현의 차이
```

## 작성 규칙

- 화면 ID는 `SCR-01`부터, 기능 ID는 영역을 나타내는 짧은 접두사와 번호를 사용한다. 예: `BUILD-01`, `FLOW-01`, `SPEC-01`.
- 기능명은 내부 컴포넌트명이 아니라 디자이너가 이해할 수 있는 사용자 결과로 쓴다.
- `확인 방법`은 `Playwright 확인` 또는 `코드 확인` 중 하나로 명시한다.
- 구현 근거가 없는 예정 기능, 희망 동작, 제품 문서의 아이디어를 현재 기능처럼 쓰지 않는다.
- 기능별 코드 경로를 나열해 본문을 무겁게 만들지 않는다. 모호하거나 제한이 있는 항목에만 근거 파일을 덧붙인다.
- 참고 이미지처럼 화면과 표를 가깝게 배치하되, 픽셀 단위로 형식을 복제하지 않는다. Sketchy답게 읽기 빠른 Markdown을 우선한다.
