# Sketchy 로그인 UX 검토

> 이 문서는 Sketchy 제품 설명을 근거로 한 일반 UX·아키텍처 추론이며, 실제 사용 데이터에 기반한 것은 아니다. "검증 필요"로 표시된 항목은 출시 전 직접 확인을 권장한다.

## 결론 요약

- **추천: 선택지 B** — 로컬(Build·Flow·Spec)은 무계정, `AI 에이전트 연결` 시점에만 로그인 요구.
- **선택지 C는 배제** — 계정 복구·다중 기기·보안과 정면충돌.
- 세 가지 규칙을 붙인다: **① 익명 서버 상태 금지 ② 로컬 사용량 측정 포기 ③ provider와 분리된 내부 userId 유지.**

---

## 기술 전제 (Figma 플러그인 OAuth)

Figma 플러그인에서 외부 OAuth(구글 포함)를 붙이는 표준 방식:

1. 플러그인이 랜덤 코드 생성
2. 외부 브라우저를 열어 로그인 진행
3. 서버가 콜백을 처리해 결과를 코드 기준으로 저장
4. 플러그인이 그 코드로 서버를 폴링해 토큰 수신
5. 토큰을 `figma.clientStorage`에 저장해 재로그인 회피

플러그인 iframe 내부에는 서버가 없어 이 폴링 방식이 정석이다.
[신뢰도 높음 — Figma 개발자 문서·다수 실제 사례에서 동일 확인]

> "플러그인 안에서 갑자기 브라우저가 열린다"는 점이 뒤의 이탈·불신의 핵심 원인이다.

---

## 1. 로그인 요구 시점

원칙: **로그인은 "서버가 반드시 개입해야 가치가 생기는 순간"에만 요구한다.**

Sketchy에서는 이 경계가 명확하다.

- Build·Flow·Spec = 플러그인 내부 로컬 → 계정 불필요
- AI Agent 연결·원격 Project·Agent Apply = 서버·신원 필요

즉 **"로그인이 필요한 경계"와 "과금이 시작되는 경계"가 정확히 같은 선**이다. 이 일치가 B를 추천하는 근본 이유다. 사용자 설명("로컬은 무료·무계정, 서버·AI는 계정 필요")과 개발 구조가 모두 단순해진다.

Figma 사용자는 디자인 작업 흐름 한가운데에서 플러그인을 켜므로, 첫 화면 로그인 강제는 특히 불리하다.

## 2. A/B/C 추천 — B (단, C 요소는 배제)

- **A (첫 실행 필수 로그인)**: 로컬 기능이 오프라인으로 완결되는데 체험 전에 마찰을 거는 선택. 로컬 가치를 스스로 버림.
- **C (익명 서버 ID 후 계정 연결)**: 함정.
  - 익명 ID는 로컬에 매여 있어 재설치·초기화·기기 이동 시 원격 Project 유실 → 대표적 CS·이탈 사유
  - 익명 → 실제 계정 병합 로직 필요 (결제·권한까지 얽히면 복잡도·버그 급증)
  - 다중 기기 불가
  - 애초에 풀려는 문제("로그인 전 서버 기능 제공")가 사용자에게 큰 가치가 아님
- **B (권장)**: 로컬 무계정, `AI 에이전트 연결`에서 로그인.

**핵심 구분:** 익명 _로컬_ 사용은 괜찮다(그게 B). 문제는 익명 상태로 _서버에 지속 상태를 만드는 것_(C)이다. 따라서 규칙으로 못박는다 — **"로그인 없이는 서버에 영구 데이터를 만들지 않는다."**

## 3. 로그인 전후 기능 경계

- **로그인 전(로컬, 무계정):** Build 전체(Screen·UI Block 무제한), Flow 확인, Spec 확인 — 로컬 디자인 경험 전부
- **로그인 후(서버):** AI Agent 연결, 원격 Project 저장·동기화, Agent Apply, 변경 Preview, Plan/결제 관리

권장 멘탈 모델:

> "당신 작업은 계정을 연결하기 전까지 이 기기 안에만 있습니다. AI와 원격 동기화를 켜는 순간 계정에 안전하게 저장됩니다."

주의: Preview는 quota를 안 깎을 뿐, "원격 Project + Agent 연결"이 전제라 로그인 후에 위치한다. "무료(quota 미차감)"와 "무계정"을 UI에서 혼동하지 않게 구분한다.

## 4. 버튼 이름·안내 문구

핵심: (1) "회원가입" 무게감 회피 (2) 왜 필요한지 한 줄 제공 (3) 브라우저가 열림을 사전 예고.

- 진입 버튼: **`AI 에이전트 연결`** (현재 이름 유지). 클릭 즉시 로그인창으로 던지지 말고 짧은 안내 모달을 한 번 끼운다.
- 모달 문구 예: _"AI 에이전트를 연결하려면 프로젝트를 안전하게 저장할 계정이 필요해요. 로그인은 브라우저 창에서 진행되고, 끝나면 자동으로 여기로 돌아옵니다."_
- 로그인 버튼: **`Google로 계속하기`** ("로그인"보다 심리적 저항이 낮음)
- 브라우저 전환 직후 대기 화면: _"브라우저에서 로그인을 완료해 주세요. 완료되면 자동으로 연결됩니다."_ + `이미 로그인했어요 / 다시 시도` 수동 복구 버튼

피할 표현: `로그인` 단독, `회원가입/로그인` 병기, `인증하기` — 마찰감·경계심을 키운다.

## 5. Google OAuth가 첫 수단으로 적절한가

**대체로 적절, 조건부.**

장점: Figma 사용자층의 Google 계정 보유율이 높고, 비밀번호 없이 빠르며 익숙하다.

짚을 점:

- **엔터프라이즈/조직 SSO 사용자**는 개인 Google 로그인이 막혀 있거나 Microsoft만 쓰는 경우가 있음 → Google 단독은 일부 배제 가능. "Google 먼저, provider 추가 가능"하게 설계.
- 계획의 **"내부 랜덤 userId ↔ 로그인 식별자 별도 연결"** 구조가 이를 가능하게 함 → 유지 권장. 이메일 매직링크·Microsoft·Figma 로그인을 나중에 추가해도 기존 계정이 안 깨짐.
- "Figma로 로그인"(Figma OAuth)도 후보이나, 공개 앱은 Figma 심사를 거치며 심사가 까다롭다는 얘기가 있음.
  [신뢰도 보통 — 공식 문서상 public app review는 확인. "까다롭다"는 개발자 블로그·포럼 기반, 직접 확인 권장]
- 결제·웹 대시보드 범용성까지 고려하면 **Google 먼저, Figma 로그인은 선택적 추가안**.

## 6. 로그인 과정의 이탈·불신·혼란 (완화책)

우선순위 순:

1. **"왜 갑자기 브라우저가 열리지?" (가장 큼)** → 누르기 전에 예고 (4번 문구)
2. **폴링 대기 상태의 무한 침묵** → 진행 표시 + 타임아웃 + `다시 시도` + `이미 로그인했어요` 수동 경로 필수
3. **Google 미검증 앱 경고 화면** → 출시 전 Google 앱 검증(verification) 완료 권장
   [신뢰도 보통~높음 — Google OAuth 일반 동작이나 정책 세부는 변동 가능, 출시 전 최신 기준 확인]
4. **권한 범위(scope) 공포** → email·profile 최소 scope만 요청
5. **"AI 쓰려고 로그인까지?"** → B의 타이밍으로 완화되나, 모달의 "왜 필요한지" 문구로 마저 보완

## 7. Free/Pro 경계를 블록 수 대신 원격 Project·Agent Apply에 두기

**타당, 강하게 동의.**

- **집행 가능성:** 블록 수는 로컬 측정이라 `clientStorage` 초기화·재설치로 우회됨. 원격 Project·Agent Apply는 서버 검증 → 정직한 집행 가능.
- **비용 정합성:** Agent Apply는 실제 LLM·연산 비용, 원격 Project는 저장·동기화 비용 발생 → 비용 지점에 과금 = 건강한 단위경제.
- **가치 정합성:** AI 자동화가 차별적 가치, 로컬 디자인은 기본기. 기본기를 벌하지 말고 파워 기능을 과금.

주의:

- "활성 원격 Project 수" 제한은 **보관/비활성화 UX**를 같이 설계해 Free 사용자가 갇히지 않게 한다.
- **Agent Apply 정의를 예측 가능하게** — 무엇이 1회로 세이고 무엇(Preview·조회)은 제외인지 명확히 표시.

## 8. 더 단순하면서 안전한 대안

가장 단순·안전한 형태는 **B의 규율을 더 세게 지키는 것**:

- **로컬 사용량 측정을 목표에서 제외.** "로컬을 정확히 제한 못 한다"는 고민을 *"로컬은 설계상 무제한이라 제한 불필요"*로 뒤집으면 익명 어뷰징 대상 자체가 사라짐 → 더 단순 + 더 안전
- **익명 서버 상태 금지 규칙**(3번)으로 C의 병합 지옥 원천 차단
- 사람용 로그인(플러그인)과 기계용 연결(MCP)을 **같은 userId로 묶되 경로 분리.** MCP는 계획대로 OAuth 2.1 + PKCE 브라우저 승인이 맞음 — PKCE는 시크릿을 못 숨기는 퍼블릭 클라이언트의 현재 표준 권장 [신뢰도 높음]
- 여력 시 **이메일 매직링크**를 보조 수단으로 두면 provider 락인/조직 제약 사용자 구제 (필수 아님)

## 9. 첫 사용자 → Pro 전환 권장 UX 흐름

1. **설치·첫 실행:** 로그인 없이 바로 Build 진입, 화면·블록 자유 생성 (마찰 0)
2. **로컬 탐색:** Flow·Spec 로컬 확인, 가치 체감
3. **AI 필요 순간:** `AI 에이전트 연결` 클릭
4. **안내 모달:** 왜 계정이 필요한지 + 브라우저 열림 예고 + `Google로 계속하기`
5. **외부 브라우저:** Google 동의(최소 scope, 검증된 앱) → 서버가 provider 신원을 내부 userId에 연결(신규면 생성) → "플러그인으로 돌아가세요" 성공 페이지
6. **자동 복귀:** 폴링 성공 감지 → 토큰 `clientStorage` 저장 → 연결 계정 표시 → 로컬 Project를 원격으로 업로드 가능 (기본 Free)
7. **첫 Agent 사용:** MCP 연결(OAuth 2.1+PKCE) 후 Free quota 내 Agent Apply 실행, Preview 무제한
8. **한도 근접:** 작업 중간 차단 금지, 맥락 내 넛지("이번 달 Agent Apply 4/5"), 진행 중 액션은 완료 보장
9. **Pro 업그레이드:** 플러그인 내 CTA → 외부 브라우저 결제 → customerId를 userId에 연결 → 복귀 즉시 Pro 한도 적용
10. **다중 기기·복구:** 다른 기기에서 같은 Google 로그인 → 같은 userId → 원격 Project 동기화. 여기서 B가 C를 이김 — 신원이 처음부터 실제 계정이라 "아무 데서나 다시 로그인" = 복구·동기화 완료

## 한계 및 확인 권장 사항

위 판단은 제품 설명 기반의 일반 UX 추론이다. 다음은 출시 전 직접 확인 권장:

- 실제 타깃 사용자층 (개인 디자이너 위주 vs 기업팀) → provider 전략 조정
- Figma·Google OAuth 심사·검증의 현재 세부 정책
- "Agent Apply 1회의 실제 비용" → 과금 숫자 조정
- Google 미검증 앱 경고, Figma OAuth 심사 난이도는 실제로 부딪혀야 정확

**전체 신뢰도: UX 판단 높음 / 플랫폼 정책 세부는 보통 — 확인 권장**
