# AI 페르소나 검증 실행 가이드

사용자가 Claude나 다른 AI 에이전트에게 “페르소나를 만들어줘”, “이 기능을 초보 PM 관점에서 검증해줘”처럼 요청하면 이 문서를 작업 규약으로 사용한다. 목적은 이미 정한 결론을 확인하는 것이 아니라 현재 구현에서 반복되는 장애를 독립적으로 찾는 것이다.

## 요청 해석

- **페르소나만 요청**: 이름, 역할, 숙련도, 업무 맥락, 시간 압박, 작업 습관을 작성한다. 제품 평가는 수행하지 않는다.
- **관점 검토 요청**: 지정된 페르소나로 현재 구현의 관련 흐름만 확인하고 짧은 근거 기반 의견을 낸다.
- **검증 또는 사용성 테스트 요청**: 아래 독립 검증 절차를 끝까지 수행하고 결과 파일을 남긴다.
- 역할이나 숙련도가 비어 있으면 Primary User인 PM/PO 중급자를 기본값으로 사용한다. 결과가 달라질 이유가 있을 때만 서로 겹치지 않는 페르소나를 추가한다.

## 반드시 지킬 독립성

- 평가가 끝날 때까지 기존 `persona/` 결과와 제품 철학·로드맵 문서를 읽지 않는다.
- 실제 UX 파악에 필요한 현재 구현, 실행 방법, 타입만 최소 범위로 확인한다.
- 제공되지 않은 동작을 성공으로 추정하지 않는다.
- AI 평가는 실제 사용자 테스트나 시간 측정이 아니다. 결과에 **구현 기반 인지적 워크스루**라고 명시한다.
- 여러 평가자를 요청받으면 서로의 결과를 보지 않게 각각 독립 실행한 뒤 마지막에만 종합한다.

## 검증 절차

1. 페르소나의 이름, 역할, Figma 숙련도, 시간 압박, 작업 습관을 정한다.
2. 사용자 요청에 과업이 없으면 핵심 흐름 과업 하나와 예외가 포함된 복잡한 과업 하나를 정한다.
3. 빈 프로젝트에서 처음 사용하는 상황으로 핵심 과업을 수행한다.
4. 같은 사용자가 다시 쓰는 상황으로 복잡한 과업을 수행해 학습 가능성과 표현 한계를 확인한다.
5. 각 단계의 기대, 구현상 실제 결과, 막힌 지점, 사용한 우회와 코드 근거를 기록한다.
6. 완료 조건별로 성공·부분 성공·실패를 판정한다.
7. 독립 보고서를 저장한 뒤에만 기존 종합 문서와 비교하고, 반복 발견을 종합에 반영한다.

## 결과 파일

새 회차는 `persona/<회차_YYYY-MM-DD>/`에 저장한다. 파일명은 `<이름>_<역할>_검증.md`로 쓴다.

```markdown
# 이름 — 역할 독립 검증

## 전제

- 페르소나:
- 검증 방식: 구현 기반 인지적 워크스루
- 확인한 구현 범위:

## 1차 과업

| 단계 | 기대 | 실제 결과 | 판정 |

## 2차 과업

| 단계 | 기대 | 실제 결과 | 판정 |

## 발견 사항

- 영향도 · 문제 · 구현 근거

## 최종 판정

- 성공 / 부분 성공 / 실패와 이유
```

여러 독립 보고서가 끝나면 공통 발견, 서로 다른 발견, 우선순위, 검증 한계를 별도 종합 파일에 정리한다. 한 번 나온 선호나 추측만으로 제품 원칙 또는 로드맵을 바꾸지 않는다.
