# Sketchy 독립 사용성 연구 — 김준호

## 참가자 설정

- 이름: 김준호
- 직무/경력: 대기업 커머스 조직 서비스 기획자, 9년 차
- 조직 환경: 디자이너 4명, 개발자 12명, 데이터 분석가 2명과 스쿼드 단위로 일한다. 신규 과제의 화면 목록, 정책, 예외 흐름을 정리해 디자인 리뷰 전에 공유하는 역할이다.
- Figma 숙련도: 중상. 기존 컴포넌트로 와이어프레임을 만들고 프로토타입 링크를 연결할 수 있지만, 오토레이아웃을 아주 정교하게 다루지는 않는다.
- 업무 압박과 습관: 회의 직전 30~60분 안에 초안을 만드는 일이 잦다. 일단 화면과 주요 CTA를 빠르게 만든 뒤 목적·정책을 보충한다. 같은 정보가 여러 곳에 있으면 최신 버전을 헷갈리는 것을 특히 싫어한다.
- 사전 정보: “Sketchy라는 Figma 플러그인”이라는 이름 외에는 설명을 받지 않았다.
- 만들 기획안: 모바일 사내 카페 픽업 주문. `메뉴 탐색 → 메뉴 상세 → 장바구니 → 주문 완료`가 기본 흐름이며, 메뉴 상세에서 즐겨찾기 상태 변경도 표현한다.

## 세션 1 — 처음부터 기본 주문 흐름 완성하기

### 목표

네 개 화면의 저충실도 와이어프레임과 핵심 이동 경로를 만들고, 리뷰 동료가 화면 목적과 가능한 행동을 읽을 수 있는 기획 초안을 완성한다.

### 사전 기대

플러그인을 열면 템플릿이나 시작 안내가 나오고, 화면 이름과 구성 요소를 넣은 다음 버튼끼리 연결하면 캔버스에 흐름이 그려질 것으로 예상했다. `Build`, `Flow`, `Spec`은 각각 제작, 흐름 확인, 문서 확인으로 추측했다.

### 세션 1 결과물

- 모바일 화면 4개와 화면별 목적
- 기본 블록으로 구성된 저충실도 와이어프레임
- 버튼 기반 화면 이동 4개와 즐겨찾기 상태 설명 1개
- 캔버스 연결선 및 화면별 읽기 전용 Spec

기본 흐름 초안은 약 35분 안에 만들 수 있었다. 그러나 반복 목록, 실제 이미지, 데이터/정책, 상태별 UI, 전체 기획서 내보내기는 결과물에 포함하지 못했다.

### 세션 1 총평

처음부터 “화면을 만들고 버튼을 연결한다”는 핵심은 짧게 학습됐다. 특히 캔버스에 실제 Figma 프레임과 프로토타입 연결이 생기는 반응은 신뢰를 줬다. 반면 편집값이 blur에 의존하고, 생성 직후 이름을 받지 않으며, Section 내부 편집이 한 단계 더 필요한 탓에 반복 작업의 리듬이 자주 끊겼다. Spec은 확인 화면이지 독립적으로 공유 가능한 기획 산출물은 아니었다.

## 세션 2 — 요구사항과 예외 흐름 추가하기

### 목표

하루 뒤 같은 파일에서 다음 변경을 반영한다.

1. 장바구니가 비어 있을 때의 화면 추가
2. 주문 실패 후 재시도 흐름 추가
3. 즐겨찾기 추가/해제 두 상태 표현
4. 메뉴 카드 두 개를 가로 배치하고 순서 조정
5. 기존 프로토타입과 충돌 없이 수정

### 사전 기대

기존 데이터가 그대로 로드되고, 화면 복제 또는 분기 추가 기능으로 빠르게 확장할 수 있으리라 예상했다. Flow에서 연결을 직접 수정하고 Spec에서 변경 누락을 점검하고 싶었다.

### 단계별 사용 기록

| 단계 | 행동                                                                                                                         | 시스템 반응                                                                                                                                                                                                  | 생각·감정                                                                                                                  | 걸린 지점 / 우회                                                                                                                                                                                  |
| ---- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 플러그인을 다시 연다.                                                                                                        | 저장된 화면·요소·상태·Feature가 복원되고 기존 화면이 다시 렌더링된다. 삭제된 노드가 있다면 프로젝트 목록에서 정리되는 구조다.                                                                                | 파일에 붙어 저장된 결과가 돌아와 안심된다. 별도 프로젝트 선택 과정이 없는 점은 간단하다.                                   | 버전 이력이나 변경 요약은 없어 어제 상태를 직접 훑는다.                                                                                                                                           |
| 2    | 빈 장바구니 화면을 기존 장바구니에서 복제하려고 화면 주변과 플러그인 메뉴를 찾는다.                                          | 화면 복제 명령이 없고 `+ Screen`만 있다. 화면 삭제 명령도 없다.                                                                                                                                              | 예외 화면은 기존 화면의 변형인데 처음부터 다시 만드는 것이 부담스럽다.                                                     | `+ Screen`으로 `빈 장바구니`를 만들고 Text와 Button을 다시 추가한다. 실수로 만든 화면은 플러그인에서 지울 수 없어 Figma 캔버스에서 프레임을 직접 삭제하는 방식으로 우회할 수밖에 없다고 판단한다. |

### 세션 2 결과물

- `빈 장바구니`, `주문 실패` 화면 추가
- 빈 상태의 조건과 재시도 동작을 Purpose/행동 설명으로 기록
- 즐겨찾기 토글 의도를 문장으로 보완
- 카드형 레이아웃은 세로 Section 두 개로 축소
- 기존 Figma 프로토타입 충돌 시 수동 제거 후 재연결하는 절차 확인

추가 요구사항 반영에는 약 40분이 들었다. 화면 자체는 늘릴 수 있었지만 조건 분기, 재시도, 토글, 복합 카드 구조는 실제 동작 모델이 아니라 설명 텍스트로만 남았다.

### 세션 2 총평

기존 프로젝트 복원과 캔버스 동기화는 안정감을 줬다. 하지만 기본 선형 흐름을 넘어서자 “그려진 화면”, “Sketchy가 이해하는 흐름”, “기획자가 설명에 적은 정책”이 서로 달라졌다. 특히 UI에서 토글처럼 설명했지만 내부 행동은 true 설정에 머무는 상태는 리뷰어에게 잘못된 확신을 줄 수 있다. 확장 편집보다 초기 스케치에 더 적합한 도구로 느껴졌다.

## 심각도별 발견사항

### 치명적 — 기획 결과의 의미가 잘못 전달될 수 있음

1. **상태 변경이 실제 표현과 설명 사이에서 어긋난다.** `Change state`는 사용자에게 일반적인 상태 전환이나 토글처럼 보이지만 UI에서는 초기값·목표값·해제·상태별 화면을 설정할 수 없다. 설명란에 토글이라고 써도 실제 저장 행동은 true 설정이므로 Spec이 구현 가능한 정의처럼 오인될 수 있다.
2. **조건 분기와 예외 진입 조건을 모델링할 수 없다.** 성공/실패, 빈 상태, 유효성 검사처럼 서비스 기획의 핵심 예외는 연결로 표현할 수 없고 Purpose나 설명에 흩어진다. Flow만 보면 빠진 경로인지 의도된 조건인지 구분되지 않는다.

### 높음 — 주요 작업을 완료하거나 유지하기 어려움

1. **화면 복제와 플러그인 내 화면 삭제가 없다.** 변형 화면을 반복 제작해야 하고, 실수한 화면 정리는 Figma 캔버스로 나가야 한다.
2. **Flow에서 흐름을 편집할 수 없다.** 화면이 늘면 특정 버튼을 캔버스에서 찾아 선택하고 Build로 돌아가야 하며, Flow는 이름과 달리 관리 중심점이 되지 못한다.
3. **전체 Spec 공유 수단이 없다.** 화면별 읽기 화면만 있고 전체 보기·복사·내보내기가 없어 결국 별도 기획 문서를 병행하게 된다.
4. **Section 중첩이 불가능해 반복 카드나 복합 UI 구조를 의미 있게 묶기 어렵다.** Horizontal Section도 단순 자식 나열만 가능해 일반적인 카드 그리드를 표현하기 어렵다.

### 중간 — 반복 작업의 속도와 확신을 낮춤

1. **이름과 설명 저장이 포커스 이탈에 의존한다.** 저장 상태가 표시되지 않아 탭 이동이나 캔버스 조작 전에 값이 반영됐는지 불안하다.
2. **생성 직후 이름을 지정할 수 없다.** `Screen 1`, `Screen 2`가 먼저 쌓여 화면이 많을수록 다시 찾아 이름 붙이는 비용이 커진다.
3. **Section 안에 요소를 추가해도 새 요소가 선택되지 않는다.** Nodes 목록에서 방금 추가한 항목을 다시 선택해야 해 `추가→이름 변경` 반복 흐름이 끊긴다.
4. **현재 화면 Flow와 Project flow가 중복된다.** 작은 360px 패널에서 같은 연결이 두 번 보여 복잡한 프로젝트의 탐색 비용이 커진다.
5. **외부 Figma 인터랙션 충돌 오류에 해결 안내가 없다.** 데이터 보호는 적절하지만 사용자가 Prototype 패널에서 무엇을 해야 하는지 알기 어렵다.

### 낮음 — 학습성과 마감 품질에 영향

1. 첫 화면에 플러그인의 결과물과 기존 프레임 사용 가능 여부를 설명하는 짧은 안내가 없다.
2. 이미지 교체, 텍스트 스타일, 입력 상태 등 블록별 설정이 거의 없어 placeholder 이상의 표현력이 제한된다.
3. Settings의 즉시 저장 여부가 명시되지 않는다.
4. 현재 화면으로 이동하는 Destination이 제외되어 새로고침·재시도 같은 자기 전환을 이동으로 표현할 수 없다.

## 개선 제안

1. **상태 기능의 약속을 좁히거나 완성한다.** 가장 작은 개선은 명칭을 `Mark state as on`처럼 실제 동작에 맞추고 Spec에도 고정값 설정임을 밝히는 것이다. 토글을 지원하려면 초기값, true/false/toggle, 상태별 라벨 또는 목적 화면을 명시적으로 선택하게 한다.
2. **Feature에 조건/결과 설명 필드를 추가하고 Flow에 함께 노출한다.** 우선 자유 텍스트 `조건` 하나만 있어도 빈 상태·성공·실패가 Purpose에 흩어지는 문제를 크게 줄인다.
3. **화면 항목에 Duplicate와 Delete를 제공한다.** Delete에는 연결 영향과 확인 단계를 보여 데이터 안전성을 지킨다. 새 화면 생성 시 이름을 바로 입력하거나 생성 직후 이름 필드에 초점을 둔다.
4. **Flow 항목에서 목적지 변경과 Feature 삭제를 허용한다.** 출발 버튼을 찾아 Build로 왕복하지 않아도 핵심 연결을 관리할 수 있게 한다. `현재 화면만 / 전체`를 토글해 중복 표시를 없앤다.
5. **Spec에 `전체 화면 보기`와 `클립보드 복사`를 먼저 제공한다.** 복잡한 문서 내보내기보다 작은 구현으로도 리뷰 전달성이 크게 개선된다. 미연결 목적지와 조건 없는 예외 화면은 경고 목록으로 함께 보여준다.
6. **Section 내부 추가 후 새 요소를 선택한다.** 바로 이름을 바꿀 수 있게 해 반복 작업의 클릭 수를 줄인다. 카드 표현은 Section 한 단계 중첩 허용이나 `Card` 프리셋 중 하나만 우선 제공한다.
7. **저장 피드백을 명확히 한다.** Enter/Ctrl+Enter 저장 또는 짧은 `Saved` 표시를 제공하고, 탭 이동 전에 활성 입력값이 확실히 반영되게 한다.
8. **충돌 오류에 복구 행동을 붙인다.** 예: `이 버튼에는 기존 Figma 클릭이 있습니다. Prototype 패널에서 제거한 뒤 다시 시도하세요.`처럼 원인과 다음 행동을 한 문장으로 안내한다.

## 최종 판단

Sketchy는 선형 모바일 플로우의 첫 와이어프레임을 빠르게 만들고, 화면 목적·요소·버튼 이동을 Figma 안에서 함께 확인하는 데 효과적이었다. 반면 두 번째 세션처럼 현실적인 조건, 상태, 반복 구조, 변형 화면이 들어오면 기획 의도를 구조화하지 못하고 설명 텍스트로 밀어낸다. 현재 상태에서 나는 초기 아이데이션에는 사용하겠지만, 개발 핸드오프의 단일 기획 원본으로는 사용하지 않겠다.
