# Sketchy 사용성 연구 — 윤서진

## 참가자와 조사 조건

- 이름: 윤서진
- 직무/경력: 초기 스타트업 Product Manager, 6년 차
- 조직 환경: 개발자 4명, 디자이너 1명과 일하는 8인 팀. 다음 날 스프린트 킥오프에 가져갈 화면 흐름을 PM이 직접 준비한다.
- Figma 숙련도: 중급. 오토 레이아웃과 간단한 프로토타입 연결은 할 수 있지만, 컴포넌트 시스템은 디자이너에게 맡긴다.
- 업무 압박과 습관: 회의 사이 30분 안에 구조를 잡고 링크를 공유하는 일이 많다. 먼저 전체 흐름을 만든 뒤 이름과 설명을 다듬으며, 저장 버튼이 없으면 자동 저장을 기대한다.
- 사전 정보: “Sketchy라는 Figma 플러그인”이라는 이름 외에는 제품 설명을 받지 않았다.
- 만들 서비스: 아파트 단지 주민을 위한 공동구매 모바일 앱
- 핵심 User Flow: 공동구매 목록 → 상품 상세 → 참여 완료
- 조사 방식: 현재 UI에서 제공하는 조작과 그에 따른 캔버스/패널 반응만으로 두 차례 과업을 수행하는 인지적 워크스루. Figma 런타임 없이 독립 실행할 수 없는 부분은 구현된 이벤트와 상태 반응을 기준으로 확인했다.

## 1차 세션 — 처음부터 핵심 흐름 만들기

### 목표

내일 개발 킥오프에서 사용할 모바일 3화면 흐름과 간단한 기획 설명을 30분 안에 만든다. 각 화면의 목적, 주요 UI, 버튼 이동을 표현하고 마지막에 전체 흐름과 명세를 확인하고 싶다.

### 사전 기대

플러그인을 열면 템플릿이나 시작 안내가 있고, 화면 이름과 목적을 먼저 적은 뒤 필요한 요소를 추가할 것으로 예상했다. `Build`, `Flow`, `Spec`은 각각 화면 제작, 화면 간 연결, 결과 문서로 추측했다. 저장은 자동일 것으로 기대했다.

### 1차 결과물

- `공동구매 목록`, `상품 상세`, `참여 완료` 모바일 프레임 3개
- 제목, 이미지 자리, 상품 정보, 버튼을 포함한 저충실도 화면 구조
- `상품 보기` → `상품 상세`, `참여하기` → `참여 완료`의 실제 Figma 클릭 이동
- 각 화면 위 목적/행동 노트와 화면별 Spec

핵심 경로는 완성했다. 특히 화면 생성, 기본 레이아웃, 버튼 연결, 화살표 생성이 한 흐름으로 이어져 짧은 시간에 “회의 가능한 캔버스”를 만들 수 있었다. 반면 기획안이라는 관점에서는 사용자 조건, 데이터, 성공 기준, 예외, 입력 검증 등을 적을 자리가 없어 화면 이름과 버튼 설명에 정보를 압축했다.

### 1차의 주요 막힘과 우회

- 저장 버튼이나 저장 완료 피드백이 없음 → 입력 후 의식적으로 바깥을 클릭하고 캔버스 반영 여부를 확인.
- Section 자식 추가 후 새 자식이 선택되지 않음 → `Nodes` 목록에서 매번 다시 선택.
- 프로젝트 전체 Spec 및 내보내기가 없음 → Figma 캔버스와 화면별 Spec을 직접 오가며 검토.
- 이미지/세부 스타일/콘텐츠 속성이 없음 → 모든 요소를 이름 중심의 와이어프레임으로 사용.

## 2차 세션 — 현실적인 요구사항과 예외 흐름 추가

### 목표

며칠 뒤 정책 리뷰에서 나온 요구를 같은 기획안에 추가한다.

1. 비로그인 사용자가 `참여하기`를 누르면 로그인 화면으로 이동한다.
2. 로그인 사용자는 참여 완료로 이동한다.
3. 품절 상품은 `품절 알림 받기` 상태를 켤 수 있다.
4. 수량 입력과 필수 동의 체크를 표현한다.

### 사전 기대

기존 화면과 연결이 저장되어 있고, 버튼에 조건별 목적지를 여러 개 지정하거나 상태를 토글할 수 있을 것으로 기대했다. 기존 화면 복제 또는 분기 추가 기능도 예상했다.

Button을 `필수 동의`로 만들고 `Change state`를 선택한다. 설명란에 `약관 동의 여부를 true로 변경`을 쓴다. | 버튼 이름으로 boolean state가 생성되고 클릭 행동이 기록된다. 캔버스에는 상태 변화가 실제 인터랙티브 컴포넌트로 표현되지 않으며, Flow/Spec과 목적 노트에는 설명이 나타난다. 설정 가능한 값은 생성 시 `true`뿐이다.      | “Change state”가 실제 프로토타입에서 보이는 변화인지 기대했는데 문서적 상태에 가깝다. 그래도 기획 메모로는 쓸 수 있다.     | 체크 해제, 토글, 초기값 변경, 버튼 활성화 조건은 표현할 수 없어 Purpose에 텍스트로 추가한다.                                                                     |

| 7    | 로그인 실패를 표현하려고 로그인 버튼에 화면 이동과 오류 상태 변경을 함께 넣으려 한다.                                                                                        | 버튼은 이동 또는 상태 변경 중 하나만 유지한다. 기존 Figma 버튼에 별도의 클릭 interaction이 이미 있으면 충돌 오류가 날 수 있다.                                                                                         | 정상/실패를 한 트리거 아래 묶을 수 없어 Flow가 실제 조건을 오해하게 만든다.                                                | `로그인 성공`, `로그인 실패 예시` 버튼을 각각 만들어 이동과 상태 설명을 분리한다. 실제 UI와 다른 테스트용 분기임을 Purpose에 명시한다.                           |

### 2차 결과물

- 기존 3화면에 `로그인` 및 품절 관련 화면을 추가한 확장 흐름
- 로그인 여부 분기를 두 개의 가상 버튼으로 나눈 근사 표현
- 수량 범위, 필수 동의, 오류 정책을 Purpose 텍스트에 기록
- `품절 알림 받기`와 `필수 동의`를 true로 만드는 상태 설명

추가 요구를 “보이게”는 만들었지만, 실제 조건 분기와 상태 전이는 정확히 모델링하지 못했다. 화면과 버튼을 더 만들어 예외를 우회 표현하면서 실제 제품 UI와 기획용 다이어그램이 섞였다. 1차의 직선형 happy path에는 잘 맞았지만, 2차의 정책성 요구에서는 신뢰도가 급격히 낮아졌다.

### 2차의 주요 막힘과 우회/포기

- 한 버튼의 조건부 복수 행동 불가 → 시나리오별 가상 버튼으로 분리.
- Input 행동·값·검증 설정 불가 → 요소 이름과 화면 Purpose에 정책 기록.
- 상태 false/toggle/관리 불가 → true 전환만 사용하고 취소 흐름 포기.
- 화면 복제/삭제 불가 → 새 화면을 처음부터 만들고 남는 화면은 캔버스에서 직접 관리.
- 전체 기획안 내보내기 불가 → Figma 링크 공유로 대체.

## 발견사항과 심각도

### 치명적(Critical)

없음. 핵심 직선 흐름을 만들고 저장된 결과로 재진입하는 과업 자체는 완료할 수 있었다.

### 높음(High)

1. **현실적인 분기와 상태 전이를 정확히 표현할 수 없다.** 버튼마다 단일 action만 가능하고 조건, 복수 action, toggle/false가 없다. PM이 실제 정책 대신 가상 버튼을 화면에 추가하게 되어 산출물이 제품 UI처럼 오해될 수 있다.
2. **삭제 후 행동이 고아 상태로 남을 수 있고 정리 UI가 없다.** 요소 삭제는 확인 없이 즉시 실행되며, 연결된 feature가 trigger만 잃은 채 Flow/Spec에 남을 수 있다. 사용자는 왜 지운 행동이 계속 보이는지 해결할 길이 없다.
3. **Spec이 전달 가능한 프로젝트 명세가 아니다.** 현재 화면만 보여주고 전체 보기, 복사, 내보내기가 없다. 화면 수가 늘면 개발 전달과 누락 검토라는 핵심 업무를 완료하기 어렵다.

### 중간(Medium)

1. **입력 요소가 시각적 자리표시자에 머문다.** 타입, 기본값, placeholder, 유효성, 오류, change/submit 행동을 지정할 수 없다.
2. **`Change state`의 명칭과 실제 결과 사이 기대 차이가 크다.** 캔버스에서 보이는 프로토타입 상태 변화가 아니라 설명 데이터가 중심이며, 상태 목록·초깃값·재사용·삭제를 관리할 곳도 없다.
3. **Section 안의 반복 편집 흐름이 비효율적이다.** 자식을 추가해도 부모 섹션이 선택되어 이름 변경을 위해 `Nodes`에서 다시 찾아야 한다.
4. **Flow의 선택 화면 연결과 전체 연결이 중복 표시된다.** 적은 연결에서도 중복 생성으로 오해했고, 규모가 커지면 스캔 비용이 커진다.
5. **화면 생명주기 기능이 부족하다.** 플러그인에서 화면 복제, 삭제, 명시적 순서 변경을 할 수 없어 반복 화면과 예외 화면을 다루기 어렵다.
6. **blur 기반 저장의 상태가 보이지 않는다.** 입력 후 즉시 저장되지 않고, 저장 완료/실패 표시도 없어 빠르게 탭을 전환하는 사용자가 변경을 신뢰하기 어렵다.

### 낮음(Low)

1. **첫 실행 안내가 없다.** 빈 화면에서 `+ Screen`으로 유추할 수는 있지만 Build→Flow→Spec의 관계와 캔버스 선택 연동을 스스로 발견해야 한다.
2. **`Name`의 의미가 불명확하다.** 레이어 명칭, 실제 표시 문구, 행동 이름이 한 값으로 함께 바뀌어 초반에는 편하지만 서로 다른 문구가 필요할 때 막힌다.
3. **설정의 영향 범위가 늦게 드러난다.** 설정이 새 화면 기본 크기에만 적용되고 기존 화면은 유지되는데, 화면 생성 전에 설정을 발견하기 어렵다.
4. **기본 블록의 커스터마이즈 범위가 매우 좁다.** 텍스트 스타일, 이미지 선택, 여백 등은 없지만 저충실도 와이어프레임 도구라는 기대를 명확히 주면 수용 가능하다.

## 개선 제안

### 우선순위 1 — 산출물의 정확성과 안전성

1. 버튼 행동에 최소한의 조건 분기를 지원한다. 복잡한 로직 빌더보다 `조건 메모 + 성공 목적지 + 실패 목적지` 정도면 스타트업 PM의 예외 흐름 대부분을 정확히 표현할 수 있다.
2. 상태 행동에 `true`, `false`, `toggle`을 노출하고, 화면별 상태 목록에서 이름·초깃값·사용처·삭제를 관리하게 한다. 실제 Figma 인터랙션으로 구현되지 않는다면 `기획 명세용 상태`라고 명확히 표시한다.
3. 요소 삭제 전 연결/자식 영향을 보여주고 확인한다. 삭제 시 연결된 feature도 함께 제거하거나, 즉시 `Remove behavior`를 제공해 고아 항목이 남지 않게 한다.
4. Spec에 `All screens` 보기와 클립보드 복사를 추가한다. 화면 목적, 계층 요소, 행동, 미연결 목적지를 한 번에 복사할 수 있으면 별도 문서 도구 없이 전달 과업이 끝난다.

### 우선순위 2 — 반복 작업 속도

1. 자식 블록 추가 후 그 자식을 선택해 상세를 바로 편집하게 한다. 연속 추가는 `Add another` 또는 섹션 제목 선택으로 분리할 수 있다.
2. 화면 복제와 안전한 삭제를 화면 드롭다운 옆 메뉴에 제공한다.
3. Flow의 `Selected screen`/`Entire project`를 탭이나 토글로 분리하고 같은 연결을 한 화면에 중복 표시하지 않는다.
4. Name/Purpose 입력에 저장 상태(`Saving…`, `Saved`)를 표시하거나 입력 즉시 debounce 저장한다.

### 우선순위 3 — 첫 사용 이해

1. 빈 상태에 “화면 만들기 → 요소 추가 → 버튼 행동 연결 → Spec 확인”의 4단계 한 줄 안내를 넣는다.
2. `Name`을 `Canvas label` 또는 유형별 `Text/Button label`로 구체화하고, 필요하면 레이어명과 표시 문구를 분리한다.
3. Input에 최소한 `placeholder`, `required`, `validation note`를 제공하고 Spec에 그대로 노출한다. 실제 입력 프로토타입 구현보다 명세 정확도를 우선하면 충분하다.

## 종합 평가

Sketchy는 직선형 모바일 User Flow의 저충실도 화면, 버튼 이동, 캔버스 화살표, 화면별 설명을 빠르게 한곳에 만드는 데 강했다. 첫 세션에서는 별도 학습 없이 핵심 경로를 완성할 수 있었다. 그러나 두 번째 세션처럼 로그인 여부, 입력 검증, 품절 상태, 실패 경로가 들어오면 화면을 왜곡하는 우회가 필요했다. 다음 개선의 핵심은 더 정교한 UI 제작 기능이 아니라, **예외와 상태를 거짓 없이 적을 최소 표현력**과 **그 결과를 한 번에 전달하는 전체 Spec**이다.
