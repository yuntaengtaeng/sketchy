# 박지우 — Product Maker 재검증

## 참가자

- 이름: 박지우
- 배경: 개발자 출신 Product Maker. 제품 가설을 빠르게 화면과 클릭 가능한 흐름으로 만들고, 비동기 요청과 예외 상태까지 기획에 남긴다.
- 기대: 화면 전환은 실제 프로토타입으로 확인하고, 구현하지 않을 동작은 명세임을 즉시 구분하고 싶다.

## 검증 범위와 측정 기준

현재 `src`의 UI와 plugin 구현만 읽어 인지적 워크스루를 수행했다. 아래 수치는 실제 수행 시간이 아니라 구현상 예상치다.

- 클릭: 버튼은 1회, `select`는 열기와 항목 선택을 합쳐 2회로 계산했다.
- plugin 왕복: UI의 `post(...)` 1회와 이에 대한 `STATE` 또는 `ERROR` 응답을 1왕복으로 계산했다.
- 텍스트 입력 자체는 클릭 수에서 제외하고, `onBlur` 저장을 일으키는 바깥 클릭은 1회로 계산했다.

## 워크스루 1 — 작은 선형 업무 플로우

목표: `요청 작성` 화면의 `제출` 버튼을 누르면 `접수 완료` 화면으로 이동하는 2화면 흐름을 만든다.

1. Build에서 `+ Screen`을 눌러 첫 화면을 만든다. Screen details를 열어 이름을 `요청 작성`으로 바꾸고 바깥을 눌러 저장한다.
2. `+ Screen`을 눌러 둘째 화면을 만들고 같은 방식으로 `접수 완료`로 이름을 바꾼다.
3. 화면 선택기에서 `요청 작성`을 고르고 Button을 추가한다. 선택된 버튼의 이름을 `제출`로 바꾸고 바깥을 눌러 저장한다.
4. `What happens?`에서 `Go to screen`, Destination에서 `접수 완료`를 고른다.
5. Figma prototype reaction, Flow, Spec을 확인한다.

예상 비용은 14클릭, 9왕복이다. 화면·요소 이름을 기본값 그대로 쓰면 5클릭과 3왕복을 줄여 9클릭, 6왕복이다. Flow와 Spec 탭 확인은 각각 1클릭이며 plugin 왕복은 없다.

판정:

- `Go to screen` 선택 후 목적지를 고르면 plugin이 실제 Figma `ON_CLICK`/`NAVIGATE` reaction을 만든다. Flow에는 화면 간 연결로, Spec에는 `Go to ...`로 나타나므로 선형 프로토타입은 완결된다.
- 목적지를 고르기 전에도 navigate Feature가 저장되어 Flow/Spec에 `Choose destination`/`Destination not selected`가 드러난다. 미완성 링크를 숨기지 않는 점은 좋다.
- 기존 Figma click interaction이 같은 버튼에 있으면 명시적 오류를 보여 주어 덮어쓰지 않는다.
- 다만 UI 문구는 `Go to screen`이지 `Prototype navigation`은 아니다. 반대로 Describe에는 선택지, placeholder, Flow, Spec, 캔버스 purpose note에서 반복해 `spec only` 또는 `not prototyped`를 표시한다. 사용자는 Describe가 명세뿐임은 오해하기 어렵지만, Navigate가 실제 reaction을 만든다는 사실은 결과를 보거나 Figma 지식이 있어야 확신한다.

## 워크스루 2 — 기존 기획에 승인·실패 상태와 서버 요청 결과 추가

목표: 기존 `승인 요청` 화면에 요청 결과를 기록하고, 보이는 `승인됨` 및 `실패` 상태를 추가한다.

가능한 최소 경로:

1. `+ Screen`으로 `승인됨`, `실패` 화면을 각각 만들고 이름을 저장한다.
2. 기존 화면에 `승인 결과 보기`, `실패 예시 보기`, `서버 요청` 버튼을 각각 추가하고 이름을 저장한다.
3. 앞의 두 버튼은 `Go to screen`으로 각각의 상태 Screen에 연결한다.
4. `서버 요청`은 `Describe outcome (spec only)`을 고르고 `승인 요청을 전송하고 응답을 기다린다` 같은 결과를 입력해 blur로 저장한다.

기존 화면 선택이 유지되고 목적 Screen 이름과 버튼 이름을 모두 지정한다고 가정하면 예상 20클릭, 16왕복이다. Flow와 Spec 검토는 추가 2클릭, 0왕복이다.

판정:

- 데이터 모델과 캔버스는 일관된다. `Screen`에는 별도 state 필드가 없고, 보이는 상태는 일반 Screen/Frame 하나로 저장된다. navigate Feature는 그 Screen을 목적지로 참조하고 캔버스에는 실제 reaction과 connector가 생긴다.
- UI도 navigate 편집 중 `For a visible state, create a separate screen and link to it`이라고 안내한다. 별도 Screen 전략은 구현과 맞는다.
- 하지만 상태 Screen은 원본 화면과 관계를 나타내는 그룹, variant, 복제 기능이 없는 완전한 독립 화면이다. 사용자가 공통 구조를 수동 재작성해야 하고, 데이터 모델에서도 무엇의 상태인지 알 수 없다.
- 더 중요한 한계는 한 요소에 trigger 기반 Feature를 하나만 둘 수 있고 action도 `navigate | describe` 하나뿐이라는 점이다. 실제 `승인 요청` 한 번의 서버 응답이 성공이면 승인 상태, 실패면 실패 상태로 갈라지는 조건 분기를 표현하거나 프로토타입화할 수 없다. 위 경로는 서로 다른 세 버튼으로 사례를 분리한 기획 표현일 뿐 실제 요청 흐름은 아니다.
- `Describe outcome`은 기존 reaction을 제거하고 description만 저장한다. 따라서 서버 요청 결과는 Flow/Spec/캔버스 note의 명세이며 실행되지 않는다. `spec only` 표시는 반복되어 경계가 분명하다.

## 이전 데이터와 정리 동작

### 과거 `set-state` 데이터 마이그레이션

- 저장 데이터를 읽을 때 `toggle-state`와 `set-state` action은 `describe`로 바뀐다. 예전 `sourceElementId`도 click trigger로 옮겨진다.
- feature의 이름과 description은 보존되므로 텍스트 유실은 피한다. 이후 Flow/Spec에서는 spec-only 결과로 표시된다.
- 그러나 읽기만으로 마이그레이션된 project를 다시 저장하지 않는다. 다음 저장 전까지 원본 plugin data는 구형 형태다.
- 과거 캔버스의 `state-indicator`는 해당 feature를 사용자가 다시 저장할 때만 제거된다. 초기 sync/renderFlow는 이를 제거하지 않아, 데이터는 Describe(spec only)인데 캔버스에는 예전 상태 표시가 남을 수 있다. 경계와 상태 전략이 과거 문서에서 일시적으로 불일치한다.

### 요소 삭제 시 Feature 정리

- UI의 Delete는 선택 요소와 모든 하위 요소 ID를 구한 뒤, 그 ID를 trigger로 참조하는 Feature를 함께 삭제한다. section 삭제도 자식 버튼의 Feature까지 정리하므로 통과다.
- 사용자가 Figma 캔버스에서 노드를 직접 지운 경우 `cleanProject`는 요소를 제거하지만 Feature 자체는 남기고 trigger만 `undefined`로 바꾼다. Flow/Spec에는 `Unlinked` Feature가 남을 수 있어, 명시적 plugin 삭제과 외부 삭제의 정리 결과는 같지 않다.

## 최종 판정

**상태 전략: 부분 통과**

새 기획에서는 “보이는 상태 = 별도 Screen = 실제 navigate prototype”, “서버 동작 설명 = Describe = spec only”가 데이터 모델, UI, Flow/Spec, 캔버스 출력에서 대체로 일치한다. 그러나 한 요청의 성공/실패 분기를 모델링할 수 없고, 구형 state 표시와 캔버스 직접 삭제 뒤 orphan Feature가 남을 수 있어 전체 통과는 아니다.

### 남은 우선순위

- P0: 없음. 새 데이터의 선형 흐름과 명세 저장을 막거나 데이터를 즉시 잃는 문제는 확인되지 않았다.
- P1: 하나의 서버 요청 trigger에 성공/실패 결과와 각 상태 Screen 전환을 함께 표현할 수 없다.
- P1: `set-state`/`toggle-state` 읽기 마이그레이션 시 구형 `state-indicator`가 자동 정리되지 않아 spec-only 데이터와 캔버스가 충돌할 수 있다.
- P2: Navigate 선택지에 실제 Figma prototype을 만든다는 직접 문구가 없다.
- P2: 캔버스에서 요소를 직접 삭제하면 관련 Feature가 삭제되지 않고 `Unlinked`로 남아 plugin Delete와 결과가 다르다.
- P2: 상태 Screen에 원본 화면과의 관계를 나타내는 메타데이터나 복제 경로가 없어 상태가 많은 기획은 수동 작업과 추적 비용이 커진다.
