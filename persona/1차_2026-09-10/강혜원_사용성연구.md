# Sketchy 독립 사용성 연구 — 강혜원

## 참가자 페르소나

- 이름: 강혜원, 34세
- 업무 맥락: 6명 규모 B2B SaaS 팀에서 프로덕트 메이커로 일한다. 이전에는 프론트엔드 개발자였고, 지금은 고객 인터뷰, 요구사항 정리, 간단한 UX 설계, React 구현까지 한 기능을 처음부터 끝까지 맡는다. 전담 디자이너는 주 2일만 합류하므로 개발 착수 전 화면 구조와 핵심 동작을 스스로 설명할 수 있어야 한다.
- Figma 숙련도: 중상. Auto Layout, 컴포넌트, 프로토타입 연결, Dev Mode를 일상적으로 사용하지만 시각 디자인을 정교하게 다듬는 사람은 아니다. 플러그인은 반복 작업을 줄일 때만 사용한다.
- 시간 압박: 보통 고객 미팅 30분 전이나 스프린트 킥오프 전 20분 안에 흐름 초안을 만든다. 예쁜 결과보다 빠르게 논점을 드러내고, 며칠 뒤 요구가 바뀌어도 고치기 쉬운 산출물을 선호한다.
- 작업 습관: 먼저 최소 성공 경로를 화면 이름과 버튼 연결로 만든 뒤, 목적과 예외를 짧게 적는다. 입력 즉시 저장될 것이라고 기대하지만, 저장 여부가 보이지 않으면 한 번 다른 화면에 갔다 돌아와 확인한다. 캔버스에서 직접 위치를 옮기고 이름을 고치는 일도 자연스럽게 한다.

## 평가 전제

코드에 구현된 UI와 Figma 동작을 기준으로 한 인지적 워크스루다. 실제 배포 환경에서 마우스로 조작한 관찰은 아니므로, 렌더링 결과와 저장 동작은 구현으로 확인 가능한 범위만 판단했다. 테스트할 업무는 “팀 점심 주문 요청”의 모바일 최소 흐름이다.

## 1차 사용 — 최소 주문 요청 흐름 만들기

### 목표

직원이 메뉴를 고르고 수량을 입력한 뒤 주문 요청을 보내 완료 화면에 도달하는 흐름을 만든다. 개발 킥오프에서 화면 구성, 화면 목적, 클릭 이동을 한눈에 보여 주고 싶다.

### 시작 기대

플러그인을 열면 새 프로젝트나 시작 버튼이 나오고, 화면을 몇 개 만든 뒤 각 화면 안에 텍스트·입력·버튼을 놓을 수 있을 것으로 예상한다. 버튼끼리 화면을 연결하면 Figma 프로토타입도 함께 만들어지고, 마지막에 전체 흐름 또는 명세를 내보낼 수 있기를 기대한다.

### 구체적인 조작과 인지

1. 플러그인을 연다. 상단의 `Sketchy`, `build`, `flow`, `spec`, 설정 아이콘으로 보이는 버튼을 본다. 본문에는 `Screens` 드롭다운, `+ Screen`이 있다. 별도 프로젝트 생성 단계가 없어서 현재 Figma 파일 자체가 프로젝트라고 이해한다.
2. 기본이 모바일인지 확신하려 설정을 연다. `Mobile 390 × 844`, `Tablet`, `Desktop` 중 Mobile이 선택되어 있고 “새 화면의 기본 프레임이며 기존 화면 크기는 유지”된다는 안내를 본다. 설정은 즉시 반영되는 선택식으로 이해하고 뒤로 간다.
3. `+ Screen`을 누른다. `Screen 1`이라는 390×844 프레임이 캔버스에 생기고 선택된다. 화면이 자동 생성·배치되고 Build에는 Text, Button, Input, Image, Divider, Section이 보여 빠르게 골격을 만드는 도구라고 이해한다.
4. 접힌 `Screen details`를 열어 Name을 `메뉴 선택`, Purpose를 `오늘 주문할 메뉴와 수량을 고른다`로 입력하고 각 필드 밖을 클릭한다. 저장 버튼이 없고 `onBlur` 때 저장되는 구조라, 입력 도중에는 저장됐는지 표시가 없다. 불안해서 다른 탭에 갔다 돌아와 값이 남는지 확인하는 우회를 한다.
5. Section을 추가하고 이름을 `주문 폼`으로 바꾼다. Section이 선택되면 헤더가 `Section`과 뒤로 가기로 바뀌고, `New elements are added inside this section` 및 `Add to section`이 나타난다. 이 모드는 “이제 누르는 블록은 이 섹션 안에 들어간다”는 점이 명확하다.
6. 섹션 안에 Text, Input, Button을 차례로 추가한다. 추가 직후 섹션 자체가 선택되므로 같은 모드에서 연속 추가할 수 있다. `Nodes` 목록에서 각 자식을 선택해 Text를 `점심 메뉴`, Input을 `수량`, Button을 `주문 요청`으로 이름 바꾼다. 다만 Input에는 실제 값, 타입, 플레이스홀더를 정하는 옵션이 없고 Text도 이름이 곧 표시 문자열이다. 요구사항 표현과 와이어프레임 속성을 분리할 수 없어 이름에 의미를 몰아넣는다.
7. `주문 요청` 버튼에서 `What happens?`를 `Go to screen`으로 고른다. 목적 화면을 아직 만들지 않아 `Choose destination`만 보인다. 화면 추가 버튼은 Section 모드에서 보이지 않으므로 상단 뒤로 가기로 화면 수준으로 돌아간 다음 `+ Screen`을 눌러 `Screen 2`를 만든다.
8. `Screen 2`를 `요청 완료`, Purpose를 `요청 접수 결과와 다음 행동을 안내한다`로 변경한다. Text `주문 요청이 접수됐어요`와 Button `메뉴로 돌아가기`를 추가한다.
9. 화면 드롭다운에서 `메뉴 선택`으로 돌아가 `주문 폼` 섹션, `주문 요청` 버튼을 다시 찾아 선택한다. `Destination`에서 `요청 완료`를 지정한다. 구현상 이때 Sketchy 기능 데이터뿐 아니라 버튼의 Figma `ON_CLICK → NAVIGATE` reaction과 캔버스 커넥터도 생긴다. 다만 기존에 이 버튼에 다른 Figma 클릭 상호작용이 있으면 오류가 나므로, 기존 디자인에 덧씌우는 방식은 충돌 가능성이 있다.
10. `요청 완료`의 `메뉴로 돌아가기`도 `메뉴 선택`에 연결한다. `flow` 탭을 연다. 선택 화면과 관련된 연결을 위에 한 번 보여 주고, 아래 `Project flow`에서 전체 연결을 다시 보여 준다. 출발·도착 화면 이름 버튼으로 캔버스 선택을 이동할 수 있는 점은 유용하지만, 같은 연결이 두 번 보여 처음에는 중복 생성된 것으로 오해한다.
11. `spec` 탭에서 각 화면을 드롭다운으로 선택하며 확인한다. Purpose, 위에서 아래 순서의 요소 번호, 클릭 결과가 읽기 문장으로 나온다. 별도 “완성/내보내기”는 없으므로 이 화면과 캔버스 자체를 기획안으로 간주한다.

### 막힘과 우회

- 목적 화면을 나중에 만들면 버튼 설정 문맥을 떠나 화면을 만들고 다시 원래 화면·섹션·버튼을 단계적으로 찾아야 한다. 그래서 다음부터는 화면을 먼저 전부 생성하겠다고 학습한다.
- 폼 제출, 입력 변경, 필수값 검증을 표현할 수 없다. 타입에는 `change`, `submit`이 정의돼 있어도 현재 UI에서 트리거를 만들 수 있는 블록은 Button의 click뿐이다. “주문 요청 버튼 클릭” 한 줄로 축약하고 검증 조건은 Purpose에 적는다.
- 요소 순서를 UI 목록에서 끌어 바꿀 수 없다. 캔버스에서 노드를 옮기면 좌표 기반 읽기 순서가 재계산되는 구현에 기대어 직접 재배치해야 한다.
- Spec은 화면 단위이고 복사·내보내기 버튼이 없다. 팀 공유는 Figma 링크와 화면 캡처로 우회한다.

### 감정과 결과

화면과 기본 블록이 클릭 몇 번으로 생기는 초반은 빠르고 가볍다. Section 진입 후 연속 추가도 편하다. 그러나 버튼 연결을 위해 문맥을 왕복하고 저장 상태를 추측하는 순간부터 “빠른 기획 도구”보다 Figma 노드를 관리하는 보조 패널처럼 느껴진다. 결과적으로 두 화면의 클릭 왕복 프로토타입과 화면별 간단한 명세는 완성할 수 있다. 반면 수량 검증, 제출 조건, 실패 상태는 표현하지 못했으므로 실제 개발 가능한 수준의 완전한 기획안은 아니다.

## 2차 사용 — 승인 단계와 품절 예외 추가

### 목표

일주일 뒤 “5개 이상 주문은 팀장 승인이 필요하고, 품절이면 메뉴를 다시 고르게 한다”는 요구를 기존 기획에 반영한다. 기존 흐름을 보존하면서 승인 대기 화면과 품절 예외를 추가하고 싶다.

### 시작 기대

같은 Figma 파일에서 플러그인을 열면 기존 프로젝트가 그대로 복원되고, Flow에서 기존 연결 사이에 화면을 삽입하거나 분기 조건을 추가할 수 있을 것으로 기대한다. 변경 전후를 비교하거나 적어도 화면 복제로 빠르게 파생 화면을 만들고 싶다.

### 구체적인 조작과 인지

1. 같은 파일에서 플러그인을 다시 연다. 프로젝트가 문서 루트 plugin data에서 읽히고 기존 Sketchy 프레임이 다시 연결된다. 사라진 노드는 정리되며, 위치를 바꾼 요소의 순서는 캔버스 좌표로 다시 계산된다. 별도 파일 선택 없이 재개되는 점은 편하다.
2. 시작 탭은 항상 Build이고 현재 Figma 선택에 따라 화면/요소가 잡힌다. 아무것도 선택하지 않았다면 내부적으로 첫 화면이 내용 대상으로 보일 수 있지만 선택 ID는 없어서, Flow의 `Flow for …` 문맥은 나타나지 않는다. 드롭다운에서 `메뉴 선택`을 명시적으로 고른다.
3. 먼저 `flow`에서 현재 왕복 두 연결을 확인한다. 여기서는 연결을 클릭해 출발/도착 화면으로 이동할 수만 있고 연결을 편집·삭제하거나 새 화면을 사이에 삽입할 수 없다. Build로 돌아간다.
4. `+ Screen`으로 `Screen 3`을 만든 뒤 `승인 대기`, Purpose를 `대량 주문의 팀장 승인 상태를 안내한다`로 바꾼다. 기존 완료 화면을 복제할 수 없으므로 Text와 Button을 처음부터 다시 추가하고 이름을 붙인다.
5. `메뉴 선택`의 `주문 요청` 버튼을 찾아 기존 목적지 `요청 완료`를 `승인 대기`로 바꾼다. 구현상 Sketchy가 소유한 이전 reaction을 제거하고 새 목적지 reaction으로 교체하므로 단일 경로 변경은 가능하다.
6. 이제 “1~4개는 요청 완료, 5개 이상은 승인 대기”라는 조건 분기를 넣으려 한다. 버튼 하나에는 기능 하나만 저장되고 동작 선택도 Navigate 또는 Change state 하나뿐이다. 조건, 비교값, 복수 목적지를 입력할 곳이 없다. 버튼을 `일반 주문 요청`과 `대량 주문 요청` 두 개로 쪼개면 시연은 가능하지만 실제 요구와 다른 UI가 되므로 하지 않는다. Purpose에 조건을 문장으로 기록하고 프로토타입은 승인 대기로만 연결하는 불완전한 우회를 택한다.
7. 품절 예외용 `품절 안내` 화면을 새로 만들려고 한다. 화면 복제와 템플릿이 없어 다시 블록을 구성한다. 품절 여부를 Input 변화나 주문 응답으로 발생시키는 트리거가 없고, 화면 상태 역시 UI에서 독립적으로 만들거나 초기값을 편집할 수 없다. 테스트용 `품절 보기` 버튼을 추가해 품절 안내로 연결할 수는 있지만 제품 UX를 왜곡한다. 결국 화면과 Purpose만 만들고 연결하지 않는다.
8. 잘못 만든 `품절 보기` 버튼은 Delete로 지울 수 있다. 하지만 잘못 만든 화면 전체를 플러그인에서 삭제하는 버튼은 없다. 캔버스에서 프레임을 직접 삭제하면 다음 동기화 때 프로젝트 목록이 정리되는 것을 구현상 기대할 수 있지만, 이 복구 경로가 UI에 안내되지 않는다.
9. `spec`을 다시 확인한다. 화면별 현재 요소와 기능은 보이지만 연결되지 않은 `품절 안내` 화면이 프로젝트 전체 기획에서 고립됐다는 경고가 없다. Purpose에 적은 승인 조건과 실제 프로토타입의 무조건 이동이 모순되어도 검증하지 않는다.
10. 변경 이력, 버전, 요구사항 단위 메모가 없으므로 기존 완성안과 확장안을 비교할 수 없다. Figma 파일을 미리 복제하지 않았다면 이전 상태로 돌아갈 Sketchy 전용 수단은 없다.

### 막힘과 우회

- 조건 분기와 한 트리거의 여러 결과를 모델링할 수 없어 Purpose 텍스트와 실제 연결이 서로 다른 기획이 된다.
- 기존 화면 복제 기능이 없어 유사한 완료/오류 상태를 반복 생성한다.
- 화면 삭제는 캔버스 직접 삭제 후 자동 정리에 의존한다. 플러그인만 보는 사용자는 삭제 불가로 판단할 가능성이 높다.
- Flow는 조회·이동용이며 그래프 편집기가 아니다. 기존 연결을 확장하려면 Build에서 원본 버튼까지 되짚어 가야 한다.
- 상태 변경은 버튼 이름을 그대로 상태 이름으로 만들고 항상 true로 설정한다. 상태명, 초기값, false 전환을 UI에서 다룰 수 없어 실제 승인/품절 상태 모델에는 부족하다.

### 감정과 결과

기존 작업이 자동 복원되는 순간에는 신뢰가 생긴다. 하지만 단순 목적지 교체를 넘는 요구가 나오자 모델의 한계가 곧 산출물의 모순으로 이어져 답답하다. “가능한 것만 예쁘게 보이는 명세”가 되어 개발자 관점에서는 오히려 오해 위험이 있다. 승인 대기와 품절 안내 화면, 목적 설명, 단일 승인 경로까지는 추가할 수 있다. 수량별 조건 분기와 품절 발생 경로는 구현할 수 없으므로 2차 기획안은 완성되지 않는다.

## 잘된 점

- 새 화면이 지정 프리셋 크기로 자동 배치되고 선택되어 빈 캔버스에서 시작하는 비용이 낮다.
- 블록 추가가 즉시 실제 Figma 노드를 만들며, 버튼 이동은 실제 프로토타입 reaction과 동기화된다. 발표용 클릭 데모까지 한 흐름으로 이어진다.
- Section 안에서는 추가 대상이 명시되고 연속 추가가 자연스럽다. 자식 목록으로 작은 화면에서도 선택할 수 있다.
- 화면 이름, 목적, 요소 이름을 바꾸면 캔버스와 Flow/Spec 표현이 함께 갱신된다.
- 프로젝트가 Figma 문서에 저장되고 삭제된 노드를 정리하므로 같은 파일 재방문은 별도 저장/불러오기 없이 가능하다.
- Spec의 계층 번호와 화면별 목적/행동 요약은 최소 개발 대화에 유용하다.

## 두 회차 사이에서 드러난 재방문·확장성 문제

첫 사용의 최소 선형 흐름에서는 “화면 생성 → 블록 추가 → 버튼 연결”이라는 구조가 잘 맞는다. 재방문 자체도 문서 저장 덕분에 매끄럽다. 문제는 재방문 후 흔히 생기는 변화가 단순 추가가 아니라 분기, 예외, 기존 경로 사이 삽입, 유사 화면 파생이라는 점이다. Sketchy의 저장 지속성은 충분하지만 편집 모델은 선형 데모 단계에 머문다.

특히 텍스트 Purpose는 자유롭게 복잡한 조건을 담을 수 있는 반면 프로토타입 모델은 단일 클릭 결과만 담는다. 시간이 지나 요구가 늘수록 이 둘의 차이가 커지고, Spec은 그 차이를 경고하지 않는다. 따라서 재방문자는 “기존 것을 안전하게 확장한다”기보다 기존 연결을 덮어쓰고 누락 사항을 문장으로 숨기게 된다. 화면 복제·삭제·연결 편집·변경 이력이 없다는 점도 화면 수가 증가할수록 누적 비용이 된다.

## 우선순위 개선안

1. 가장 먼저 버튼/폼 기능 모델에 조건과 복수 결과를 추가하고, UI에서 Input change 및 form submit을 실제로 생성할 수 있게 한다. 완전한 규칙 엔진보다 `조건(필드·연산자·값) → 목적 화면`의 최소 구조가 먼저다.
2. Flow 목록에서 연결의 목적지 변경, 삭제, 그리고 새 화면을 연결 사이에 삽입할 수 있게 한다. 고립 화면과 목적지 미지정 연결은 명확히 경고한다.
3. 화면 행에 `복제`, `삭제`를 제공한다. 삭제 시 연결 영향만 확인하고, Figma 노드와 프로젝트 데이터를 함께 안전하게 정리한다.
4. Spec에 “설명에는 있으나 동작으로 표현되지 않은 조건”을 자동 판별하기 어렵다면, 최소한 미연결 화면·목적지 미지정·트리거가 사라진 기능을 검증 항목으로 표시한다. 전체 프로젝트 명세 복사도 제공한다.
5. 입력 필드는 Enter/즉시 저장 또는 명시적 저장 상태(`Saving…`/`Saved`)를 보여 주고, Section 안에서도 화면 전환·추가가 가능한 고정 탐색을 유지한다.
6. 상태 편집 화면을 만들어 상태명, 초기값, true/false 설정을 분리한다. 그 다음 단계로 토글을 고려한다.
7. 중복되는 Flow 표현에 `Selected screen`과 `All connections`의 목적을 더 분명히 표시하거나, 선택 필터 토글 하나로 합친다. 깨진 특수문자도 함께 바로잡는다.

## 종합 판단

Sketchy는 빈 Figma 파일에서 두세 화면의 선형 클릭 프로토타입과 화면별 요약 명세를 빠르게 만드는 데 성공한다. 그러나 실제 제품 기획이 한 번의 피드백을 거쳐 조건과 예외를 갖는 순간, 현재 행동 모델과 편집 UX로는 기획안을 완성할 수 없다. 재방문 시 데이터가 남는다는 장점보다, 남아 있는 구조를 안전하게 변형하고 모순을 찾는 기능의 부재가 더 크게 체감된다.
