## 만들려는 서비스와 기획안

동네 공방의 원데이 클래스를 발견하고 예약하는 모바일 서비스 **모아클래스**를 만든다.

1차 목표 흐름은 `클래스 탐색 → 클래스 상세 → 예약 확인 → 예약 완료`이다. 탐색 화면에는 검색 입력과 추천 카드, 상세 화면에는 대표 이미지·설명·가격·예약 버튼, 예약 확인 화면에는 일정 요약과 결제 버튼, 완료 화면에는 확인 메시지와 홈 버튼이 필요하다.

2차 요구사항은 현실적인 예외 흐름을 추가하는 것이다. 상세 화면에서 찜 상태를 바꾸고, 비회원이 예약하면 로그인 안내로 보내며, 매진 클래스에서는 예약 대신 대기 알림 신청을 제공한다.

> 아래 기록은 플러그인이 제공하는 UI와 그 조작에 따른 캔버스/프로젝트 반응만으로 수행한 독립 세션이다. 제공되지 않은 조작은 성공한 것처럼 간주하지 않았다.

## 1차 세션 — 처음부터 핵심 예약 흐름 만들기

### 목표

리뷰에 쓸 수 있는 네 화면짜리 모바일 와이어프레임과 클릭 가능한 happy path, 화면별 기획 요약을 완성한다.

### 사전 기대

이름만 보고 손그림 같은 저충실도 화면을 빠르게 만드는 도구라고 예상했다. 빈 캔버스에서 화면 템플릿을 고르고, 블록을 쌓고, 화면 사이를 연결하는 순서를 기대했다. Build / Flow / Spec은 각각 제작, 흐름 확인, 명세라고 추측했다.

### 1차 결과물

- 모바일 프레임 4개: 탐색, 클래스 상세, 예약 확인, 예약 완료
- 기본 블록으로 만든 저충실도 화면 구조
- 버튼 클릭 기반의 순환 가능한 예약 happy path
- 각 화면의 Purpose와 자동 생성된 화면별 Spec
- 캔버스의 자동 연결선 및 Flow 목록

### 1차 총평

“화면 만들기→버튼 연결→명세 확인”이라는 큰 루프는 설명 없이도 15분 안에 익혔다. 특히 실제 Figma 프레임과 프로토타입 인터랙션이 만들어지는 점은 기대 이상이었다. 반면 상세 편집에서는 복제, 재정렬, 화면 삭제가 없어 같은 조작을 반복했고, 저장 시점과 현재 선택 대상이 모호해 속도가 끊겼다. 결과는 리뷰용 구조도에는 충분하지만, 실제 UI 와이어프레임으로 발전시키기에는 표현력이 빠르게 한계에 닿았다.

## 2차 세션 — 재방문해 상태와 예외 흐름 추가하기

### 목표

기존 기획안에 다음을 추가한다.

1. 상세 화면의 찜 버튼을 눌러 저장 상태로 바꾸기
2. 비회원 예약 시 로그인 안내를 거쳐 예약 확인으로 이동하기
3. 매진일 때 대기 알림 신청 흐름 제공하기

### 사전 기대

이전 프로젝트가 파일에 남아 있고, 기존 화면/연결을 수정할 수 있을 것으로 기대했다. `Change state`를 보았기 때문에 버튼 텍스트나 화면 상태를 실제로 토글할 수 있다고 추측했다. 예외 흐름은 기존 화면 복제로 빠르게 만들고, Flow에서 분기를 확인하고 싶었다.

### 단계별 사용 기록

| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | 시간이 지난 뒤 같은 Figma 파일에서 플러그인을 다시 연다.                                                                                                                              | 기존 화면, 요소, 설정, feature가 다시 나타나고 자동 연결선도 재구성된다. 현재 캔버스 선택에 따라 관련 화면/요소가 열린다.                                                                                                   | 별도 프로젝트 불러오기가 없어도 이어서 작업할 수 있어 좋다.                                                                                               | 플러그인 데이터의 저장 위치나 동기화 상태에 대한 설명은 없지만 같은 파일 안에서는 문제없이 계속한다.                                                                     |

### 2차 결과물

- 기존 happy path에 로그인 안내 화면과 돌아가기 경로 추가
- 별도 매진 상세 화면과 대기 알림 신청 버튼 추가
- 찜, 대기 알림을 Change state 설명으로 기록
- Flow/Spec에 예외 행동의 텍스트 명세 추가

완성하지 못한 부분은 로그인 여부에 따른 조건 분기, 찜 토글의 실제 시각 상태, 입력값 검증/submit, 모달 표현, 정상 상세의 효율적 복제, 테스트 화면 삭제이다.

### 2차 총평

기존 선형 연결을 수정하거나 새 화면을 이어 붙이는 일은 쉬웠다. 그러나 현실적인 요구사항이 들어오자 “행동을 설명하는 것”과 “동작하는 프로토타입”의 경계가 UI에서 분명하지 않았다. Navigate는 실제 Figma 프로토타입으로 작동하지만 Change state는 주로 명세 데이터로 남아 같은 수준의 실행 가능성을 기대한 사용자를 실망시킨다. 또한 생성보다 수정·정리 기능이 부족해 프로젝트가 커질수록 유지 비용이 빠르게 증가한다.

## 발견사항과 심각도

### 치명적 (Critical)

없음. 기본 화면 생성과 버튼 기반 선형 흐름은 중단 없이 완료할 수 있었다.

### 높음 (High)

1. **Change state가 실행 가능한 상태 변화처럼 보이지만 실제 시각 상태 전환을 만들지 않는다.** Navigate와 같은 What happens? 목록에 있어 동등한 프로토타입 기능으로 기대하게 된다. 찜, 선택, 펼침 같은 핵심 상태 시연을 완료할 수 없다.
2. **조건 분기와 폼 이벤트를 표현할 수 없다.** 로그인 여부, 매진 여부 같은 조건이 없고 Input은 생성할 수 있어도 change/submit 행동을 지정할 수 없다. 실제 서비스의 예외 흐름이 정적 화면 우회로 축소된다.
3. **화면 삭제·복제·재정렬이 없다.** 초기 생성보다 재방문 수정 세션에서 영향이 크다. 잘못 만든 화면을 안전하게 정리하지 못하고, 유사한 상태 화면을 처음부터 다시 만들어야 한다.
4. **캔버스 선택과 플러그인 맥락이 쉽게 어긋난다.** 내부 라벨처럼 메타데이터가 없는 노드를 선택하면 선택 맥락이 사라지고 첫 화면으로 fallback되어, 사용자가 보고 있던 화면과 편집 대상이 달라질 수 있다.

### 중간 (Medium)

1. **저장 시점이 blur에 의존하지만 저장 상태 피드백이 없다.** 입력 후 바로 탭을 바꾸거나 플러그인을 닫을 때 저장됐는지 판단하기 어렵다.
2. **섹션 자식 추가 후 새 요소가 선택되지 않는다.** 반복적으로 Nodes 목록에서 방금 만든 항목을 찾아야 하며, 같은 타입을 여러 개 만들면 구분도 어렵다.
3. **Flow의 선택 화면 영역과 Project flow가 같은 연결을 중복 표시한다.** 연결이 많아질수록 스캔이 느려지고 조건/분기 구조를 파악하기 어렵다.
4. **Spec에서 화면 전환과 전체 내보내기가 어렵다.** 현재 화면 의존성이 강하고, 여러 화면의 명세를 한 번에 검토·공유하는 동선이 없다.
5. **제공 범위와 결과 수준을 설명하지 않는다.** 첫 화면에서 블록이 실제 Figma 노드를 만든다는 점, Navigate와 Change state의 실행 수준 차이, 지원하는 상호작용 범위를 알 수 없다.

### 낮음 (Low)

1. 탭 이름이 영어 소문자이고 일부 기호 중심 컨트롤은 완성도와 의미 전달이 약하다.
2. 블록 스타일 조절은 버튼 Filled/Outline과 섹션 방향뿐이라 저충실도 이후 확장이 어렵다.
3. 화면 선택이 드롭다운 하나라 화면 수가 늘면 전체 구조를 훑기 어렵다.
4. 화면 목적과 블록 이름을 모두 직접 입력해야 해 유사 화면 제작 시 반복 입력이 많다.

## 개선 제안

### 우선순위 1 — 기능 기대와 실제 결과를 일치시키기

- What happens?의 항목을 `Navigate (prototype)`와 `Describe state change (spec only)`처럼 결과 수준이 드러나는 문구로 바꾸고, 선택 직후 짧은 설명을 제공한다.
- 가능하다면 Change state에 최소한 `Set true / Set false / Toggle`과 두 시각 상태 연결을 제공한다. 실행 구현 전이라면 “시각 변화는 생성되지 않음”을 명확히 표시한다.
- Input에는 최소한 Submit 버튼과 연결할 수 있는 폼 그룹 또는 `On change / On submit` 행동 입력을 제공한다.

### 우선순위 2 — 재방문 편집의 기본 작업 완성하기

- Screen details에 Duplicate와 Delete를 추가한다. 삭제 전 연결/요소 영향만 한 번 확인하고, Figma Undo로 복구 가능하다는 안내를 붙인다.
- 화면 드롭다운에 정렬 가능한 목록 또는 화면 관리 뷰를 제공한다. 현재 화면과 시작 화면을 명확히 표시한다.
- 블록 추가 직후 새 블록을 선택해 details로 바로 이어지게 한다. 섹션으로 돌아가는 경로는 breadcrumb로 유지한다.

### 우선순위 3 — 선택과 저장의 신뢰 높이기

- 내부 자식 노드가 선택되어도 가장 가까운 Sketchy 요소/화면을 부모 방향으로 찾아 맥락을 유지한다. fallback이 필요하면 조용히 첫 화면을 보여주지 말고 `Sketchy 화면을 선택하세요` 상태를 표시한다.
- Name/Purpose/description에 디바운스 자동 저장과 `Saved` 피드백을 제공하거나, 명시적 Apply를 사용해 blur 의존성을 없앤다.
- 헤더나 화면 선택기에 현재 편집 중인 화면 이름을 항상 표시한다.

### 우선순위 4 — 흐름 검토와 공유 개선하기

- Flow에서 `Selected only / Entire project`를 토글하게 해 중복을 제거한다.
- Navigate와 상태 설명을 시각적으로 구분하고, 미연결 행동만 모아보는 필터를 제공한다.
- Spec에 화면 선택기를 유지하고 `전체 화면 복사` 또는 Markdown 내보내기를 제공한다.

## 최종 판단

Sketchy는 처음 만드는 작은 선형 흐름에서는 빠르고 배울 것이 적다. 화면 프레임, 기본 블록, 실제 Navigate, 자동 명세가 한 루프로 이어지는 점은 분명한 강점이다. 하지만 두 번째 세션처럼 수정과 예외가 시작되면 프로토타이핑 도구인지 행동 명세 도구인지 경계가 흐려지고, 화면 관리와 선택 안정성 부족이 작업 신뢰를 떨어뜨린다. 현재 상태에서 나는 **초기 리뷰용 happy path 초안**에는 쓰겠지만, **조건·상태·폼이 있는 실제 제품 흐름의 기준 파일**로는 쓰지 않겠다.
