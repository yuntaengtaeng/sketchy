# Sketchy 초보 독립 UX 검증

## 검증 전제와 사용자

- 사용자: **김서윤, 27세**, 8명 규모 반려동물 커머스 스타트업의 콘텐츠 마케터. Figma는 카드뉴스 문구를 고치는 용도로 4~5번 써 봤고, 이번 주 처음으로 제품 기획 업무를 맡았다.
- 업무 맥락: 내일 오전 개발 회의 전에 모바일 **무료 샘플 신청 흐름**을 화면, 클릭 흐름, 간단한 명세까지 만들어야 한다. 1차 작업에는 40분, 이틀 뒤 변경 반영에는 20분밖에 없다.
- 작업 습관: 마우스로 눈에 보이는 버튼부터 누르고, 설정 문서는 거의 읽지 않는다. 화면 이름은 한국어로 구체적으로 짓지만 낯선 영문 제품 용어는 검색하기보다 먼저 눌러 본다. 저장 버튼이 없으면 자동 저장인지 불안해 다른 탭을 눌러 확인한다.
- 검증 방식: 실제 사람을 관찰하거나 시간을 잰 테스트가 아니라, `manifest/package`와 `src/ui`, `src/plugin`, `src/shared` 구현을 근거로 한 **구현 기반 인지적 워크스루**다. 따라서 실제 렌더링의 시각 품질, Figma 호스트의 체감 지연, 실사용 소요 시간은 검증하지 않았다. 아래의 클릭 결과와 실패 판정은 구현상 가능한 범위만 반영했다.

## 1차: 무료 샘플 신청 User Flow 만들기

### 목표

`상품 소개 → 신청서 → 신청 완료`의 3개 화면을 만들고, 소개 화면의 신청 버튼과 신청서의 제출 버튼을 연결한다. 제출 전에는 확인 팝업을 띄우고 팝업의 확인 버튼으로 완료 화면에 가게 한 뒤, Flow와 Spec에서 개발자에게 넘길 기획안이 되었는지 확인한다.

### 시작 기대

플러그인을 열면 템플릿이나 “첫 화면 만들기” 안내가 있고, 화면을 추가한 뒤 각 화면 안에 제목·입력창·버튼을 끌어 넣으며 연결할 수 있을 것으로 기대한다. `Build`는 화면 제작, `Flow`는 연결도, `Spec`은 문서라고 짐작한다. `Screen`은 앱 한 페이지, `State`는 같은 화면의 로딩/오류 상태라고 어렴풋이 이해한다.

### 수행 기록

#### 1. 빈 프로젝트에서 화면 만들기

1. 상단의 `build / flow / spec` 중 선택 강조가 된 `build`를 현재 작업 영역으로 이해한다.
2. `Screens`의 빈 셀렉트와 `+ Screen`을 본다. 빈 셀렉트를 먼저 눌러 보지만 `Select a screen` 외에 고를 것이 없어 닫는다. **첫 잘못 누름**이다.
3. `+ Screen`을 눌러 `Screen 1`을 만든다. 별도 이름 입력 대화상자가 없고 즉시 Figma 캔버스에 모바일 프레임이 생성·선택된다.
4. 아래쪽 `Screen details`를 펼쳐 Name을 `상품 소개`, Purpose를 `무료 샘플의 장점을 보고 신청을 시작한다`로 바꾼다. 입력 직후 아무 변화가 없어 잠깐 멈칫한다. 다른 곳을 클릭해 포커스를 빼야 저장 메시지가 전송되는 구조이므로, 자동 저장이라는 확신은 낮다.
5. 같은 방식으로 `+ Screen`을 두 번 눌러 `신청서`, `신청 완료`를 만들고 각각 Purpose를 입력한다.

이해 근거: `+ Screen`이라는 결과 중심 라벨과 자동 선택 덕분에 생성 자체는 설명 없이 가능하다. 반면 이름과 Purpose의 저장 조건이 `onBlur`이고 저장 상태 표시가 없어 “입력 중/저장됨”을 구별할 수 없다.

- 멈칫: 화면 크기를 어디서 정하는지 보이지 않는다. 우측 상단의 글자가 깨져 보이는 아이콘성 버튼을 설정이라고 즉시 알아보기 어렵다.
- 확신: 화면 생성 5/5, 이름 저장 3/5.
- 감정: 첫 화면이 즉시 캔버스에 생겨 안도하지만, 저장 여부는 불안하다.

#### 2. 상품 소개 화면 구성

1. Screens 셀렉트에서 `상품 소개`를 고른다.
2. `Add something` 아래 `Text`, `Button`, `Input`, `Image`, `Divider`, `Section` 카드 중 `Text`를 눌러 제목을 만든다.
3. 생성된 항목이 바로 선택되어 `text details`가 보인다. Name을 `무료 샘플 받아보기`로 바꾸고 바깥을 클릭한다.
4. `Image`, `Text`, `Button`을 차례로 추가하고 이름을 `샘플 이미지`, `배송비 없이 체험해 보세요`, `무료 신청하기`로 바꾼다.
5. Button의 `Style`에서 `Filled`가 선택된 것을 보고 주 행동 버튼이라고 이해해 그대로 둔다.

이해 근거: 블록 카드에 간단한 미리보기와 익숙한 요소명이 있어 초보도 추가 결과를 예측할 수 있다. 다만 캔버스의 요소를 클릭하면 세부 정보로 이동하고, 플러그인에서 블록을 누르면 새 요소가 생기는 두 조작 모델이 섞여 있다.

- 멈칫: Text를 추가할 때마다 플러그인 아래쪽에 details가 붙지만 “목록”은 없어 이전 요소로 돌아가려면 캔버스를 클릭해야 한다. Figma 선택 개념을 조금 알아야 한다.
- 잘못/되돌아감: `Section`을 “한 화면의 구역 제목”으로 생각해 눌렀다가, 선택 즉시 편집 화면이 `Add to section`, `Nodes`로 바뀌어 컨테이너임을 뒤늦게 이해한다. 뒤로 가기로 Screen에 돌아온 뒤 해당 Section을 Delete한다. 삭제 확인이나 자식 영향 안내는 없다.
- 선택지 고민: Button과 Filled/Outline은 비교가 쉽다. Section은 카드만 보고 용도를 알기 어렵다.
- 확신: 블록 추가 4/5, 구조 관리 2/5.
- 감정: 와이어프레임이 빨리 생기는 점은 만족스럽지만 선택한 요소를 다시 찾는 데 긴장한다.

#### 3. 소개 버튼을 신청서로 연결

1. 캔버스에서 `무료 신청하기` 버튼을 선택한다.
2. `button details`의 `Default · prototype`(구현 문자열에는 구분 문자가 깨져 보일 가능성이 있음) 영역을 본다.
3. `What happens?` 아래 붙어 있는 세 버튼 `Go to screen / Open popup / Stay on screen`을 비교한다. 선택 강조가 있는 segmented selector로 보이지만, 라디오인지 즉시 실행 버튼인지 설명이 없다.
4. 목표가 다음 페이지 이동이므로 `Go to screen`을 누른다.
5. 바로 `Destination` 셀렉트가 나타나고 `신청서`를 선택한다.
6. `Also happens`에는 `신청 시작 이벤트 기록`을 입력하고 바깥을 클릭한다.

이해 근거: `What happens?`라는 질문과 결과형 선택지, 선택 뒤에만 나타나는 Destination은 단계적으로 이해하기 좋다. 현재 Screen은 대상에서 제외되고 일반 Screen만 보이므로 실수 범위도 작다.

- 멈칫: `Default · prototype`이 “기본 클릭 동작이며 실제 Figma 프로토타입이 된다”는 뜻인지, 단순 기본값인지 알기 어렵다. `prototype`이라는 말은 Figma 초보에게 기능 범위가 불명확하다.
- 선택지 고민: `Go to screen`과 `Stay on screen`은 구별되지만, `Stay on screen`이 오류 문구 표시·상태 변경·단순 설명 중 무엇인지 알 수 없다.
- 잘못/되돌아감: Destination을 정하기 전에 실수로 `Stay on screen`을 눌렀다가 Destination이 사라진다. 경고 없이 액션이 즉시 바뀌어 이전 선택이 덮인 것처럼 느낀다. 다시 `Go to screen`과 `신청서`를 선택한다.
- 확신: 최종 연결 4/5, 용어 이해 2/5.
- 감정: 연결 자체는 짧아서 기쁘지만 저장 버튼이 없고 선택 즉시 반영되어 조심스럽다.

#### 4. 신청서와 확인 팝업 만들기

1. 신청서 Screen을 선택해 Text `배송 정보를 입력해 주세요`, Input `이름`, Input `주소`, Button `신청 내용 확인`을 추가한다.
2. Input을 선택해도 Name 외에 필수 여부, placeholder, 입력 타입, 검증 규칙을 설정할 수 없음을 확인한다. 기획안에 필수값 오류를 넣고 싶지만 현재 UI에서는 입력 요소 행동을 작성할 수 없다.
3. `신청 내용 확인` 버튼을 선택하고 segmented selector에서 `Open popup`을 누른다.
4. Destination을 고르는 단계가 먼저일 것으로 기대했지만, 누르는 순간 `신청서 · Popup 1`이라는 State가 자동 생성되고 연결된다. 화면 셀렉트에는 `States` 그룹이 생긴다.
5. `Edit popup` 버튼을 눌러 팝업 Section 편집으로 이동한다. 이 버튼은 “팝업 편집”이라는 결과가 명확해 다음 행동을 고르기 쉽다.
6. 기본 Text `Popup`을 선택해 `입력한 내용으로 신청할까요?`로 이름을 바꾼다.
7. 팝업 Section에 Button 두 개를 추가해 `신청 확정`, `취소`로 이름을 바꾼다.
8. `신청 확정`을 선택한다. 팝업 내부라 selector가 `Go to screen / Close popup / Stay on screen`으로 바뀐다. `Go to screen` → Destination `신청 완료`를 고른다.
9. `취소`를 선택하고 `Close popup`을 고른다.
10. 상단 뒤로 가기를 눌러 신청서로 돌아간다.

이해 근거: `Open popup`을 고르면 팝업용 State, dim, 팝업 Section과 기본 Text까지 자동 생성된다. 초기 작업량은 크게 줄어든다. 팝업 안에서는 허용 액션이 `Close popup`으로 바뀌어 맥락과 맞는다.

- 멈칫: `State`가 팝업을 뜻하는지, 모든 상태의 상위 개념인지 아무 설명이 없다. 일반 오류/로딩 State를 직접 추가하는 버튼은 없고, 구현상 현재 생성 가능한 State는 팝업뿐이다.
- 선택지 고민: 팝업을 연 뒤 Destination이 자동으로 채워져 편하지만, 기존 팝업을 재사용하는 선택과 새 팝업 생성의 차이를 누르기 전에 알 수 없다. 빈 Destination 상태에서 `Open popup` 선택 자체가 생성 명령이라는 점이 숨겨져 있다.
- 잘못/되돌아감: 팝업을 보기만 하려 `Open popup`을 눌렀는데 이미 State가 만들어진다. 실행 취소 버튼은 없다. 이번 과업에는 필요해 유지하지만, 탐색 클릭이 문서 구조를 바꾸는 경험이다.
- 확신: 팝업 생성 3/5, 팝업 내부 편집 4/5, State 개념 1/5.
- 감정: 자동 생성은 놀랍고 편하지만, 돌이키기 어려운 변화처럼 보여 당황한다.

#### 5. Flow와 Spec으로 기획안 확인

1. 상단 `flow`를 클릭한다.
2. 선택 중인 Screen과 관련된 `Flow for …`와 전체 `Project flow`가 함께 나온다. 출발 Screen, 기능명, 도착 Screen이 행으로 표시되고 Screen 버튼을 누르면 캔버스가 해당 Screen으로 이동한다.
3. 같은 연결이 선택 Screen 영역과 Project 영역에 중복으로 보여 처음에는 연결이 두 번 생성됐다고 오해한다. 섹션 제목을 다시 읽고 중복 뷰임을 이해한다.
4. `spec`을 클릭한다. 현재 선택 Screen의 Purpose, 위에서 아래 요소 목록, 사용자가 할 수 있는 행동이 보인다.
5. 다른 Screen의 Spec을 보고 싶어 Screen 셀렉트를 찾지만 Spec 탭에는 없다. Figma 캔버스에서 프레임을 선택하거나 Build로 돌아가 Screen을 선택한 뒤 다시 Spec으로 와야 한다.

이해 근거: Flow는 연결 상태와 Destination 누락을 텍스트로 보여 주고, Spec은 화면별 구조와 행동을 자동 정리한다. 별도 내보내기 없이도 회의 중 참고할 수 있는 기획안 역할은 한다.

- 멈칫: `Flow`가 편집 탭인지 검토 탭인지 알 수 없다. 구현상 연결을 직접 추가·수정할 수 없는 읽기 전용에 가깝다. `Spec`도 복사, 내보내기, 전체 화면 명세 보기 기능은 없다.
- 선택지 고민: Flow 행의 Screen 이름 버튼을 누르면 Flow 필터가 바뀔지 Build로 이동할지 예측하기 어렵다. 실제로는 Figma 선택만 이동하며 탭은 Flow에 남는다.
- 잘못/되돌아감: Spec에서 Screen을 바꾸려고 제목을 눌러 보지만 동작하지 않는다. Build → Screen 선택 → Spec으로 우회한다.
- 확신: 연결 검토 4/5, “완성된 전달물” 여부 2/5.
- 감정: 자동 요약은 유용하지만 제출하거나 공유할 산출물로 마감됐다는 느낌은 약하다.

### 1차 결과

**부분 성공.** 세 일반 Screen, 한 팝업 State, 네 개 버튼 행동, Flow/화면별 Spec까지 구현상 만들 수 있다. Figma의 기본 클릭 프로토타입도 각 버튼의 기본 Case에 연결된다. 그러나 입력 필드의 필수/검증 규칙은 작성할 곳이 없고, 전체 기획안을 한 번에 내보내거나 완료 상태로 확정할 수 없다. 따라서 “낮은 충실도의 화면·클릭 흐름 초안”은 성공했지만 “개발에 바로 전달할 완성 기획안”은 실패다.

## 2차: 품절 예외와 재신청 요구 반영

### 추가 요구

이틀 뒤 운영팀이 다음을 요청한다.

1. 샘플 재고가 있으면 기존대로 신청서로 간다.
2. 재고가 없으면 같은 `무료 신청하기` 버튼에서 품절 안내를 보여야 한다.
3. 주소가 비어 있으면 제출하지 않고 오류 상태를 보여야 한다.
4. 신청 완료 화면에 `다른 제품 보기` 버튼을 추가해 상품 소개로 돌아가게 한다.
5. 품절 안내가 더는 필요 없을 때 삭제가 다른 화면/연결에 미치는 영향을 확인해야 한다.

### 시작 기대

이전에 만든 버튼을 고르면 `Default` 외에 조건별 분기를 더할 수 있고, Screen을 복제해 `신청서-주소 오류` State를 만든 뒤 Case의 Destination으로 연결할 것으로 기대한다. Flow에서 모든 분기를 비교하고, 필요 없어진 State를 지울 때 영향 관계를 안내받고 싶다.

### 수행 기록

#### 1. 기존 기획안 다시 찾기

1. 플러그인을 다시 열면 저장된 프로젝트가 로드되고 첫 Screen 또는 현재 Figma 선택에 맞는 Screen이 보인다.
2. `flow`에서 전체 연결을 훑고 `상품 소개` 버튼을 눌러 해당 프레임을 선택한다.
3. `build`로 돌아와 캔버스의 `무료 신청하기` 버튼을 선택한다.

- 멈칫: 프로젝트나 버전 이름이 없어 이 문서가 맞는지 확인할 단서가 Screen 이름뿐이다.
- 확신: 기존 흐름 찾기 4/5.
- 감정: 자동 저장·복원이 된 점은 안도감을 준다.

#### 2. 같은 버튼에 품절 Case 추가

1. 기존 `Default · prototype` 아래 `+ Add case`를 누른다.
2. `Case 2 · flow`가 생기고 When에 `샘플 재고가 없음`을 입력한다.
3. `What happens?`에서 `Stay on screen`을 선택한다.
4. `Outcome`에 `품절 안내를 표시하고 신청 버튼을 비활성화한다`고 입력한다.
5. Flow 탭에서 기본 이동과 품절 Case가 모두 나타나는 것을 확인한다. Spec에도 `When 샘플 재고가 없음…` 형태로 기록된다.

이해 근거: Default와 Case 2가 시각적으로 분리되고 Case에만 When이 있어 조건 분기 작성은 가능하다. `Case 2 · flow`라는 이름은 이 분기가 문서상의 흐름임을 암시한다.

- 멈칫: `Default · prototype`과 `Case 2 · flow`의 차이를 설명하는 문장이 없다. 초보는 둘 다 실제 프로토타입에서 조건에 따라 실행될 것으로 기대하기 쉽다.
- 선택지 고민: `Stay on screen`은 Destination이 없고 Outcome만 적게 한다. 실제 품절 UI를 표시하는지 단순 메모인지 눌러 보기 전에는 모른다.
- 잘못/되돌아감: 처음에는 `Open popup`이 품절 안내에 더 현실적이라 생각해 누른다. 즉시 두 번째 팝업 State가 생성되는 것을 보고, 조건 Case인데도 팝업이 자동 생성되어 놀란다. `Stay on screen`으로 바꿔도 이미 생성된 팝업 State 자체는 자동 삭제되지 않는다. States 셀렉트에서 해당 팝업을 골라 `State details` → Delete state로 별도 삭제한다.
- 확신: 문서상 예외 기록 4/5, 실제 조건 프로토타입 1/5.
- 감정: Flow에 분기가 보이는 점은 좋지만, “작동하는 프로토타입”이라 믿었다가 배신감을 느낀다.

구현상 판정: 추가 Case는 Project feature로 저장되어 Flow/Spec에는 보이지만, 한 버튼의 Figma `ON_CLICK` 반응은 첫 번째 feature, 즉 기본 Case만 동기화된다. 조건을 평가하는 런타임도 없다. 따라서 **재고 조건에 따라 실제로 갈라지는 프로토타입은 만들 수 없다.** Case 2의 `flow` 표기는 정확한 힌트이지만 설명 없이는 충분하지 않다.

#### 3. 주소 오류 State 만들기 시도

1. 신청서 Screen을 선택하고 `Screen details`를 펼친다.
2. `Duplicate screen`을 눌러 `신청서 copy`를 만든다.
3. 이름을 `신청서 - 주소 오류`로 바꾸고 오류 Text를 추가한다.
4. 이 복제본이 States 그룹이 아니라 Screens 그룹에 들어가는 것을 확인한다.
5. 원래 신청서의 `신청 내용 확인` 버튼에 `+ Add case`를 만들고 When `주소가 비어 있음`, `Go to screen` → Destination `신청서 - 주소 오류`를 고른다.

이해 근거: Duplicate는 기존 요소까지 복제하므로 오류 화면을 빠르게 만드는 현실적인 우회로다. 하지만 이것은 Base Screen과 연결된 State가 아니라 별도 일반 Screen이다.

- 멈칫: `State`를 직접 만드는 메뉴가 없다. 팝업 외 State를 만드는 것이 불가능한지, 숨겨진 방식이 있는지 판단하기 어렵다.
- 선택지 고민: 오류를 `Stay on screen` Outcome으로만 적을지, Screen 복제로 시각화할지 고민한다. 전자는 UI가 없고 후자는 Screen 수가 늘어난다.
- 잘못/되돌아감: Screens 셀렉트의 States 그룹을 열어 추가 항목이나 `+ State`가 있을 것으로 기대하지만 선택 목록일 뿐이다.
- 확신: 오류 화면 시각화 3/5, State 모델 이해 1/5.
- 감정: 화면 복제로 급한 회의 자료는 만들지만, 제품 모델과 맞는지 찜찜하다.

구현상 판정: 일반 오류/로딩 State를 생성하는 기능은 없다. Duplicate는 요소를 복제하지만 별도 일반 Screen을 만든다. Case 2를 그 Screen에 연결해 Flow/Spec에 기록할 수는 있어도 주소 조건에 따른 실제 프로토타입 분기는 실행되지 않는다. **요구는 문서상 부분 성공, 동작상 실패**다.

#### 4. 완료 화면의 되돌아가기 연결

1. `신청 완료` Screen에 Button을 추가하고 Name을 `다른 제품 보기`로 바꾼다.
2. Default에서 `Go to screen`을 선택하고 Destination으로 `상품 소개`를 고른다.
3. Flow에서 역방향 연결을 확인한다.

- 멈칫/오류: 특별한 문제 없음. 현재 Screen은 Destination에서 제외되지만 다른 Screen으로 돌아가는 연결은 가능하다.
- 확신: 5/5.
- 감정: 가장 단순하고 예측 가능한 작업이라 편안하다.

#### 5. 불필요한 팝업과 Screen 삭제 영향 확인

1. 잘못 만들어진 `상품 소개 · Popup 2` State를 선택하고 `State details`를 펼친다.
2. `Delete state`를 누른다. 확인 대화상자는 이름, incoming connection 수, 되돌릴 수 없음을 알려 준다. 연결이 남아 있다면 함께 제거된다는 것을 여기서 이해한다.
3. 원래 Screen인 `상품 소개` 삭제도 시험적으로 눌러 확인 문구만 본다. 파생 State 수와 incoming connection 수가 표시되는 것을 확인한 뒤 취소한다.
4. 요소 삭제 영향을 확인하려 품절 관련 버튼의 `Delete`를 누르려다가, 이 버튼에는 확인창이나 “연결 Case도 삭제됨” 안내가 없음을 보고 실제 삭제는 하지 않는다.
5. 품절 Case만 제거할 때는 `Remove case`를 누른다. 이 역시 확인 없이 즉시 삭제된다.

이해 근거: Screen/State 삭제는 파생 State와 들어오는 연결 개수를 사전에 알려 주는 점이 좋다. 반면 구체적으로 어떤 연결인지, 나가는 연결과 내부 요소가 어떻게 되는지는 보여 주지 않는다.

- 멈칫: `incoming connections`가 한국인 초보에게 “이 화면으로 들어오는 버튼 연결”임을 바로 설명하지 않는다. 숫자만 있고 출발 Screen/버튼 이름이 없다.
- 선택지 고민: State만 지울지, 연결 Case부터 지울지 안전한 순서를 알기 어렵다. Screen 삭제가 연결까지 정리한다는 문구로 State 삭제를 선택한다.
- 잘못/되돌아감: Case를 잘못 삭제해도 Undo/확인/복구가 없다. 구현상 즉시 feature와 Figma 반응 동기화가 실행된다.
- 확신: Screen 삭제 영향 4/5, 요소/Case 삭제 영향 1/5.
- 감정: 큰 단위 삭제는 비교적 안심되지만 작은 단위 삭제가 오히려 더 위험하게 느껴진다.

### 2차 결과

**부분 실패.** 기존 흐름 복원, 일반 Screen 복제, 추가 Case의 조건·Outcome 기록, 완료 화면의 역방향 연결, Flow/Spec 반영은 가능하다. 그러나 추가 Case는 실제 조건부 Figma 프로토타입이 아니며, Input 검증 동작과 일반 오류 State도 만들 수 없다. 급한 회의용 정적 기획 메모는 갱신할 수 있지만 “현실적인 예외 흐름이 작동하는 기획안”은 구현상 완성할 수 없다.

## 잘된 점

1. 빈 프로젝트에서 `+ Screen` 한 번으로 설정된 모바일 프레임을 만들고 캔버스까지 포커스해 시작 장벽이 낮다.
2. Text, Button, Input, Image, Divider, Section의 클릭형 카드와 미리보기는 초보가 타이핑 없이 와이어프레임을 빠르게 만든다.
3. `What happens?`와 `Go to screen / Open popup / Stay on screen`은 내부 용어 대신 사용자 결과를 묻는다. Destination도 필요한 경우에만 나타난다.
4. 팝업 생성 시 dim, 팝업 컨테이너, 기본 Text를 자동 구성하고 `Edit popup`으로 곧장 이동할 수 있어 반복 작업이 적다.
5. 팝업 내부에서는 선택지가 `Close popup`으로 문맥에 맞게 바뀐다.
6. Flow는 미연결 Destination을 `not linked`로 드러내며, Spec은 Purpose·요소 순서·행동을 자동 정리한다.
7. Screen 삭제 확인에는 파생 State와 들어오는 연결의 개수, 되돌릴 수 없다는 경고가 포함된다.
8. 컨트롤에 `aria-pressed`, label, focus-visible 스타일이 있어 키보드 및 보조기술의 기본 단서를 고려했다.

## 문제와 심각도

### 치명적

1. **Case flow와 실제 prototype의 의미 불일치가 설명되지 않는다.** 추가 Case는 조건과 액션을 저장하고 Flow/Spec에 표시하지만 실제 Figma 클릭 반응은 기본 Case 하나뿐이다. 초보가 “조건 분기를 구현했다”고 잘못 전달할 위험이 매우 크다.
2. **입력 검증과 일반 UI State를 표현할 핵심 경로가 없다.** Input에는 이름 외 설정이 없고, 일반 State 생성 기능도 없다. 제품 흐름의 가장 흔한 오류·빈 값·로딩 예외를 완성할 수 없다.

### 높음

1. **`Open popup` 선택이 곧 새 State 생성이라는 사실이 사전에 드러나지 않는다.** segmented selector 탐색만으로 캔버스와 프로젝트 구조가 변경되며 전용 Undo가 없다.
2. **저장 피드백이 없다.** Name, Purpose, When, Outcome은 포커스를 잃을 때 저장되지만 저장됨/저장 중 상태가 없다. 탭 전환이나 플러그인 종료 전에 불안하다.
3. **요소와 Case 삭제가 확인 없이 즉시 실행된다.** Section 삭제 시 자식 요소, Button 삭제 시 연결된 Case가 함께 사라지지만 사전 영향 안내가 없다.
4. **Spec에서 Screen 전환과 전체 산출물 확인이 어렵다.** 현재 Figma 선택에 종속되고 전체 Spec/복사/내보내기가 없어 전달물 완결성이 낮다.

### 중간

1. Screen/State, Default prototype/Case flow, Stay on screen의 의미를 알려 주는 짧은 설명이 없다.
2. Flow의 선택 Screen 구간과 Project flow가 중복되어 연결 중복으로 오해할 수 있다.
3. Section이 컨테이너라는 의미가 추가 카드만으로 약하고, 들어가면 작업 문맥이 크게 바뀐다.
4. Screen 삭제 경고의 `derived states`, `incoming connections`는 개수만 보여 주며 실제 이름과 영향 방향을 설명하지 않는다.
5. Flow와 Spec은 보기 탭인데 편집 가능 여부나 다음 행동이 안내되지 않는다.
6. 설정 버튼이 아이콘만 표시되고, 구현 문자열 일부에는 `쨌`, `??`, `횞`처럼 깨진 문자가 보여 실제 빌드에서도 노출된다면 라벨 이해와 신뢰를 훼손할 수 있다. 실제 렌더링 확인이 필요하다.

### 낮음

1. 영문 UI만 제공되어 한국인 초보에게 Purpose, Outcome, Destination 같은 추상 명사의 부담이 있다.
2. Screen 이름 기본값은 빠르지만 생성 전에 이름을 정할 수 없어 나중에 details를 펼쳐 수정해야 한다.
3. 스타일 선택이 Filled/Outline으로 단순한 것은 좋지만 실제 차이를 작은 select 텍스트로만 비교한다.

## 가장 어려웠던 선택지 목록

1. `Default · prototype`과 `Case 2 · flow`: 둘 다 버튼 행동처럼 보이는데 실제 실행 범위가 다르다.
2. `Open popup`: 기존 팝업 선택인지 새 팝업 생성인지 누르기 전에 알 수 없다.
3. `Stay on screen`: 실제 화면 변화인지 기획 설명만 남기는지 불명확하다.
4. Screen과 State: Popup은 State이지만 오류 State는 추가할 수 없어 개념 경계가 일관되지 않다.
5. Section: 레이아웃 컨테이너인지 화면 구획용 시각 요소인지 카드에서 알기 어렵다.
6. Flow와 Spec: 작업을 편집하는 곳인지 결과를 검토하는 곳인지, 어디까지 “완성”인지 판단하기 어렵다.
7. State 삭제와 Case 삭제 순서: 어느 쪽이 안전하고 무엇이 연쇄 삭제되는지 작은 단위에서는 안내가 없다.

## 우선순위 개선안

### P0 — 잘못된 성공 인식 방지

1. Case 제목 바로 아래에 고정 설명을 둔다: `Default는 Figma에서 클릭 가능 · 추가 Case는 기획 문서에만 표시`. Flow와 Spec에서도 `문서용 분기` 배지를 반복한다.
2. 추가 Case를 실제 조건부 프로토타입으로 지원하지 않을 것이라면 `Case` 대신 `예외 메모 추가`처럼 기능 한계를 드러내는 결과형 이름을 쓴다.
3. Input에 최소한 `필수 여부`와 `검증/오류 Outcome`을 제공하거나, 지원 전까지는 Input details에서 “현재 입력 동작은 문서화되지 않음”을 명시한다.

### P1 — 파괴적·숨은 동작을 예측 가능하게

1. `Open popup` 선택 후 바로 만들지 말고 `새 팝업 만들기`와 기존 팝업 Destination을 명시적으로 고르게 한다. 생성 후에는 `Popup 1 created · Undo` 피드백을 준다.
2. 요소/Section/Case 삭제 전에 구체적 영향을 표시한다. 예: `이 Section과 내부 요소 4개, 버튼 연결 1개가 삭제됩니다`.
3. 모든 blur 저장 필드에 `Saved` 상태를 짧게 표시하고, 저장되지 않은 입력이 있는 상태에서 탭 이동/종료를 안전하게 처리한다.

### P2 — 초보의 작업 문맥 유지

1. Screen 셀렉트를 Build뿐 아니라 Flow와 Spec에서도 제공하고, Spec에는 `전체 화면 보기/복사`를 추가한다.
2. 첫 사용 빈 상태에 세 문장만 제공한다: `Screen을 만드세요 → 요소를 추가하세요 → Button에서 행동을 연결하세요`.
3. State를 Popup 전용으로 유지한다면 UI에서 `Popup states`라고 부른다. 일반 State를 도입한다면 `+ State`와 Base Screen 관계를 명시한다.
4. Flow의 중복 구간은 탭이나 토글로 `선택한 Screen / 전체 프로젝트` 중 하나씩 보이게 한다.

### P3 — 용어와 비교 부담 줄이기

1. 추상 명사에 짧은 예시를 붙인다: Destination `어디로 이동하나요?`, Outcome `화면에 남는 결과`, Purpose `사용자가 여기서 하는 일`.
2. Section 카드에 `요소를 묶고 배치` 설명을 추가한다.
3. Screen 삭제 영향에는 출발 Screen과 버튼 이름을 최대 몇 개까지 직접 나열한다.
4. 실제 플러그인 빌드에서 깨진 구분 문자·아이콘·곱셈 기호가 보이는지 확인하고 정상 문자 또는 접근 가능한 텍스트로 교체한다.

## 최종 판단

Sketchy는 초보가 클릭만으로 저충실도 Screen과 기본 이동·팝업 흐름을 빠르게 만드는 데 강하다. 특히 결과형 액션 선택과 팝업 자동 구성은 첫 성공을 앞당긴다. 반면 현재 제품은 **작동하는 기본 prototype**과 **문서에만 남는 Case flow**를 한 편집기 안에서 매우 비슷하게 보여 준다. 이 경계를 설명하지 않으면 초보 기획자가 구현되지 않은 예외 흐름을 완료했다고 믿게 된다. 우선적으로 기능을 더 늘리기보다 이 한계를 명확히 표시하고, 숨은 생성·연쇄 삭제·blur 저장에 예측 가능성과 복구 수단을 제공해야 한다.
