# 초보·중수 독립 UX 검증 종합

## 검증 성격

이 문서는 실제 사용자를 관찰한 정량 사용성 테스트가 아니라, 서로 독립적인 두 페르소나가 현재 구현을 근거로 수행한 **인지적 워크스루의 교차 분석**이다. 소요 시간이나 발생률은 측정값이 아니며, 아래 판단은 두 검증에서 반복된 행동·오해·복구 경로를 근거로 한다.

## 결론

Sketchy는 화면을 만들고 정상적인 화면 전환을 연결하는 첫 흐름은 빠르다. 그러나 사용자가 탐색적으로 선택해 보는 순간 실제 구조가 바뀌는 액션, 문서로만 남는 Case와 실제 Prototype의 차이, Popup을 State라고 부르는 모델 때문에 2차 수정에서 신뢰가 크게 떨어진다.

핵심 문제는 설명 문구가 부족해서라기보다 **선택지의 이름과 동작 결과가 일치하지 않는 것**이다. 긴 안내를 더하기보다 클릭 전 결과를 예측할 수 있게 만들고, 실제로 동작하지 않는 범위를 선택 UI 자체에서 구분해야 한다.

## 공통 멈칫 지점

1. `Open popup`은 액션 선택처럼 보이지만, 클릭 즉시 Popup State 생성과 기존 액션 교체까지 수행한다. 두 사용자 모두 결과를 누르기 전에 예측하지 못했다.
2. `Default · prototype`과 `Case · flow`가 실제 실행 범위를 충분히 전달하지 못한다. 추가 Case도 조건에 따라 재생되는 Prototype이라고 오인할 수 있다.
3. `State`는 일반적인 오류·로딩 상태로 이해되지만 실제 생성 가능한 State는 Popup 중심이다. 오류 상태를 만들려다 별도 Screen 복제로 우회했다.
4. `Stay on screen`은 실제 화면 변화인지, 문서용 Outcome인지 선택지만 보고 판단하기 어렵다.
5. 이름, Purpose, When, Outcome이 포커스를 벗어날 때 저장되지만 저장 완료 표시가 없어 다른 곳을 눌러 확인한다.
6. Popup 편집 뒤 `Back`이 원본 Screen이 아니라 Popup State 문맥으로 돌아가 위치 감각을 잃는다.
7. Flow의 현재 화면 목록과 Project flow에 같은 연결이 반복되어 중복 연결로 오해한다.
8. Section·요소·Case 삭제는 연쇄 영향을 설명하지 않고 즉시 실행된다. Screen 삭제만 보호되는 규칙이 일관되지 않다.

## 숙련도별 차이

### 초보에서 더 크게 드러난 문제

- 빈 Screen 선택 목록을 먼저 누르고, Section을 화면의 구역 제목으로 오해하는 등 조작 모델을 찾는 비용이 컸다.
- `prototype`, `Destination`, `State`, `incoming connections` 같은 용어를 제품 안의 단서만으로 해석하기 어려웠다.
- Spec에서 다른 Screen을 보고 싶을 때 Build로 돌아가 선택한 뒤 다시 Spec으로 오는 우회 경로를 사용했다.
- Popup을 보기 위해 `Open popup`을 시험 클릭했다가 구조가 생성되어 탐색 자체를 위험하게 느꼈다.

### 중수에서 더 선명하게 드러난 문제

- Screen과 Destination은 기존 Figma 경험으로 이해했지만, 그 경험 때문에 Case를 실제 조건부 Prototype으로 더 쉽게 오인했다.
- Popup 자동 생성, 추가 Case의 문서 전용 성격처럼 Sketchy 고유 규칙은 Figma 숙련도로 보완되지 않았다.
- Section 안 요소 재진입, Popup 편집 문맥, Flow/Spec의 전달 형태에서 반복 작업과 정보 구조의 비효율을 더 민감하게 발견했다.
- 제품이 명확해서 성공한 부분과 Figma 경험으로 추론해 성공한 부분이 달랐다. 현재 UX는 중수에게 쉬운 것이 아니라, 일부 비용을 기존 지식에 전가한다.

## 가장 어려웠던 선택

| 선택 | 사용자가 알기 어려웠던 것 | 실제 결과 |
|---|---|---|
| Go to screen / Open popup / Stay on screen | 동작 종류만 고르는지 구조도 생성하는지 | Popup은 구조를 즉시 생성, Stay는 주로 설명 기록 |
| Default / Case | 둘 다 Prototype에서 실행되는지 | 첫 Case만 실제 Figma reaction에 반영 |
| Screen / State | 오류·로딩도 State로 만들 수 있는지 | 현재 State 생성은 Popup 중심 |
| 새 Screen / Duplicate | 상태 표현에 어느 쪽이 맞는지 | Duplicate는 별도 일반 Screen 생성 |
| Delete / Remove case | 현재 항목만 없어지는지 연결까지 없어지는지 | 소유 요소와 Feature가 연쇄 삭제될 수 있음 |

## 잘 전달되는 부분

- 빈 상태의 `+ Screen`은 시작점이 명확하다.
- 화면과 블록 생성 결과가 캔버스에 즉시 나타나 정상 흐름의 뼈대를 빠르게 만들 수 있다.
- `Go to screen`을 고른 뒤 Destination이 나타나는 단계적 구조는 이해하기 쉽다.
- Popup 안에서는 `Open popup`을 제거하고 `Close popup`을 제공하며 Destination 후보를 제한한 점이 안전하다.
- 화면 이름을 바꿔도 ID 기반 연결이 유지된다.
- Screen 삭제는 파생 State와 들어오는 연결 수를 미리 알려 준다.

## 우선순위

### P0 — 결과를 잘못 믿게 만드는 문제

1. 추가 Case가 실제 조건부 Prototype처럼 보이는 문제를 해결한다. 가장 좋은 방향은 문서 전용 Case를 별도 실행 선택지처럼 꾸미지 않고, `Additional flow`처럼 명확히 분리하는 것이다. 실제 재생되지 않는 사실은 짧고 상시 보이는 상태로 표현한다.
2. `Open popup`의 숨은 생성 동작을 없앤다. Popup이 없으면 `Create popup`, 있으면 `Open popup`으로 행동 이름을 나누거나, 선택 뒤 생성 여부를 고르게 한다.
3. Section·요소·Case 연쇄 삭제에 영향 요약과 확인 또는 즉시 Undo를 제공한다.

### P1 — 흐름을 멈추게 하는 문제

1. 현재 구현 범위에 맞춰 `States`를 `Popups`로 구체화하고 원본 Screen 관계를 표시한다. 일반 상태 기능을 제공하기 전까지 포괄적인 State 모델을 약속하지 않는다.
2. Popup 편집 헤더와 Back의 목적지를 원본 Screen/source 버튼 기준으로 명확히 한다.
3. 선택형 액션을 시험해도 기존 Destination이 즉시 유실되지 않게 초안 선택 또는 Undo를 제공한다.
4. 입력 저장 상태를 작게 표시한다.

### P2 — 반복 비용과 전달성

1. 새 블록을 추가하면 그 블록을 즉시 편집 대상으로 선택한다.
2. Flow의 현재 화면/전체 목록 중복을 한 목록의 필터 또는 강조로 정리한다.
3. 화면별 Spec을 이동 없이 전환하고, 전체 프로젝트 Spec을 한 번에 복사하는 최소 경로를 제공한다.

## 철학 기준 판단

기능 설명을 더 붙이는 것만으로 해결하면 다시 UI가 무거워진다. 이번 검증이 가리키는 방향은 다음 세 가지다.

- 선택지 이름은 클릭 결과와 같아야 한다.
- 실제 동작과 문서용 명세는 같은 강도의 UI로 보이면 안 된다.
- 사용자가 시험해 보는 클릭은 되돌릴 수 있거나 구조를 몰래 바꾸지 않아야 한다.

따라서 우선순위는 일반 State 시스템이나 복잡한 조건 엔진을 새로 만드는 것이 아니다. 먼저 현재 제공하는 Popup과 문서용 Case의 정체를 솔직하고 예측 가능하게 만드는 것이 가장 작은 유효 수정이다.
