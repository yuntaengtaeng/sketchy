# Sketchy 중수 사용자 독립 UX 검증

## 평가 전제와 사용자 설정

- 사용자: **박서윤(32세)**, 교육 스타트업 서비스 기획자 4년 차. Figma로 모바일 와이어프레임과 화면 전환 Prototype을 만들 수 있고, 소규모 기능 기획을 세 차례 주도했다. 컴포넌트·오토레이아웃은 필요한 만큼만 쓴다.
- 업무 맥락: 목요일 오후, 다음 날 오전 개발 리뷰에 올릴 **모바일 강의 찜/신청 흐름**의 초안을 만들어야 한다. 1차에는 45분 안에 정상 흐름을 만들고, 2차에는 일주일 뒤 들어온 품절·확인 팝업 요구를 반영한다.
- 습관: 먼저 화면을 빠르게 복제한 뒤 이름을 고치고, 버튼을 연결하고, 마지막에 Flow를 훑는다. 긴 도움말은 잘 읽지 않고 눈앞의 컨트롤 명칭과 Figma 관례로 판단한다. 변경 직후 캔버스와 Prototype 연결을 확인하는 편이다.
- 방법: 실행 화면을 실제로 조작하거나 실제 시간을 측정한 사용성 테스트가 아니다. `manifest/package` 및 `src/ui`, `src/plugin`, `src/shared` 구현을 최소 범위로 읽고, 빈 프로젝트에서 처음 쓰는 상황을 재구성한 **구현 기반 인지적 워크스루**다. 따라서 시각적 체감, 렌더링 오류, 클릭 속도는 확정할 수 없다. 구현상 제공되지 않는 동작은 성공으로 간주하지 않았다.

## 1차 회차 — 정상 신청 흐름 만들기

### 목표

`강의 목록 → 강의 상세 → 신청 완료` 3개 화면을 만들고, 목록의 카드 버튼과 상세의 신청 버튼을 Prototype으로 연결한다. 상세에는 제목, 이미지, 설명, 신청 버튼이 있어야 하며 개발자에게 화면 목적과 행동을 설명할 수 있는 기획안으로 마무리한다.

### 시작 기대

처음에는 Build에서 화면을 만들고 요소를 추가한 뒤 버튼을 선택하면 Figma Prototype과 비슷한 `On click → Navigate to`를 지정할 수 있을 것이라 기대했다. Flow는 전체 연결도, Spec은 선택 화면의 전달용 명세로 예상했다. 이 기대는 탭 이름과 기존 Figma 경험을 함께 사용한 추론이며, 제품 내 온보딩으로 형성된 것은 아니다.

### 구체적 수행 순서와 인지

1. 플러그인을 열면 `Build / Flow / Spec`과 설정 아이콘, `Screens`, `+ Screen`을 본다. 빈 상태에서 다음 행동은 사실상 `+ Screen`뿐이라 바로 누른다.
   - 결과: 모바일 기본 크기의 `Screen 1` 프레임이 생성되고 선택된다.
   - 이해 근거: `+ Screen`은 제품 문구가 명확했다.
   - 확신/감정: 95%, 안도. 첫 진입은 막히지 않는다.

2. `Screen details`를 펼쳐 이름을 `강의 목록`, Purpose를 `신청 가능한 강의를 탐색한다`로 입력하고 다른 곳을 클릭해 blur 저장을 유도한다.
   - 멈칫: 저장 버튼도 저장 완료 표시도 없다. Figma 속성 패널처럼 자동 저장일 것이라고 **기존 경험으로 보완**했다. 입력 도중 탭을 바꾸면 저장되는지도 확신하기 어렵다.
   - 확신/감정: 70%, 약간 불안.

3. `Add something`에서 Text, Section, Button 중 구조를 고민한다. 카드 묶음을 만들기 위해 Section을 선택한다.
   - 결과: 캔버스에 Section이 생기고 선택되면서 플러그인 상단이 `Section`, 본문이 `Add to section / Nodes`로 바뀐다.
   - 멈칫: 화면 편집기 안으로 들어간 것인지, 캔버스의 Figma 레이어를 선택했기 때문에 문맥이 바뀐 것인지 설명이 없다. `Back`으로 화면으로 돌아갈 수 있다고 추론한다.
   - 선택 비교: 바로 Text/Image/Button을 화면에 각각 추가할지 Section 안에 넣을지 고민했다. Section의 이점은 `New elements are added inside this section`에서 뒤늦게 이해했다.
   - 확신/감정: 75%, 구조가 단순해지는 점은 좋지만 예상보다 문맥 이동이 크다.

4. Section 안에 Image, Text, Button을 차례로 누르고 Nodes에서 각 항목을 선택해 이름을 `강의 썸네일`, `실무 UX 기초`, `상세 보기`로 바꾼다. Button Style은 Filled를 유지한다.
   - 잘못 누름/복구: Text 추가 직후 새 요소가 아니라 Section이 계속 선택되는 동작 때문에, 곧바로 상세 입력이 나타날 것으로 기대했다가 Nodes 목록에서 Text를 다시 눌렀다. 기능상 복구 가능하지만 한 단계가 숨어 있다.
   - 확신/감정: 80%, 반복 후 규칙을 학습함.

5. `Back`을 눌러 화면 수준으로 돌아가 `Duplicate screen`을 두 번 눌러 3개 화면을 만든다. 화면 선택 Select로 각 copy를 골라 `강의 상세`, `신청 완료`로 이름과 Purpose를 변경한다. 필요 없는 복제 요소는 각자 선택 후 Delete한다.
   - 선택 비교: `+ Screen`으로 빈 화면을 만들지 Duplicate로 구조를 재사용할지 고민했으나, 내 작업 습관상 복제를 택했다.
   - 멈칫: 화면 Select의 `Screens`와 `States` 구분에서 State가 UI 상태인지, variant인지, 팝업인지 알 수 없다. 아직 State가 없어서 실제 의미를 확인할 수도 없다. 여기서는 기존 Figma의 화면/상태 개념을 임시로 대입했다.
   - 실패 위험: 요소 Delete에는 확인창이나 연결 영향 안내가 없다. 이 시점엔 연결 전이라 괜찮지만 앞으로는 위험해 보인다.

6. `강의 상세`을 선택해 Text, Image, Text, Button을 추가하고 각각 이름을 `실무 UX 기초`, `강의 이미지`, `초급자를 위한 4주 과정`, `신청하기`로 바꾼다. `신청 완료`에는 Text와 Button을 추가해 `신청이 완료되었습니다`, `목록으로`로 바꾼다.
   - 확신/감정: 85%, 블록 추가와 이름 변경은 단순하고 캔버스에 즉시 결과가 생겨 만족.

7. `강의 목록`으로 돌아와 Section → Nodes → `상세 보기` 버튼을 선택한다. `button details` 아래 `Default · prototype`에서 `Go to screen`을 누른다.
   - 멈칫: `Default · prototype`이 “기본 케이스는 실제 Prototype에 연결된다”는 의미인지, 기본 스타일/기본 상태인지 설명이 없다. `Case · flow`와 대비되는 의미는 아직 보이지 않는다.
   - Segmented selector 판단: `Go to screen / Open popup / Stay on screen`이 붙어 있고 선택 배경이 생겨 단일 선택임은 시각적으로 추론 가능하다. 하지만 Radio나 Select보다 선택 후 즉시 저장·부작용이 있다는 사실은 알 수 없다. 제품 표현 60%, 기존 segmented control 경험 40%로 이해했다.
   - 선택 비교: `Go to screen`과 `Stay on screen` 중 전자는 명확하다. `Open popup`은 팝업을 먼저 만들어 두어야 하는지 알 수 없어 피한다.

8. `Destination` Select가 나타나 `강의 상세`을 선택한다.
   - 이해: Destination은 도착 화면이라는 뜻을 기존 Figma Prototype 용어로 즉시 이해했다. 한국어 기획 중수지만 영어 자체는 장애가 작다.
   - 멈칫: 액션을 누른 순간 목적지 없는 Feature가 먼저 저장되고 Flow에 `not linked` 상태가 생긴다는 점은 UI만 보고 예상하기 어렵다. 목적지 선택 후 완성되는 것으로 받아들였다.
   - 확신/감정: 선택 후 90%, 연결 완료 피드백은 캔버스 화살표를 보고 확인할 것으로 기대.

9. 같은 방식으로 `강의 상세`의 `신청하기 → 강의 완료`, `신청 완료`의 `목록으로 → 강의 목록`을 연결한다. 실수로 `Stay on screen`을 한 번 눌렀다가 Outcome 입력란이 나타나는 것을 보고 다시 `Go to screen`과 Destination을 선택한다.
   - 복구: 되돌리기 버튼은 없지만 selector 재선택으로 복구된다. 다만 `Stay on screen`을 누르는 즉시 기존 Destination 정보가 사라지므로 시험 클릭 비용이 크다.
   - 확신/감정: 85%, 복구는 됐지만 즉시 저장되는 선택기에 더 조심스러워짐.

10. Flow 탭을 눌러 선택 화면 관련 흐름과 `Project flow`를 본다. source 버튼과 destination 버튼을 누르면 해당 프레임으로 이동한다.
    - 이해: Flow는 편집보다는 검토·탐색 뷰다. 연결선과 목록이 함께 만들어지는 점은 유용하다.
    - 멈칫: `Flow for …`와 `Project flow`에 같은 연결이 중복 표시되어 처음엔 중복 Feature를 만든 줄 알았다. 구역 제목을 다시 읽고 현재 화면 필터 + 전체 목록임을 이해했다.
    - 확신/감정: 80%, 전체 누락 확인에는 좋으나 중복 인지가 거슬림.

11. Spec 탭에서 각 화면을 선택하며 Purpose, top-to-bottom 요소, 사용자 행동을 확인한다.
    - 이해: Spec은 읽기 전용이며 선택된 한 화면만 기술한다. Flow와 Spec의 역할 차이는 결과를 보고 이해했다.
    - 멈칫: Spec 자체를 복사·내보내거나 전체 화면 기획안으로 묶는 기능은 없다. 개발 전달용 “완성”은 Figma 파일을 공유하고 상대가 플러그인을 열어보는 수준이다.

### 1차 결과

- **부분 성공**: 3개 화면, 블록, Purpose, 3개의 정상 화면 전환, 캔버스 연결선, 화면별 Spec을 만들 수 있다. 실제 Figma ON_CLICK Prototype 연결도 첫 케이스 기준으로 생성된다.
- **완전한 기획안 완성에는 미달**: 전체 Spec 내보내기/복사, 주석형 요구사항, 입력 검증 같은 비클릭 행동은 제한적이다. 이름·Purpose 저장 완료 피드백도 없다.
- 최종 확신: **82%**. “Prototype이 동작한다”는 확신은 구현상 높지만, 전달받는 사람이 Flow/Spec을 어떻게 소비할지는 낮다.
- 최종 감정: 빠르게 뼈대를 만든 만족감과, 용어/자동 저장/선택 즉시 반영에 대한 약한 불안이 공존한다.

## 2차 회차 — 확인 팝업과 품절 예외 흐름 반영

### 추가 요구

일주일 뒤 다음 변경을 받았다.

1. `신청하기`를 누르면 바로 완료 화면으로 가지 말고 확인 팝업을 연다.
2. 팝업에서 `신청 확정`은 완료 화면으로, `취소`는 팝업 닫기로 동작한다.
3. 좌석이 없을 때는 같은 `신청하기`에서 이동하지 않고 `마감되어 신청할 수 없음`을 보여주는 예외 Case를 기획안에 남긴다.
4. 기존 완료 화면은 유지하되 이름을 `신청 결과`로 바꾼다.

### 시작 기대

기존 상세 화면의 신청 버튼에서 `Open popup`을 선택하고 Destination을 새 팝업으로 지정할 것으로 예상했다. 예외 Case는 조건을 입력하면 Figma Prototype에도 조건 분기가 생길 수 있기를 기대했지만, 일반 Figma Prototype에 조건 설정이 복잡하다는 경험 때문에 반신반의했다.

### 구체적 수행 순서와 인지

1. 화면 Select에서 `강의 상세`을 찾고 Section/Nodes를 거쳐 `신청하기`를 선택한다. 기존 `Default · prototype`의 `Go to screen`이 선택되어 있고 Destination이 `신청 완료`인 것을 확인한다.
   - 멈칫: 일주일 뒤에는 Section 안 버튼을 찾기 위해 `Section → Nodes → Button`의 문맥 이동을 기억해야 한다. 캔버스에서 직접 버튼을 선택하면 상세가 열리는 것은 기존 Figma 선택 경험으로 추론 가능하지만 제품 내 안내는 없다.
   - 확신/감정: 75%, 재진입 비용이 있음.

2. `Open popup`을 누른다.
   - 예상과 다른 결과: 기존 팝업 Destination 목록이 비어 있는 상태에서, 선택 즉시 `강의 상세 · Popup 1`이라는 파생 화면과 dim, Popup Section, 기본 Text가 자동 생성되고 연결된다.
   - 놀람: “Open popup”을 단순 액션 종류 선택으로 이해했는데 실제로는 **새 팝업 생성까지 수행**한다. 클릭 전에 결과 설명이나 `Create popup` 명칭이 없어 부작용을 예측할 수 없다.
   - Screen/State 이해: 화면 Select에 새 항목이 `States` 아래 나타나며 kind는 popup이다. 제품은 State라고 부르지만 실질적으로는 기본 화면을 복제한 팝업 전용 파생 프레임이다. UI 상태 일반을 뜻한다고 오해할 가능성이 높다. 이것은 구현을 보고 알았으며 UI만으로는 명확하지 않다.
   - 확신/감정: 55%, 편리하지만 통제권을 뺏긴 느낌.

3. Destination에는 방금 생성된 Popup 1이 자동 지정되고 `Edit popup` 버튼이 나타난다. 이를 누른다.
   - 이해: 버튼 이름이 결과 중심이라 명확하다. 누르면 팝업 Section을 선택하고 `Section` 편집 화면으로 들어간다.
   - 멈칫: `Edit popup`이 별도 모달 편집기를 열지, 캔버스의 파생 State로 이동할지 알 수 없다. 실제로는 후자다. 헤더에는 단지 `Section`이라고만 표시되어 팝업 편집 중이라는 문맥이 약하다.
   - 확신/감정: 70%, 목적은 달성하지만 위치 감각이 흐려짐.

4. 기본 `Popup` Text를 Nodes에서 선택해 `이 강의를 신청할까요?`로 변경한다. 팝업 Section에 Button 두 개를 추가하고 `신청 확정`, `취소`로 이름을 바꾼다.
   - 잘못 누름/복구: 첫 Button 추가 후 Section이 선택된 채라 바로 이름을 못 바꾸고 Nodes에서 Button을 골랐다. 두 번째 Button을 추가한 뒤 동명이 두 개가 잠시 생겨 어느 것이 새 버튼인지 순서로 판단했다.
   - 확신/감정: 75%, 가능하지만 반복 동작이 많다.

5. `신청 확정` 버튼에서 `Go to screen`을 고르고 Destination `신청 완료`를 선택한다. 팝업 내부 선택지는 `Go to screen / Close popup / Stay on screen`으로 바뀌어 `Open popup`이 없다.
   - 이해: 팝업 안에서 중첩 팝업을 막는다는 제약은 합리적이다. 다만 왜 선택지가 달라졌는지 설명은 없고 문맥을 보고 추론했다.
   - Destination 선택: 목록에는 일반 Screens만 나와 팝업 자체를 잘못 고를 수 없어서 안전하다.
   - 확신/감정: 90%, 가드레일이 좋다.

6. `취소` 버튼에서 `Close popup`을 선택한다. `Also happens`에 `입력값 변경 없음`을 적는다.
   - 이해: Close popup은 Destination 없이 완료되므로 간단하다. `Also happens`는 부수 효과 설명란으로 이해된다.
   - 멈칫: textarea가 blur에 저장되며 저장 표시가 없어 또 다른 컨트롤을 눌러 저장을 유도한다.

7. `Back`을 눌러 돌아간다.
   - 예상 오류: Back이 기존 `강의 상세` 화면 수준으로 돌아갈 것으로 기대하지만, 구현상 Section 문맥의 Back은 현재 선택된 popup State 자체를 선택한다. 결과적으로 Build는 `State details`와 팝업 State 전체 블록 화면을 보여준다. 다시 화면 Select에서 `강의 상세`을 골라야 한다.
   - 감정: 짜증. “팝업 편집 종료”와 “파생 State 선택”이 같은 뒤로가기로 이어져 정보 구조가 예상과 다르다.

8. `신청하기`로 돌아가 `+ Add case`를 누른다.
   - 결과: 새 `Case 2 · flow`가 즉시 `Stay on screen` action으로 생성된다. `When`에 `잔여 좌석이 0일 때`, Outcome에 `마감되어 신청할 수 없음 메시지를 보여준다`를 입력한다.
   - Default prototype/Case flow 이해: 이제야 기본 케이스는 실제 Prototype, 추가 Case는 Flow 문서용이라는 의미를 대비해 추론한다. 그러나 legend만으로는 실제 동작 범위를 충분히 설명하지 않는다.
   - 심각한 기대 불일치: 추가 Case도 캔버스 연결선/Flow에는 나타나지만 Figma 버튼의 실제 클릭 반응은 **첫 Feature 하나만** 사용된다. 조건 입력은 실행 조건이 아니라 문서 문자열이다. 제품에서 `flow`라고 표시했으나 “Prototype에서 실행되지 않음”을 직접 말하지 않아 테스트 전에는 성공으로 오인할 수 있다.
   - 확신/감정: 문서화 성공 85%, 인터랙션 구현 20%, 실망.

9. 실수로 `+ Add case`를 한 번 더 눌러 `Case 3 · flow`를 만든다. 즉시 `Remove case`로 삭제한다.
   - 복구: 개별 삭제는 쉽고 명칭도 명확하다. 확인창이 없어 오클릭에는 취약하지만 방금 만든 빈 Case라 부담은 작다.
   - 삭제 영향: Case 삭제는 해당 Feature와 소유한 Prototype reaction 재계산까지 수행하지만 UI는 영향 범위를 말하지 않는다. 기본 Case를 삭제할 때 실제 Prototype 연결이 사라지거나 다음 Case가 primary가 될 수 있다는 점도 예고되지 않는다.

10. 화면 Select에서 `신청 완료`를 고르고 `Screen details`에서 이름을 `신청 결과`로 변경한다.
    - 결과: 연결의 destination id는 유지되고 Flow 표시 이름도 갱신된다. 이 점은 안정적이다.

11. Flow를 확인한다.
    - 정상 흐름: 상세 → Popup 1, Popup 1의 확정 → 신청 결과, 취소 → Close popup이 보인다.
    - 예외 흐름: 상세의 같은 신청 버튼이 `마감되어 신청할 수 없음`이라는 비인터랙티브 결과로 추가 표시된다.
    - 멈칫: 같은 source/버튼에서 Default와 Case가 평면적으로 나열되고 우선순위/조건 실행 여부를 명확히 시각화하지 않는다. 조건 문자열은 보이지만 “문서 전용”임을 재확인할 표식이 없다.

12. Spec에서 강의 상세과 팝업 State를 각각 본다.
    - 결과: 화면별 요소와 행동은 읽을 수 있다. 팝업 State는 원본 화면을 복제한 요소까지 포함하므로 Spec에 배경 화면 요소가 함께 나타나 팝업 자체 범위를 빠르게 구분하기 어렵다.
    - 최종 한계: 단일 종합 기획서나 내보내기는 없고, 예외 조건을 실제 Prototype으로 재생할 수도 없다. 따라서 “추가 요구를 기획안에 기록”하는 것은 성공하지만 “현실적인 예외 흐름을 동작하게 반영”하는 것은 실패다.

### 삭제 영향 별도 검증

- 일반 Screen 삭제: `Screen details`의 삭제 확인문에 파생 State 수와 incoming connection 수, 되돌릴 수 없다는 문구가 나온다. 사용자가 영향 범위를 보고 중단할 수 있어 좋다.
- popup State 삭제: 해당 State와 이를 향하는 연결이 제거된다고 추론할 수 있으나, 확인문에 incoming connection 수는 표시된다. 다만 원본 화면과의 관계를 일상어로 설명하지 않는다.
- Section/버튼 등 요소 삭제: 확인 없이 즉시 요소, 하위 요소, 관련 Feature가 함께 삭제된다. 특히 Section 삭제는 내부 버튼과 Prototype/Case까지 연쇄 삭제되지만 영향 안내가 없다. 가장 위험한 삭제 비대칭이다.
- Case 삭제: 확인 없이 즉시 삭제되며 실제 Figma reaction에도 영향을 줄 수 있다. Default와 flow-only Case의 영향 차이를 안내하지 않는다.

### 2차 결과

- **부분 성공**: 확인 팝업 자동 생성, 팝업 내용 편집, 확정/취소 Prototype, 예외 Case 문서화, 기존 destination 화면 이름 변경은 가능하다.
- **실패**: 조건 Case를 실제 Figma Prototype 분기로 실행하는 것은 구현상 불가능하다. 추가 Case는 Flow/Spec용 설명에 가깝고, 첫 Case만 실제 클릭 reaction이 된다.
- 최종 확신: 구조/기록 78%, 실제 예외 Prototype 20%.
- 최종 감정: 팝업 자동 생성과 안전한 destination 필터는 반갑지만, `Case · flow`의 실행 불가 범위와 예측하기 어려운 자동 생성 때문에 신뢰가 낮아졌다.

## 잘된 점

1. 빈 상태에서 `+ Screen`이라는 명확한 단일 시작점을 제공한다.
2. 화면 생성, 블록 추가, 이름 변경이 캔버스 노드와 직접 연결되어 빠르게 저충실도 와이어프레임을 만든다.
3. Section은 내부 요소 묶음과 방향 설정을 간단히 제공하고, 팝업 Section 자체는 삭제하지 못하게 보호한다.
4. 액션 종류에 따라 Destination 후보를 일반 Screen 또는 해당 원본의 popup State로 제한해 잘못된 연결을 예방한다.
5. 팝업 내부에서는 중첩 팝업 선택을 제거하고 `Close popup`을 제공한다.
6. Flow source/destination을 눌러 캔버스로 이동할 수 있고, 캔버스 연결선과 실제 Figma reaction을 함께 갱신한다.
7. Screen 삭제 전 파생 State와 incoming connection 개수를 알려 주고 되돌릴 수 없음을 경고한다.
8. 화면 이름을 바꿔도 id 기반 연결이 유지되어 수정 회차에서 안정적이다.

## 문제 목록 — 심각도별

### 치명적

- 없음. 핵심 정상 흐름 생성 자체가 막히지는 않는다.

### 높음

1. **Case의 실행 범위가 불명확하다.** `Case · flow`의 조건은 문서용 문자열이고 실제 Figma Prototype에는 첫 Case만 반영되지만 이를 명시하지 않는다. 사용자가 예외 Prototype이 완성됐다고 잘못 보고할 수 있다.
2. **Section/요소 삭제가 무경고 연쇄 삭제다.** 하위 요소와 연결/Case가 함께 사라져도 확인과 영향 요약이 없다. Screen 삭제 보호와 일관되지 않다.
3. **Open popup의 부작용이 예측 불가능하다.** selector 선택 한 번으로 원본 전체를 복제한 파생 State와 팝업을 생성하고 기존 기본 액션을 교체한다. 명칭이나 사전 설명이 이를 전달하지 않는다.

### 중간

1. `State`가 popup 전용 파생 프레임이라는 정보가 없어 일반 상태/variant로 오해하기 쉽다.
2. `Default · prototype`과 `Case · flow`가 짧은 표기만으로 실제 Prototype/문서 전용 차이를 설명하지 못한다.
3. 팝업 편집 후 Back이 원본 Screen이 아니라 popup State로 돌아가 사용자의 공간 기대와 어긋난다.
4. 이름, Purpose, When, Outcome이 blur에 저장되나 저장 상태 피드백이 없다.
5. selector를 시험 클릭하면 즉시 저장되고 기존 Destination이 소실되어 비교 탐색 비용이 크다.
6. popup State가 원본 화면 전체를 복제해 Flow/Spec에서 배경 요소와 팝업 고유 요소의 경계가 약하다.
7. Flow의 선택 화면 목록과 Project flow가 같은 항목을 중복 표시해 중복 Feature처럼 보인다.
8. 블록 추가 후 Section이 계속 선택되어 새 노드 편집을 위해 Nodes에서 다시 찾아야 한다.

### 낮음

1. 전반적으로 영문 용어가 많아 한국어 사용자에게 첫 해석 비용이 있다.
2. Screen Select가 커질수록 이름 기반 탐색만 가능하고 그룹은 Screens/States 두 개뿐이다.
3. Spec은 화면 단위 읽기 전용이라 전체 기획안 복사/내보내기 흐름이 없다.
4. Remove case에 확인이 없어 빈 Case 정리에는 빠르지만 기존 Case 오삭제에는 취약하다.

## 가장 고민이 컸던 선택지

1. 화면에 블록을 직접 나열할지 Section 안에 넣을지.
2. 새 Screen을 만들지 기존 Screen을 복제할지.
3. `Go to screen`, `Open popup`, `Stay on screen`이 각각 Prototype 동작인지 문서용 결과인지.
4. `State`를 일반 UI 상태로 다룰지 popup 파생 화면으로 다룰지.
5. `Default · prototype`과 `Case · flow` 중 어느 것이 실제 재생되는지.
6. Open popup 전에 팝업을 만들어야 하는지, 선택하면 자동 생성되는지.
7. 팝업 편집 후 Back으로 원본 Screen에 갈지 popup State에 남을지.
8. Delete가 현재 요소만 지우는지 하위 요소와 연결까지 지우는지.

## 우선순위 개선안

1. **Case의 진실을 UI에 직접 표시한다.** `Default (Figma prototype)`과 `Additional case (documentation only)`처럼 이름을 바꾸고, `When` 아래에 “Flow/Spec에만 기록되며 Prototype에서 실행되지 않음”을 상시 노출한다.
2. **연쇄 삭제를 일관되게 보호한다.** Section/요소/Case 삭제 전에 `하위 요소 N개, 연결 N개, Case N개가 제거됨`을 요약하고 확인받는다. 영향이 없는 단일 장식 요소만 즉시 삭제해도 된다.
3. **Open popup을 예측 가능한 행위로 바꾼다.** 팝업이 없을 때 selector 명칭을 `Create popup`으로 표시하거나, 선택 후 `새 popup을 만들까요?`와 생성 결과를 안내한다. 기존 팝업이 있으면 `Open popup` + Destination을 유지한다.
4. **Screen/State 용어를 구체화한다.** 현재 구현 범위라면 `Screens / Popups`로 그룹명을 바꾸고 `Popup based on 강의 상세`처럼 관계를 표시한다.
5. **팝업 편집 문맥과 복귀를 명확히 한다.** 헤더를 `Edit popup: …`로 표시하고 Back은 원본 Screen 및 source 버튼으로 복귀시킨다.
6. **즉시 저장 피드백을 제공한다.** blur 입력 옆에 `Saved` 상태를 잠깐 표시하고, selector의 파괴적 변경에는 기존 목적지 소실을 막거나 최소 Undo를 제공한다.
7. **Section 추가 후 새 요소를 선택한다.** 방금 추가한 노드를 바로 상세 편집 대상으로 열고, Section으로 돌아가는 경로는 유지한다.
8. **Flow 중복 인지를 줄인다.** 선택 화면 Flow를 접을 수 있게 하거나 Project flow에서 해당 항목을 강조해 한 번만 보여 준다.
9. **Spec 전달 경로를 최소 추가한다.** 전체 화면 Spec을 한 번에 복사하는 단일 `Copy project spec` 정도만 제공하면 개발 리뷰 전달성이 크게 올라간다.

## 종합 판단

Sketchy는 빈 Figma 파일에서 모바일 화면과 정상 클릭 흐름을 빠르게 만드는 데 강하다. 중수 사용자는 기존 Figma 경험으로 Screen, Destination, Prototype 연결을 보완해 1차 과업을 큰 막힘 없이 끝낼 수 있다. 그러나 추가 요구가 들어오는 2차에서는 `State=popup`, `Open popup=자동 생성`, `Case flow=문서 전용`이라는 제품 고유 규칙이 드러나며, 이 규칙들이 UI에서 충분히 설명되지 않는다. 특히 조건 Case를 실제 Prototype으로 오인하는 문제와 무경고 연쇄 삭제는 개발 리뷰의 신뢰와 데이터 안전에 직접 영향을 준다. 우선 이 두 문제와 팝업 생성의 예측 가능성을 해결해야 한다.
