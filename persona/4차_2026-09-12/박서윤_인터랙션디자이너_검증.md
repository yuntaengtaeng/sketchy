# 박서윤 — 인터랙션 디자이너 독립 검증

## 전제

- 페르소나: 박서윤, B2B 편집기 경험이 많은 시니어 UX/Interaction 디자이너. Figma 숙련도는 높으며, 회의 직전 10분 안에 구조가 있는 로우파이 와이어프레임을 만드는 상황이다. 캔버스에서 대상을 먼저 선택하고 속성을 조정하며, 현재 위치와 다음 행동이 눈에 보이기를 기대한다.
- 검증 방식: 구현 기반 인지적 워크스루. 실제 사용자 테스트나 시간 측정은 수행하지 않았다.
- 확인한 구현 범위: `src/ui/App.tsx`, `src/ui/style.css`, `src/ui/features/build/*`, `src/shared/element-tree.ts`, `src/shared/index.ts`, `src/plugin/main.ts`, `src/plugin/commands/canvas/element.ts`, `src/plugin/commands/canvas/screen.ts`
- 환경 조건: Plugin UI는 360×720px이며, 빈 프로젝트에서 처음 사용하는 핵심 과업과 재사용 상황의 복잡 과업을 코드상 상태 전이와 노출 순서로 확인했다.

## 1차 과업

과업: 빈 프로젝트에서 Screen을 만들고 이름과 Purpose를 작성한 뒤 요소를 추가한다.

### 1차 과업 관찰

- 초기 성공 경로는 짧다. 빈 상태에서 Screen 생성 1회, 이름·Purpose 입력, 요소 추가 1회로 핵심 구조를 만들 수 있다.
- `Add something`은 이전처럼 접혀 있지 않고 Screen 편집과 같은 흐름에 있어 발견성이 좋다.
- Screen 이름과 Purpose가 `onBlur` 저장인데 저장됨·저장 중 상태가 없다. 사용자가 입력 직후 캔버스를 클릭하면 결과가 반영되므로 기능상 작동하지만, 10분 내 빠르게 여러 필드를 바꾸는 사용자에게는 확신이 약하다.
- `Other screens`의 Select는 다른 Screen 이동을 담당하고 `+ Screen`은 생성한다. 목적은 다르지만 360px에서 같은 시각 무게를 가져 새 Screen CTA의 우선순위가 충분히 낮아졌다고 보기는 어렵다.

과업: `Screen > Section 1 > Section 2 > Button/Input`과 `Section 1 > Section 3 > 요소`를 만들고, Button에서 상위·형제·다른 가지로 이동한다.

## 발견 사항

- 높음 · Section 내부 삽입 후 새 Node가 선택되지 않는다. 사용자의 명시적 행동은 “Button 추가”인데 결과 포커스는 부모 Section으로 돌아간다. `insertBlock()`이 `parentElement`가 있을 때 `figma.currentPage.selection = [parentNode]`를 설정하는 것이 근거다. 생성된 Node를 선택하면 재탐색 1클릭을 없애고 이름·옵션 편집을 즉시 이어갈 수 있다.
- 높음 · “Sibling navigation”은 leaf Node에만 성립한다. `Build.tsx`는 비-Section 요소에서 `elementSiblings()`를 쓰지만 Section이면 `SectionEditor`가 자식만 렌더링한다. 따라서 Section 2 ↔ Section 3은 한 번에 이동할 수 없다. 동일 컴포넌트 안에 목록을 더 쌓기보다, Section Inspector에 작은 `Siblings` Select 또는 breadcrumb의 각 조상에 동급 항목을 여는 선택기를 붙이는 편이 360px에 적합하다.
- 높음 · 깊은 breadcrumb의 현재 위치 가시성이 보장되지 않는다. `.breadcrumb`는 `overflow-x: auto`지만 모든 scrollbar를 숨기고 선택 변경 시 현재 crumb를 `scrollIntoView`하지 않는다. 긴 Screen/Section 이름에서는 사용자가 최상위 Screen만 보고 현재 Node가 오른쪽에 숨은 채 시작할 수 있다.
- 중간 · `In X`는 짧지만 목록 관계가 모호하다. leaf 선택에서는 같은 부모의 형제 전체를 뜻하고, Section 선택에서는 그 Section의 자식을 뜻한다. 화면에 보이는 형태가 같아 사용자는 제목보다 시행착오로 관계를 배운다. `Inside X`(자식)와 `Alongside current node` 또는 `Other items in X`(형제)처럼 관계를 분리하거나, 항상 “현재 컨테이너의 자식 목록”이라는 하나의 모델로 통일하는 편이 낫다.
- 중간 · Section 선택 시 현재 선택 표시가 목록에 없다. `SectionEditor`는 자식 목록에 부모 Section의 id를 `selectedElementId`로 넘겨 어느 행도 pressed가 되지 않는다. Breadcrumb의 굵은 현재 항목은 있지만 Inspector와 목록 사이에서 선택 피드백이 일관되지 않는다.
- 중간 · 현재 Node 이름보다 타입이 Inspector 제목을 차지한다. `button details`, `section details` 아래 Name 필드에 실제 이름이 나온다. 여러 `Button`을 오갈 때 breadcrumb와 목록에는 이름이 보이지만 편집 시작점은 타입명이라 확인 비용이 생긴다. 제목은 `Buy button`, 보조 라벨은 `Button`이 더 직접적이다.
- 중간 · Screen 이동 Select와 `+ Screen`, 그리고 3열 Block Picker는 360px에서 밀도가 높다. Block 카드는 최소 72px이라 조작 가능하지만, 3열은 긴 현지화 라벨과 타입 확장에 취약하다. 현재 6개 타입에서는 유지 가능하되 라벨 줄바꿈과 키보드 포커스 상태를 실제 Plugin에서 확인할 필요가 있다.
- 낮음 · Section 최대 깊이가 UI에서 사라짐으로만 전달된다. Low-fi 제약을 유지하는 것은 타당하지만 사용자가 앞 단계에서 Section을 봤다면 오류나 권한 문제로 오해할 수 있다. `Add to section` 아래 짧은 “Maximum section depth reached” 안내는 빈 추상화 없이 제약을 설명한다.
- 낮음 · Name/Purpose의 blur 저장에는 완료 피드백이 없다. 자동 저장을 유지하되 작은 상태 텍스트 하나로 최근 저장을 확인할 수 있으면 반복 편집의 불안을 줄인다.

## 더 편한 UX 대안 비교

### 권장: Breadcrumb + 컨텍스트 목록 유지, 두 군데만 보완

현재 방향을 유지하면서 다음 두 가지를 우선 수정하는 것이 가장 효율적이다.

1. Section 내부에서 생성한 새 Node를 즉시 선택한다.
2. Section 선택 상태에만 부모 컨테이너의 형제를 고르는 작은 `Sibling` Select를 제공한다.

이 조합은 leaf Node의 `In X` 목록을 그대로 쓰며, Section의 자식 제작 화면을 복잡하게 만들지 않고 Section 2 ↔ Section 3 이동을 2클릭에서 1회 선택으로 줄인다. Select 대신 목록을 하나 더 렌더링하면 `Inspector + Add picker + Children + Siblings`가 720px 높이에서 길어지므로 권하지 않는다.

### 대안: Breadcrumb 각 단계의 드롭다운

`Section 2` crumb 옆의 작은 chevron으로 같은 깊이의 `Section 3`을 선택하는 방식이다. 공간 효율과 다른 가지 이동에는 가장 강하지만, breadcrumb가 일반 링크인지 메뉴인지 복합 상호작용이 생기고 작은 타깃이 접근성에 불리하다. 향후 계층 이동 빈도가 충분히 확인된 뒤 적용할 수 있다.

### 대안: 전체 Layer Tree

현재 과업의 모든 이동을 한곳에서 해결하지만, 360px의 Inspector와 경쟁하며 접기·펼치기, 들여쓰기, 재정렬 기대까지 만든다. 최대 `Screen > Section > Section > Node` 깊이에서는 현재 문제보다 UI 비용이 크다. 현 단계에서는 채택하지 않는 것이 낫다.

## 우선순위

1. Section 내부 삽입 결과를 생성 Node 선택으로 변경한다.
2. Breadcrumb가 선택된 마지막 항목을 항상 보이게 스크롤하고 양끝 overflow 단서를 제공한다.
3. Section 선택 시 형제 Section으로 바로 이동할 수 있는 컴팩트한 선택 수단을 추가한다.
4. `In X`가 자식/형제 중 무엇을 의미하는지 라벨 모델을 통일한다.
5. Inspector 제목을 Node 이름 중심으로 바꾸고 Screen 자동 저장 피드백을 보완한다.

## 최종 판정

- **부분 성공.** 선택 기반 Inspector, 재귀 breadcrumb, leaf Node의 형제 목록은 기존의 “선택 후 다른 Node로 이동하기 어려움”을 실질적으로 줄이며, 전체 Layer Tree 없이도 최대 두 단계 Section 구조를 이해할 수 있다.
- 다만 복잡 과업의 주 반복 동작인 “Section 안에 추가하고 바로 편집”이 매번 부모로 되돌아가고, Section 형제 이동은 제안된 sibling navigation의 예외로 남는다. 깊은 breadcrumb의 가시성까지 보완하기 전에는 빠른 구조 제작 UX가 완성됐다고 보기 어렵다.
- 가장 작은 유효 개선은 범용 Tree나 Sidebar 프레임워크 추가가 아니라 **생성 결과 포커스 수정 + Section 형제 선택 수단 + breadcrumb 가시성 보장**이다.
