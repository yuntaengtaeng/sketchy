# 김서윤 — PM 2차 독립 재검증

## 참가자와 방법

- 초기 B2B SaaS 스타트업 PM/PO 5년 차
- Figma 숙련도 중상, 개발 킥오프 전 빠르게 화면 흐름과 명세를 만드는 상황
- 기존 persona와 제품 설명을 보지 않고 현재 `src` 구현만 확인한 인지적 워크스루
- 실제 플러그인 실행이나 시간 측정 결과가 아니라 구현상 가능 여부를 평가함

## 1차 과업 — 4화면 온보딩

`워크스페이스 생성 → 팀 정보 입력 → 요금제 선택 → 설정 완료`를 만들고 각 CTA를 다음 화면으로 연결했다.

- 네 화면 생성, 이름과 Purpose 변경, Button 추가, 실제 Figma Navigate 연결은 구현상 가능했다.
- 화면은 한 행에 네 개까지 배치되어 이번 선형 과업은 읽기 쉬웠다.
- Screen details가 접혀 있고 아래쪽에 있어 이름부터 정하려는 흐름은 스크롤과 재선택이 필요했다.
- `Notes (spec only)`는 “입력값 저장 후 이동” 같은 개발 전달에는 유용했지만, 이동 전 처리인지 도착 상태 설명인지 작성 범위는 모호했다.
- Flow의 선택 화면 연결이 Project flow에 다시 나타나 중복처럼 보였다.

판정은 **부분 성공**이다. 선형 prototype과 명세는 완성할 수 있지만 반복 선택, 접힘 UI, blur 저장이 시간 압박에서 마찰을 만든다.

## 2차 과업 — 상태 복제, 삭제 복구, Snackbar

`팀 정보 입력`을 Duplicate해 정상/오류 상태를 만들고 연결한 뒤, 목적 화면을 삭제하고 원래 버튼에 새 action을 설정했다.

- 화면과 중첩 요소 구조는 새 ID로 복제되어 상태 화면 제작이 빨라졌다.
- 복제본의 Feature와 Figma reaction은 복사되지 않았다. 안전한 기본값이지만 UI가 이를 알리지 않아 Flow에서 확인하기 전까지 연결된 것으로 오해할 수 있다.
- 화면 삭제 시 해당 화면과 요소, 출발 Feature, 들어오는 Feature와 reaction이 함께 정리됐다.
- 삭제 후 원래 버튼은 `Choose action`으로 돌아가 새 Navigate를 설정할 수 있었다. 과거의 disabled 같은 복구 불가능 상태는 재현되지 않았다.
- 다만 삭제된 incoming Feature의 Notes까지 사라져 원래 의도를 복구할 단서가 없고, 삭제 확인창에도 영향 연결 수가 표시되지 않았다.

“저장 성공 Snackbar를 3초 노출”은 실제 prototype으로 만들 수 없었다. Describe에 문장으로 남기거나 Snackbar가 그려진 전체 화면으로 Navigate할 수 있지만, overlay·자동 닫힘·현재 화면 유지 의미는 보존되지 않는다.

## 최종 판정과 우선순위

전체 판정은 **부분 성공**이다.

1. Duplicate가 콘텐츠만 복제하고 연결은 제외한다는 결과를 조작 근처에서 알려야 한다.
2. Delete 전에 제거될 incoming 연결 수를 알리고 삭제 뒤 재연결 단서를 남겨야 한다.
3. Popup/Snackbar를 실제 결과로 만드는 최소 overlay 행동이 필요하다.
4. Screen details 발견성과 blur 저장 피드백을 개선해야 한다.
