# 오하늘 — 기획자 독립 검증

## 전제

- 페르소나: 오하늘, 커머스 스타트업 PM. Figma 숙련도는 중급(오토레이아웃·컴포넌트 개념은 알지만 직접 조립은 느려서 피함). Claude Code로 MCP Agent에게 요청해본 경험이 있어 자연어 지시에 능숙. 스프린트 리뷰 30분 전 초안을 팀에 공유해야 하는 시간 압박이 큼. 작업 습관은 "Agent에게 먼저 통짜로 요청 → 결과를 훑어보고 부족한 부분만 후속 요청 → 마지막에 팀 공유용 산출물로 정리".
- 검증 방식: 구현 기반 인지적 워크스루(실제 사용자 테스트나 시간 측정이 아님).
- 확인한 구현 범위: `docs/development/mcp-v1.md`, `docs/development/remote-mcp.md`, `src/mcp/schemas.ts`, `src/mcp/change-tools.ts`, `src/mcp/read-tools.ts`, `src/mcp/create-server.ts`, `src/core/project-change.ts`, `src/core/validate-project-changes.ts`, `src/shared/index.ts`, `src/shared/element-tree.ts`, `src/ui/features/spec/Spec.tsx`, `src/ui/features/spec/describe.ts`, `src/plugin/main.ts`의 `EXPORT_PROJECT` 처리.
- 검증 방법에 대한 제약: 연결된 실제 Sketchy 프로젝트(`project-mtxwg04u-anrrch`, revision 53)가 비어 있지 않고 이미 QR 주문 플로우가 들어 있었다. 실제 사용자 데이터를 훼손하지 않기 위해 `apply_project_changes`는 호출하지 않고 `preview_project_changes`(저장하지 않는 검증, `apply`와 동일한 검증기 사용— `mcp-v1.md` "Preview와 Apply는 같은 검증기를 사용한다")와 `get_project`/`get_screen`만으로 스키마·검증 동작을 실측했다. 따라서 "빈 프로젝트에 실제로 저장"까지는 확인하지 못했고, 저장 전 단계(스키마 통과 여부, 검증 오류 메시지)까지만 실측했다.

## 발견 사항

- P1 · Element에 숫자·단위 등 구조화된 속성 필드가 없다 · `src/mcp/schemas.ts`의 `element`(`name`, `description`만 허용)와 `src/core/project-change.ts`의 `Element` 타입이 동일하게 문자열 두 개뿐이며, 실제 preview로 "평점 4.8"을 만들어도 자유 텍스트로만 저장됨을 확인.
- P1 · Spec 탭이 Element의 `description`을 전혀 표시하지 않는다 · `src/ui/features/spec/Spec.tsx`의 `ElementList`가 `element.name`과 `element.type`만 렌더링. Agent가 채워 넣은 값(평점, 리뷰 개수 등)이 기획서 산출물에 나타나지 않아 Spec을 "지금 화면에 무엇이 있는지" 이상의 근거 문서로 쓰기 어려움.
- P1 · Export가 사람이 읽는 문서가 아니라 내부 Canonical JSON 스냅샷이다 · `src/plugin/main.ts`의 `EXPORT_PROJECT` 핸들러가 `createProjectDocument`를 `JSON.stringify(document, null, 2)`로 그대로 다운로드. 팀 공유용 산출물이 아니라 MCP fixture/개발자용 데이터임.
- P2 · 이미 만든 Element의 순서를 나중에 바꿀 수 없다 · `UPDATE_ELEMENT`의 patch 스키마(`schemas.ts`)에 `order` 필드가 없어 실제 호출 시 "Unrecognized key" 오류로 거절됨을 확인. 기존 요소 사이에 새 요소를 끼우려면 처음부터 정수 간격을 벌려 만들었어야 하며, 그렇지 않으면 삭제 후 재생성해야 하고 삭제는 하위 트리·연결 Action까지 함께 지운다(`validate-project-changes.ts`의 `DELETE_ELEMENT`).
- P2 · Screen에는 순서·좌표 개념이 없다 · `schemas.ts`/`project-change.ts`의 `Screen`에 위치 필드가 없어 "두 화면 사이에 끼워 넣기"는 항상 Feature의 `destinationScreenId` 재배선으로만 표현된다. 실측(preview)으로는 정상 동작했지만, Agent가 "위치"라는 개념 없이 그래프 재배선을 스스로 설계해야 자연어 요청("결제와 주문완료 사이에 넣어줘")을 올바르게 수행할 수 있다.
- P3 · Apply가 Figma Canvas를 즉시 바꾸지 않는다 · `create-server.ts`의 서버 안내문과 `remote-mcp.md`에 따르면 Plugin이 열려 있어야 poll로 자동 반영되므로, Figma를 닫아둔 채 Agent에게 요청한 오하늘은 결과가 바로 안 보여 혼란을 겪을 수 있다.

## 최종 판정

- 부분 성공. Screen/Element/Action을 자연어 요청으로 빠르게 쌓고 preview→apply 계약으로 안전하게 검증하는 핵심 흐름, 그리고 화면 간 흐름을 재배선해 중간에 새 화면을 끼워 넣는 예외 처리는 코드·실측 모두에서 안정적으로 동작했다. 그러나 오하늘이 실제로 원하는 결과물 — "평점/리뷰 개수 같은 구조화된 제품 정보"와 "팀에 공유할 기획서" — 는 현재 구현에서 이름-설명 문자열 뭉치(Spec에는 그마저도 설명이 안 보임)와 내부 JSON 스냅샷 수준에 머물러 있어, "의미 있는 제품 구조"로 남지 못하고 사실상 텍스트 뭉치로 남는다.
