# 오하늘 — UX/인터랙션 디자이너 독립 검증

## 전제

- 페르소나: 오하늘, 프로덕트 디자이너 (UX/인터랙션 전담), Figma 숙련도 상급 (Auto Layout, Variants, 컴포넌트 속성까지 실무에서 매일 사용). 스타트업 소속으로 스프린트 킥오프 직전 30분 안에 로우파이 와이어프레임을 조립해 개발팀과 정렬해야 하는 상시 시간 압박 상태. 작업 습관: 화면을 먼저 대략 배치한 뒤 요소를 세밀하게 끼워 넣고 다듬는 "빠른 골격 → 정교화" 순서를 선호하며, 마우스 클릭·드래그 기반 조작에 익숙하고 타이핑/코드형 입력은 최후 수단으로만 쓴다.
- 검증 방식: 구현 기반 인지적 워크스루 (실제 사용자 테스트나 시간 측정 아님)
- 확인한 구현 범위:
  - `src/ui/features/build/` 전체 (BlockPicker.tsx, ScreenEditor.tsx, Build.tsx, ElementDetails.tsx, SectionEditor.tsx, NodeList.tsx, blockRegistry.ts, ButtonOptions.tsx, SectionOptions.tsx)
  - `src/plugin/commands/canvas/element.ts`, `element-render.ts`
  - `src/shared/index.ts` (`BLOCK_DEFINITIONS`, `Element`, `PluginMessage`, 특히 `INSERT_BLOCK`)
  - `src/shared/element-tree.ts` (`elementSiblings`, `canNestSection`, `MAX_SECTION_DEPTH`)
  - `src/core/validate-project-changes.ts`, `src/core/project-change.ts`
  - `src/mcp/schemas.ts`
  - `docs/development/mcp-v1.md` (기술 계약 문서)

## 2차 과업 — 기존 요소 A, B, C 사이(B와 C 사이)에 새 요소 끼워 넣기

| 단계                                                                 |                                                                                 기대 | 실제 결과                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | 판정 |
| -------------------------------------------------------------------- | -----------------------------------------------------------------------------------: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| Plugin UI: B와 C 사이에 새 블록을 넣을 위치를 지정                   |                 BlockPicker나 NodeList에서 "B 다음에 삽입" 같은 위치 지정이 가능하다 | `BlockPicker.tsx`는 `INSERT_BLOCK`에 `screenId`, `block`, `parentElementId`만 보낸다. 위치/순서 파라미터가 없다 (`PluginMessage`의 `INSERT_BLOCK` 정의, `src/shared/index.ts` 202-208행)                                                                                                                                                                                                                                                                                                                                                      | 실패 |
| Plugin UI: 실제 삽입 위치                                            |                                       새 블록은 항상 부모의 마지막 자식으로 추가된다 | `element.ts`의 `insertBlock`은 `element.order`를 아예 설정하지 않고, `element-render.ts`의 `createElementNode`가 `parent.appendChild(node)`로 Figma 노드 트리 맨 끝에 붙인다. `ScreenEditor`/`SectionEditor`는 `order ?? 0`으로 정렬하는데 모든 UI 생성 Element가 `order` 미설정(=0 동률)이라 정렬은 배열 push 순서, 즉 생성 순서와 같다 → 항상 맨 끝(C 뒤)에 삽입됨                                                                                                                                                                          | 실패 |
| Plugin UI: 순서를 바로잡을 수단                                      |                  드래그 재정렬이나 "위/아래로 이동" 버튼으로 B/C 사이로 옮길 수 있다 | `NodeList.tsx`는 클릭으로 선택만 하는 버튼 목록이고 드래그 핸들이나 이동 컨트롤이 없다. `ElementDetails.tsx`에도 이동 기능 없음, 있는 건 이름 수정과 삭제뿐. 재정렬 수단이 코드 어디에도 없음                                                                                                                                                                                                                                                                                                                                                 | 실패 |
| MCP Batch: `ADD_ELEMENT`로 위치 지정 가능한지                        | Agent가 새 Element의 `order`를 B와 C 사이 값으로 지정해 정확한 위치에 삽입할 수 있다 | `schemas.ts`의 `element` 스키마는 `order: z.number().int().nonnegative().optional()`을 허용하므로 신규 Element 생성 시 order 지정 자체는 가능. 그러나 기존 A/B/C는 Plugin UI로 만들어졌다면 order가 없어 `elementSiblings`(`element-tree.ts` 38행)에서 전부 `order ?? 0`으로 동률 취급된다. 신규 Element에 `order: 1`을 줘도 기존 3개(0,0,0)보다 항상 뒤로 정렬되어 "B와 C 사이"가 아니라 "C 뒤" 즉 맨 끝에 배치된다. 반대로 새 Element에 `order: -1`이나 `0.5`류를 줘도 스키마가 `nonnegative` 정수만 허용해 소수·음수 삽입 트릭도 막혀 있다 | 실패 |
| MCP Batch: 기존 A/B/C의 order를 재조정해서라도 위치를 맞출 수 있는지 |     안 되면, Agent가 A/B/C에 order를 다시 부여하는 `UPDATE_ELEMENT`로 우회할 수 있다 | `ElementPatch`(`project-change.ts` 79-81행, `schemas.ts`의 `elementPatch`)는 `name, description, buttonVariant, direction`만 허용하고 `order`는 패치 대상에서 빠져 있다. 즉 한 번 생성된 Element의 order는 이후 어떤 MCP 변경으로도 바꿀 수 없다. 우회 경로 없음                                                                                                                                                                                                                                                                              | 실패 |

## 발견 사항

- P1 · "B와 C 사이에 끼워 넣기"가 Plugin UI와 MCP Batch 양쪽 모두에서 구조적으로 불가능하다. Plugin UI는 `insertBlock`이 항상 `parent.appendChild`로 끝에만 붙이고(`src/plugin/commands/canvas/element-render.ts` 85행), 재정렬 UI가 아예 없다(`NodeList.tsx`). MCP는 `order` 필드가 `ADD_ELEMENT`에만 있고 `UPDATE_ELEMENT` 패치에는 없어(`src/core/project-change.ts` 79-81행) 기존 요소 순서를 나중에 조정할 방법이 없으며, 신규 Element에 order를 줘도 UI로 만든 기존 요소들은 order가 비어 있어 항상 0 동률로 앞서기 때문에 원하는 "사이" 위치가 나오지 않는다. "인터랙션 UI 초안을 빠르게 조립하고 요소를 세밀하게 다루는" 목적의 도구에서 순서 편집이 빠지면, 실무 디자이너는 매번 "지우고 순서대로 다시 쌓기"로 우회해야 한다.
- P2 · 리뷰처럼 "라벨-값" 성격의 서로 다른 정보 조각을 담는 전용 블록이 없다. `BLOCK_DEFINITIONS`(`src/shared/index.ts` 9-16행)는 text/button/input/image/divider/section 6종뿐이라, 평점과 리뷰 개수 같은 짧은 메타 정보도 각각 별도 text 블록으로 쪼개 넣어야 한다. 로우파이 단계라 치명적이진 않지만, section 안에 이름만 있는 text가 여러 개 쌓이면 NodeList에서 `item.type`만 보고는 "평점 텍스트"인지 "개수 텍스트"인지 이름을 일일이 클릭해서 확인해야 한다.
- P3 · MCP `element` 스키마의 `order`가 `nonnegative` 정수로 제한되어 있어(`src/mcp/schemas.ts` 31행), 설령 기존 요소들이 order를 갖고 있었더라도 두 정수 사이에 끼워 넣는 소수 값 트릭(예: 1과 2 사이에 1.5)조차 스키마 단계에서 거부된다. 향후 order 기반 위치 지정을 살리려면 최소한 실수(float) 허용이나 명시적인 "afterElementId" 같은 상대 위치 지정 방식이 필요해 보인다.

## 최종 판정

- 부분 성공. 빈 프로젝트에서 화면을 만들고 섹션 안에 text 블록들을 조합해 "상품 리뷰" 영역을 구성하는 1차 과업은 Plugin UI와 MCP 양쪽 다 (형태는 투박해도) 가능했다. 그러나 2차 과업인 "기존 요소 사이에 새 요소 끼워 넣기"는 Plugin UI에 삽입 위치 지정도, 사후 재정렬 수단도 전혀 없고, MCP Batch 역시 `order`가 신규 생성 시에만 쓰이고 패치로 갱신할 수 없어 기존 요소와의 상대 위치를 맞출 방법이 없다는 것을 코드로 확인했다. "요소를 세밀하게 다루고 싶어 하는" 인터랙션 디자이너 관점에서 이 순서 편집 공백은 반복 작업마다 부딪히는 핵심 장애로 판단된다.
