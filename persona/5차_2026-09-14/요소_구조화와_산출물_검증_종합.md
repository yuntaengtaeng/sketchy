# 요소 순서·구조화·산출물 독립 검증 종합

## 검증 범위

- 방식: UX/인터랙션 디자이너와 기획자/PM, 두 독립 페르소나의 구현 기반 인지적
  워크스루. 서로의 결과를 보지 않고 각자 소스 코드를 직접 읽고 판단했다
  (기획자 페르소나는 실제 연결된 프로젝트에 `preview_project_changes`를
  실행해 스키마 거절 오류까지 실측했다).
- 대상: (1) 기존 요소 사이에 새 요소를 끼워 넣는 능력, (2) 평점·개수 같은
  서로 다른 정보를 요소에 구조화해서 담는 능력, (3) 만든 결과를 팀 공유
  산출물로 꺼내는 능력 (Spec, Export).
- 한계: 실제 사용자 테스트나 시간 측정 결과가 아니다.

## 종합 판정

**부분 성공.** Screen·Element·Action을 자연어 요청이나 클릭 몇 번으로
빠르게 쌓는 핵심 흐름과 화면 간 흐름을 그래프로 재배선하는 예외 처리는
Plugin UI와 MCP Batch 양쪽 모두 안정적으로 동작한다. 그러나 두 페르소나가
공통으로 부딪힌 지점은 "이미 만든 것을 나중에 다시 다듬는" 단계다 — 요소
순서를 바꾸거나, 서로 다른 정보를 구조화해서 남기거나, 결과를 사람이 읽는
문서로 꺼내는 세 가지 모두 현재 구현에 없다.

## 공통 발견

### P1 · 기존 요소 사이에 새 요소를 끼워 넣을 방법이 없다

두 페르소나 모두 코드로 확인했다.

- Plugin UI: `BlockPicker`의 `INSERT_BLOCK`은 위치 파라미터가 없고,
  `insertBlock`은 `order`를 설정하지 않으며 Figma 노드도
  `parent.appendChild`로 항상 끝에 붙는다. `NodeList`에는 드래그나
  이동 버튼이 없다.
- MCP Batch: `element` 스키마의 `order`는 `ADD_ELEMENT` 생성 시에만
  받는다. `UPDATE_ELEMENT`의 patch 스키마에는 `order`가 아예 없어서,
  PM 페르소나가 실제로 `preview_project_changes`를 호출해보니
  `Unrecognized key: "order"`로 즉시 거절됐다. 기존 UI로 만든 요소는
  애초에 `order`가 비어 있어 신규 요소에 어떤 order를 줘도 항상 뒤로
  밀린다.
- 결과적으로 "간격을 미리 벌려서 만들지 않은 이상" 기존 순서 사이에
  끼워 넣는 방법이 UI·MCP 어느 쪽에도 없다. 삭제 후 재생성만 가능한데,
  삭제는 하위 트리와 연결된 Action/Case까지 함께 지운다.

### P1 · 서로 다른 정보(평점, 개수)를 구조화해서 담을 방법이 없다

`Element`(`project-change.ts`, `mcp/schemas.ts`)는 `name`·`description`
문자열 두 개뿐이고 숫자·단위·타입 필드가 없다. "★ 4.8", "128개 리뷰" 같은
값은 별도 text 요소 두 개를 만들거나 description에 밀어 넣는 자유 텍스트로만
표현된다. 사용자가 처음 이 세션에서 지적한 "Section 이름에 '상품 리뷰 · ★
4.8 (128)'이 다 압축되어 들어감" 현상과 정확히 같은 근본 원인이다 — Agent도
Plugin UI도 애초에 그 이상을 표현할 스키마가 없다.

## 서로 다른 발견

- UX 디자이너 페르소나: MCP `order`가 `nonnegative` 정수로만 제한돼 있어
  두 정수 사이에 소수 값(1.5 등)을 끼워 넣는 트릭도 스키마 단계에서 막힌다는
  세부 사항을 짚었다.
- 기획자 페르소나: **Spec 탭이 `element.description`을 전혀 렌더링하지
  않는다**는 점을 발견했다 (`Spec.tsx`의 `ElementList`는 이름과 타입만
  표시). Agent가 채워 넣은 값이 애초에 Spec 산출물에 나타나지 않는다.
- 기획자 페르소나: **Export가 `JSON.stringify(document, null, 2)`를 그대로
  다운로드하는 내부 Canonical 스냅샷**이라는 점을 확인했다. 사람이 읽는
  기획서가 아니라 MCP fixture/개발자용 데이터다. 사용자가 이번 세션에서
  제안한 "로그인 유저에게 프로젝트를 그럴듯한 기획서 `.md`로 뽑아준다"는
  아이디어가 채울 수 있는 정확한 공백이다.
- 기획자 페르소나: 화면 사이(예: 결제↔주문완료)에 새 화면을 끼워 넣는
  것은 실측(`preview_project_changes`, `valid:true`)으로 **성공**을
  확인했다 — Screen에는 순서 개념이 없고 Feature의
  `destinationScreenId` 재배선만으로 표현되기 때문에, 요소 레벨과 달리
  화면 레벨 "중간 삽입"은 이미 가능하다.
- 기획자 페르소나: Apply가 Figma Canvas를 즉시 바꾸지 않고 Plugin이 열려
  있어야 poll로 반영된다는 설계(이번 세션에서 이미 구현·검증한
  자동 동기화)를 별도로 재확인했다. Plugin을 닫아둔 채 Agent에게 요청하면
  결과가 바로 안 보여 혼란을 겪을 수 있다는 점을 기획자 관점에서 다시
  지적했다.

## 권장 다음 순서

1. **요소 순서 재배치를 MCP·UI 양쪽에 추가한다.** `UPDATE_ELEMENT` patch에
   `order`를 추가하거나, 절대 순번 대신 `insertAfterElementId` 같은 상대
   위치 지정으로 바꾼다. Plugin UI에도 최소한 "위/아래로 이동" 정도는
   붙인다 (전체 드래그 재정렬까지는 실제 사용 빈도를 보고 판단).
2. **Spec 탭에 `element.description`을 표시한다.** 스키마 변경 없이 렌더링
   누락만 고치는 작은 수정이며, 지금 상태로는 Agent가 채운 내용이 산출물에
   전혀 안 보이는 명백한 결함이다.
3. **Export를 사람이 읽는 문서로 만든다.** 사용자가 제안한 로그인 유저 대상
   `.md` 기획서 내보내기 방향과 일치한다. 지금 내부 JSON 스냅샷 위에
   Screen/Element/Feature를 사람이 읽는 문장으로 요약하는 레이어를 얹는
   형태가 될 것으로 보인다 (Spec 탭의 `describe.ts`가 이미 일부 요소를
   문장으로 바꾸는 로직을 갖고 있어 재사용 가능성이 있다 — 다음 작업에서
   실제로 확인 필요).
4. **평점·개수 같은 구조화된 필드 도입은 실제 관찰 후 판단한다.** 로우파이
   도구의 단순함을 지키는 것과, Section 안에 이름만 다른 text가 쌓여
   무엇인지 구분 안 되는 문제 사이의 균형이 필요하다. 당장 새 필드 타입을
   추가하기보다, 1번(순서)과 2번(Spec)을 먼저 고쳐서 "구조는 있는데 못
   찾는다"는 문제부터 없앤 뒤에도 부족하면 그때 라벨-값 필드를 검토한다.

## 검증 한계

- 두 보고서 모두 구현 기반 인지적 워크스루이며 실제 사용자 테스트가
  아니다.
- 기획자 페르소나는 실제 프로덕션 프로젝트를 훼손하지 않기 위해
  `apply_project_changes`(저장)는 호출하지 않고 `preview_project_changes`
  (같은 검증기를 쓰는 저장 없는 검증)까지만 실측했다. "요소 순서를 실제로
  저장한 뒤 Figma Canvas에 반영되는 모습"은 이번 검증 범위 밖이다.
- 두 페르소나 모두 같은 이름("오하늘")을 독립적으로 선택했다. 우연이며
  파일명은 역할로 구분되어 있어 결과에는 영향이 없다.
