# Sketchy 독립 페르소나 연구 종합

## 연구 목적

Sketchy의 기획 의도나 제품 철학을 알려 주지 않은 사람들이 이 플러그인을 처음 접했을 때 무엇으로 이해하는지, 그리고 첫 초안이 아닌 두 번째 수정 작업에서도 계속 쓸 수 있는지를 확인했다.

참가자마다 다음 두 과업을 수행했다.

1. 자신의 업무에서 실제로 만들 법한 User Flow를 처음부터 만들고 기획안으로 정리한다.
2. 시간이 지난 뒤 같은 기획안에 현실적인 추가 요구와 예외 흐름을 반영한다.

이 연구는 실제 배포 플러그인을 마우스로 조작한 대면 테스트가 아니다. 각 독립 에이전트가 현재 구현된 UI와 Figma 명령 흐름을 최소한으로 확인한 뒤 수행한 인지적 워크스루다. 따라서 발견사항은 구현과 사용자의 기대가 충돌할 가능성을 찾는 데 유효하지만, 실제 완료 시간이나 클릭 오류율을 측정한 결과는 아니다.

## 독립성 통제

- 각 참가자는 대화 맥락을 전달하지 않는 별도 에이전트로 시작했다.
- 서로 대화하거나 다른 참가자의 결과를 읽지 못하게 했다.
- `persona` 폴더를 읽지 못하게 해 앞선 결과에 맞춰 의견이 수렴되는 것을 막았다.
- README, 기능 정의, 프로젝트 철학, AGENTS 문서를 읽지 못하게 했다.
- 실제 UX 파악에 필요한 manifest, package, UI, plugin, shared 코드만 최소 범위로 보게 했다.
- 참가자별로 자기 파일 하나만 쓰고 제품 코드는 수정하지 못하게 했다.
- 어떤 User Flow를 선택할지는 각 참가자가 자신의 업무 맥락에서 독립적으로 정하게 했다.

## 에이전트에게 내린 명령

### 공통 명령 골격

아래 내용을 모든 참가자에게 동일하게 전달하고, 첫 문단의 직무만 다르게 지정했다.

> 당신은 Figma 플러그인의 독립 사용성 평가 참가자다. Sketchy의 내부 철학이나 기존 기획을 모르는 일반 사용자처럼 행동한다. 다른 에이전트와 대화하거나 그 결과를 참고하지 않고, persona 폴더와 제품 설명·철학 문서를 읽지 않는다. 실제 제공 UX를 파악하는 데 필요한 구현만 최소한으로 살펴본다.
>
> 먼저 한국 이름, 업무 맥락, Figma 숙련도, 시간 압박과 작업 습관을 구체적인 페르소나로 정한다. 이후 이 플러그인을 실제로 두 번 사용한다고 가정해 구현에 근거한 인지적 워크스루를 한다.
>
> 1차 사용에서는 본인이 실제 만들 법한 User Flow를 처음부터 생성하고 기획안을 완성하려 시도한다. 2차 사용에서는 시간이 지난 뒤 같은 기존 기획안에 현실적인 추가 요구사항을 넣고 수정·확장한다.
>
> 각 회차에 목표, 시작 기대, 구체적인 조작 순서, 화면에서 이해한 것, 막힘과 우회, 감정, 결과를 기록한다. 구현상 가능한 것과 불가능한 것을 구분하고 성공했다고 꾸미지 않는다. 마지막에는 잘된 점, 심각도별 문제, 재방문·확장성 문제, 우선순위 개선안을 작성한다.
>
> 프로젝트 코드는 수정하지 않고 본인의 결과 파일 하나만 작성한다.

### 참가자별 역할 지정

| 참가자 | 지정한 출발 역할                | 스스로 선택한 플로우                         | 두 번째 과업                                |
| ------ | ------------------------------- | -------------------------------------------- | ------------------------------------------- |
| 윤서진 | 초기 스타트업 PM/PO             | 공동구매 목록 → 상품 상세 → 참여 완료        | 로그인 분기, 품절 알림, 수량과 필수 동의    |
| 김준호 | 대기업·에이전시형 서비스 기획자 | 카페 메뉴 탐색 → 상세 → 장바구니 → 주문 완료 | 빈 장바구니, 주문 실패, 즐겨찾기, 카드 구조 |
| 김소연 | B2C Product Designer            | 클래스 탐색 → 상세 → 예약 확인 → 예약 완료   | 찜, 로그인 안내, 매진과 대기 알림           |
| 강혜원 | 개발자 출신 프로덕트 메이커     | 메뉴 선택 → 수량 입력 → 주문 요청 완료       | 수량별 승인 분기와 품절 예외                |

## 참가자별 핵심 결과

### 윤서진 — 빠른 기획과 전달 관점

- 세 화면의 선형 happy path는 화면 생성, 블록 배치, 버튼 연결, Flow와 Spec 확인까지 완료했다.
- 두 번째 과업에서는 로그인 여부나 품절 같은 조건을 한 버튼에 붙이지 못해 가상 버튼과 Purpose 문장으로 우회했다.
- Section 안에 자식을 연속 추가하는 흐름은 빠르지만, 생성된 자식 이름을 고치려면 Nodes에서 다시 찾아야 했다.
- 요소 삭제 뒤 행동이 고아 상태로 남을 수 있고 이를 정리할 UI가 없어 결과 신뢰가 흔들렸다.
- 화면별 Spec만으로는 전체 기획 전달을 끝낼 수 없어 별도 문서가 다시 필요했다.

### 김준호 — 정책과 예외 관리 관점

- 실제 Figma 프레임과 프로토타입 연결이 만들어지는 점에서 초반 신뢰를 얻었다.
- 빈 상태, 주문 실패, 재시도, 즐겨찾기 토글을 정확히 모델링하지 못했다.
- 화면 복제·삭제, Flow에서의 연결 편집이 없어 두 번째 세션의 유지 비용이 크게 늘었다.
- Section을 중첩할 수 없어 Image와 Button을 묶은 반복 카드 구조를 의미 있게 표현하기 어려웠다.
- Spec의 전체 보기·복사·내보내기가 없어 핸드오프의 단일 원본이 되지 못했다.

### 김소연 — 디자인 제작과 선택 안정성 관점

- 화면, 기본 블록, Navigate가 한 루프로 이어져 작은 선형 프로토타입은 빠르게 만들었다.
- `Change state`가 실제 시각 상태 전환처럼 보이지만 정적 명세에 가까워 기대와 결과의 간극이 가장 컸다.
- 캔버스에서 내부 텍스트 노드를 선택하면 플러그인의 편집 맥락이 다른 화면으로 어긋날 수 있음을 발견했다.
- 화면 복제·삭제·재정렬 부재가 정상/매진 같은 유사 화면 제작과 정리에 직접적인 부담이 됐다.
- 생성 직후 자식 선택, 저장 상태 피드백이 없어 반복 편집의 리듬과 확신이 약했다.

### 강혜원 — 구현 가능한 명세 관점

- 문서 단위 저장과 재진입은 자연스러웠고 단일 목적지 교체도 가능했다.
- 조건을 Purpose에 쓸 수는 있지만 실제 연결은 무조건 이동이어서 기획 문장과 프로토타입이 서로 모순될 수 있었다.
- Flow에서 연결 사이에 화면을 삽입하거나 목적지를 수정·삭제할 수 없어 원본 버튼까지 계속 역탐색했다.
- Input change와 form submit이 없어 수량 기반 승인이라는 두 번째 과업의 핵심을 완료하지 못했다.
- 고립 화면이나 설명과 동작의 모순을 Spec이 경고하지 않아 잘못된 완성감을 줄 수 있다고 평가했다.

## 교차 분석

### 네 명 모두에게 확인된 강점

1. **첫 화면을 만드는 진입 비용이 낮다.** 별도 프로젝트 설정 없이 현재 Figma 문서에서 바로 시작하고, 프리셋 크기의 화면과 기본 블록을 클릭으로 만든다.
2. **작은 선형 흐름은 빠르게 완성된다.** 화면 생성 → 블록 추가 → Button Navigate → Flow/Spec 확인이라는 기본 루프는 모두 이해했다.
3. **실제 캔버스 결과가 신뢰를 준다.** 버튼 이동이 실제 Figma 프로토타입 reaction과 연결선으로 생성되는 점은 단순 문서 도구보다 강한 가치다.
4. **프로젝트 단위 저장은 재방문에 적합하다.** 같은 문서에서 별도 불러오기 없이 기존 작업을 이어 가는 경험은 네 명 모두 자연스럽게 받아들였다.

### 네 명 모두에게 확인된 핵심 한계

1. **두 번째 사용에서 조건과 예외를 정확히 담지 못한다.** 참가자 네 명이 서로 다른 도메인을 골랐지만 로그인, 품절, 실패, 승인 등 조건부 흐름에서 모두 막혔다.
2. **`Change state`의 약속과 결과가 다르다.** true 설정과 행동 설명만 가능한데 이름과 배치가 실제 프로토타입 상태 전환을 기대하게 한다.
3. **화면 생명주기와 재편집이 부족하다.** 화면 복제·삭제, Flow 연결 편집 부재 때문에 새로 만드는 것보다 고치는 일이 훨씬 비싸다.
4. **Input은 보이지만 행동은 없다.** 값, 검증, change, submit을 다루지 못해 일반적인 폼 흐름이 Purpose 메모로 밀려난다.
5. **Spec은 화면 확인용이지 전체 전달물은 아니다.** 전체 보기, 복사 또는 내보내기가 없어 실제 협업에서는 별도 문서가 다시 생긴다.

### 일부 참가자만 발견했지만 중요한 문제

- 내부 Figma 자식 노드를 선택했을 때 가장 가까운 Sketchy 부모를 찾지 않고 다른 화면으로 fallback하면 잘못된 대상을 편집할 위험이 있다.
- 요소 삭제 뒤 trigger 없는 Feature가 남을 수 있다면 단순 불편이 아니라 데이터 일관성 문제다.
- Section 중첩이 없어 반복 카드 같은 최소한의 의미 그룹을 만들기 어렵다.
- Flow의 선택 화면 목록과 Project flow 중복은 연결이 많아질수록 탐색 비용을 키운다.
- blur 저장에 피드백이 없어 빠르게 탭을 이동하거나 닫을 때 마지막 변경을 신뢰하기 어렵다.

## 개선 방향

### P0 — 산출물이 거짓말하지 않게 만들기

1. **현재 `Change state`의 이름과 설명을 실제 범위에 맞춘다.** 당장 시각 상태를 만들지 않는다면 `Describe state change` 또는 `Set state on (spec only)`처럼 명세 전용임을 드러낸다. 다음 단계에서 상태명과 `true / false / toggle`을 제공한다.
2. **삭제 시 Feature까지 일관되게 정리한다.** 요소 삭제 전에 자식과 연결 영향을 알리고, 연결된 행동을 함께 삭제하거나 명시적으로 유지할지 결정하게 한다. 고아 Feature는 Flow/Spec 검증에서 바로 보여 준다.
3. **선택 fallback을 안전하게 바꾼다.** 내부 자식이 선택되면 가장 가까운 Sketchy 요소나 화면을 부모 방향으로 찾는다. 찾지 못하면 첫 화면을 편집 대상으로 보여 주지 말고 선택 안내 상태를 표시한다.

P0는 기능을 더 많이 제공하기 위한 항목이 아니다. 현재 결과를 사용자가 실제보다 완성된 기획이나 프로토타입으로 오해하지 않게 하는 최소 안전장치다.

### P1 — 두 번째 사용을 성립시키기

1. **화면 Duplicate와 안전한 Delete를 제공한다.** 유사 상태 화면을 다시 만드는 비용과 캔버스 직접 삭제라는 숨은 우회를 없앤다.
2. **행동에 최소 조건 표현을 추가한다.** 범용 규칙 엔진보다 `조건 메모 + 성공 목적지 + 예외 목적지`처럼 작은 모델로 시작한다. 실제 프로토타입으로 모두 실행할 수 없다면 실행 여부를 구분한다.
3. **Flow에서 목적지 변경과 행동 삭제를 허용한다.** 전체 구조를 본 자리에서 수정할 수 있게 하고, 복잡한 그래프 편집기는 만들지 않는다.
4. **Input을 제출 행동과 연결한다.** 우선 `required`, validation note, submit Button 연결 정도로 제한하면 일반적인 폼 기획의 핵심을 담을 수 있다.
5. **Spec에 All screens와 Copy를 제공한다.** 별도 파일 포맷이나 협업 시스템보다 전체 명세를 한 번에 보고 복사하는 작은 기능이 먼저다.

### P2 — 반복 편집의 속도와 확신 높이기

1. Section 안에서 블록 추가 후 새 자식을 바로 편집할 수 있게 하되, 연속 추가 모드로 돌아가는 동선을 짧게 유지한다.
2. 입력값에 `Saving… / Saved` 또는 즉시 저장 피드백을 제공한다.
3. Flow는 `Selected screen / Entire project`를 명시적 필터로 나눠 중복을 없앤다.
4. Section 한 단계 중첩을 허용할지 검토한다. Card 같은 도메인 프리셋을 추가하기보다 범용 그룹 구조를 유지한다.
5. 고립 화면, 목적지 미지정, trigger 없는 행동을 Spec 또는 Flow의 검증 목록으로 보여 준다.

## 제품 방향에 대한 결론

현재 Sketchy의 가장 선명한 가치는 **Figma 안에서 작은 선형 User Flow의 저충실도 화면, 실제 Navigate, 최소 명세를 빠르게 함께 만드는 것**이다. 참가자들은 이 가치를 설명 없이도 발견했다.

반대로 지금 가장 큰 위험은 표현력이 적다는 사실 자체가 아니다. 명세 문장에는 복잡한 행동을 쓸 수 있지만 캔버스와 행동 모델은 이를 실행하거나 구조화하지 못하고, UI가 그 차이를 충분히 말해 주지 않는다는 점이다. 그래서 다음 개선은 블록 종류나 스타일 옵션을 늘리는 것보다 다음 순서를 따르는 편이 제품 철학에 맞다.

1. 지금 가능한 것과 불가능한 것을 정확히 보이게 한다.
2. 재방문 때 기존 화면과 연결을 안전하게 변형할 수 있게 한다.
3. 조건·폼·상태에는 가장 작은 공용 표현만 추가한다.
4. 결과 전체를 한 번에 검토하고 전달할 수 있게 한다.

## 다음 검증 제안

P0와 P1 일부를 반영한 뒤 실제 사용자 3명에게 동일한 두 회차 과업을 수행하게 한다. 이때는 다음을 측정한다.

- 첫 화면 생성부터 첫 Navigate 완성까지 걸린 시간
- 두 번째 과업에서 원래 버튼을 다시 찾는 데 필요한 클릭 수
- 사용자가 `Change state`를 실제 시각 전환으로 이해하는 비율
- 조건과 프로토타입이 불일치한 채 완료했다고 판단하는 비율
- 전체 기획을 동료에게 전달할 때 별도 문서를 만드는지 여부

이 측정으로 이번 인지적 워크스루의 위험 신호가 실제 사용에서도 재현되는지 확인할 수 있다.

## 상태 전략 수정 및 재검증

### 결정

Figma 유료 기능이나 Variant에 의존하는 상태 엔진은 만들지 않는다. 시각적으로 달라지는 상태는 `Screen`이라는 기존 공용 단위로 표현한다. 예를 들어 `상품 상세 · 기본`과 `상품 상세 · 찜됨`을 별도 화면으로 만들고 `Go to screen (prototype)`으로 연결한다. 이 방식은 모든 Figma 요금제에서 같은 캔버스와 실제 Navigate 결과를 만든다.

화면 이동이 없는 저장·요청·기록은 `Describe outcome (spec only)`로 구분한다. Navigate에도 `Notes (spec only)`를 함께 적을 수 있어 “선택을 저장한 뒤 선택됨 화면으로 이동”처럼 시각 결과와 비시각 결과를 한 행동에 보존한다. 과거 `set-state` 데이터는 이 문서용 행동으로 읽되, 더 이상 실제 상태 전환처럼 표시하지 않는다.

### 수정된 우선순위

#### P0 — 실행 결과와 명세의 경계를 정확히 유지

- `Go to screen (prototype)`과 `Describe outcome (spec only)`를 명시적으로 구분한다.
- 시각 상태는 별도 Screen으로 만들라는 안내와 요금제 독립성을 Destination 앞에 표시한다.
- Navigate에 문서용 Notes를 함께 제공해 실제 이동과 서버 저장 설명 중 하나를 잃지 않게 한다.
- 행동 종류를 바꿀 때 기존 행동이 교체됨을 확인한다.
- 요소 또는 캔버스 노드 삭제 시 연결된 Feature를 함께 정리한다.
- 내부 자식 노드 선택 시 가장 가까운 Sketchy 부모 맥락을 유지한다.

#### P1 — 상태 Screen을 현실적인 작업 단위로 만들기

- Screen Duplicate와 안전한 Delete를 제공해 기본/선택/오류 상태를 반복 작성하지 않게 한다.
- 조건은 범용 규칙 엔진보다 `조건 메모 + 기본 목적지 + 예외 목적지`의 최소 구조로 시작한다.
- Flow에서 목적지 변경과 행동 삭제를 제공한다.
- Spec에 전체 화면 보기와 Copy를 제공하고 고립 화면·목적지 미지정을 표시한다.

#### P2 — 반복 편집의 속도와 확신 높이기

- Section 자식 추가 후 즉시 편집과 연속 추가 사이의 왕복을 줄인다.
- 입력값에 저장 완료 피드백을 제공한다.
- Flow의 선택 화면/전체 프로젝트 중복을 필터 하나로 합친다.
- Input에는 우선 required, validation note, submit Button 연결만 제공한다.

`true / false / toggle` 상태 모델과 Variant 생성은 우선순위에서 제거했다. 별도 Screen 방식으로 표현할 수 없는 요구가 실제 검증에서 반복될 때만 다시 검토한다.

### 독립 재검증 결과

서로의 결과와 기존 persona 문서를 보지 않은 PM, Product Designer, 개발자 출신 Product Maker 3명이 수정된 모델로 동일한 2회차 인지적 워크스루를 수행했다. 기록은 `persona/validation`에 보관했다.

- 세 참가자 모두 Navigate가 실제 Figma 프로토타입이고 Describe가 문서 전용이라는 차이를 이해했다.
- 세 참가자 모두 별도 Screen 상태 방식이 Figma 요금제와 무관하게 일관적이라는 점은 납득했다.
- 최종 판정은 모두 **부분 통과**였다. 가장 큰 이유는 상태 Screen 복제 부재와 조건 분기 부재였다.
- 최초 검증에서는 Navigate와 비시각 결과를 동시에 보존할 수 없다는 문제가 발견됐다. 이에 Navigate Notes를 추가했다.
- 내부 선택 fallback, 요소·캔버스 직접 삭제의 고아 Feature, 구형 state indicator 정리 문제도 같은 수정에서 보완했다.

이번 검증으로 Variant 없는 상태 전략의 방향은 유지할 수 있다고 판단한다. 다음 구현 단위는 상태 시스템이 아니라 **Screen Duplicate**다. 이 기능이 있어야 별도 Screen 전략이 설명뿐 아니라 실제로 빠른 작업 방식이 된다.
