# 김서윤 PM 재검증

## 참가자와 기준

- 이름: 김서윤
- 역할: 초기 스타트업의 모바일 서비스 PM
- 배경: Figma로 화면 흐름과 개발 전달 문서를 만들지만 인터랙티브 컴포넌트나 변수 기능은 거의 쓰지 않는다. 무료 Figma 플랜에서 혼자 빠르게 초안을 만드는 상황을 가정한다.
- 범위: 현재 `src`의 실제 UI와 플러그인 동작만 처음 보는 상황으로 검토했다.
- 측정: 클릭 수와 UI↔플러그인 왕복 수는 구현 경로에 따른 예상치이며 실제 수행 시간이나 관찰값이 아니다. 텍스트 입력은 클릭 수에서 제외했다.

## 1차 인지적 워크스루: 3화면 선형 모바일 플로우

### 목표와 경로

기본 Mobile 설정을 유지해 `Screen 1 → Screen 2 → Screen 3`을 만든다.

1. Build에서 `+ Screen`을 세 번 누른다. 새 화면이 390×844로 생성되고 즉시 선택된다.
2. 화면 드롭다운에서 Screen 1을 선택하고 Button을 추가한다.
3. 자동으로 선택된 버튼의 `What happens?`에서 `Go to screen`을 고른다.
4. 나타난 Destination에서 Screen 2를 선택한다.
5. Screen 2를 선택하고 Button 추가 → `Go to screen` → Screen 3 선택을 반복한다.
6. Flow 탭에서 연결을 확인한다.

### 구현 기반 예상 측정

- 최소 12클릭: 화면 생성 3, Screen 1 선택 1, 첫 연결 3, Screen 2 선택 1, 둘째 연결 3, Flow 탭 1.
- 상태 변경 왕복 최소 11회: 화면 생성 3, 화면 선택 2, 버튼 삽입 2, 액션 선택 2, 목적지 선택 2. Flow 탭은 UI 내부 전환이라 왕복이 없다.
- 화면 이름을 의미 있게 바꾸면 화면마다 `Screen details` 열기, Name 포커스, blur 저장이 필요해 약 9클릭과 3회 저장 왕복이 추가된다.

### 판단

- 선형 흐름은 성공 가능성이 높다. `Go to screen`과 Destination의 조합은 의미가 분명하고 실제 Figma 프로토타입 연결까지 생성한다.
- 버튼 추가 직후 세부 설정이 나타나 다음 행동을 찾기 쉽다.
- 별도 상태 Screen 안내는 `Go to screen`을 선택한 뒤에만 보인다. 처음부터 상태를 만들려는 사용자는 이 옵션을 열기 전까지 상태 전략을 발견하기 어렵다.
- 기본 숫자 화면명은 빠르지만, 화면이 늘면 Destination과 Flow에서 의미를 다시 해석해야 한다.

## 2차 인지적 워크스루: 찜 on/off와 서버 결과·예외

### 목표

기존 상품 상세 기획에 다음을 추가한다.

- 찜 off에서 버튼을 누르면 on 시각 상태가 된다.
- 다시 누르면 off로 돌아간다.
- 찜 상태를 서버에 저장한다.
- 비로그인 사용자는 로그인 화면으로 보내고, 저장 실패 시 기존 상태를 유지하며 오류를 알린다.

### 예상 경로와 발견

1. 찜 on 상태용 Screen을 별도로 만든다. `Go to screen` 선택 뒤 표시되는 “For a visible state, create a separate screen and link to it. This works on every Figma plan.” 안내는 별도 Screen을 쓰는 이유와 무료 플랜 호환성을 직접 설명한다.
2. Screen 복제 기능이 없어 기존 상품 상세 요소를 새 상태 화면에 다시 추가해야 한다. 화면이 복잡할수록 상태 하나를 위해 재구성하는 비용과 두 화면의 불일치 위험이 커진다.
3. off 화면의 찜 Button은 on 화면으로, on 화면의 찜 Button은 off 화면으로 `Go to screen`을 설정한다. 단순 왕복 토글 프로토타입은 완성된다.
4. 같은 버튼에 서버 저장을 기록하려고 `Describe outcome (spec only)`을 선택하면 기존 navigation이 대체된다. Outcome에 서버 저장을 적을 수 있지만 화면 이동은 사라진다.
5. 비로그인·저장 실패 조건도 Outcome 자유문에 적을 수는 있으나, 조건 분기로 구조화되지 않고 화면 이동과 같은 트리거에 함께 보존되지 않는다.

### 구현 기반 예상 측정

- 두 상태 Screen과 각 찜 Button이 준비된 최소 전제에서 왕복 토글 지정: 6클릭, 저장 왕복 4회. 각 버튼에서 액션 선택과 Destination 선택을 합쳐 3클릭으로 계산했다.
- on 상태 Screen 생성은 `+ Screen` 1클릭/1회 왕복이 추가된다. 복제 경로가 없어 원본 요소 수만큼 재삽입 클릭과 왕복이 늘어나며 총량은 고정할 수 없다.
- 서버 저장만 기술하려면 `Describe outcome` 선택, Outcome 포커스, 바깥 클릭으로 저장하는 약 3클릭/2회 왕복이 든다. 그 순간 기존 화면 이동 1건은 대체된다.
- 조건 예외를 같은 Outcome에 이어 쓰는 데 구조화 클릭은 추가되지 않지만 실행 가능하거나 검증 가능한 분기는 생성되지 않는다.

## 용어와 안내의 첫인상

- `Go to screen`: 화면 이동이라는 뜻은 즉시 이해된다. 선택 뒤 나오는 안내도 보이는 상태를 별도 Screen으로 표현한다는 모델과 무료 플랜 호환 이유를 쉽게 전달한다. 다만 상태 전환도 이 옵션이라는 사실이 선택 전에는 드러나지 않는다.
- `Describe outcome (spec only)`: 프로토타입이 아니라 명세에만 남는다는 의미를 괄호가 전달하고, placeholder가 서버 저장 같은 비시각 결과를 떠올리게 한다.
- 두 옵션이 상호 배타적이라는 경고는 없다. navigation이 설정된 버튼에서 describe를 선택하면 기존 연결이 교체되므로, 사용자는 “화면 전환에 서버 저장을 추가한다”고 오해할 가능성이 높다.

## 상태 전략 판정

**부분 통과**

별도 Screen 방식은 무료 Figma에서도 on/off처럼 보이는 상태를 프로토타입으로 나타내는 방법으로 납득 가능하며 단순 토글은 만들 수 있다. 하지만 실제 행동에서 흔한 “시각 상태 전환 + 서버 저장 + 조건 예외”를 한 트리거에 함께 담을 수 없다. `Describe outcome`이 navigation을 대체해 프로토타입과 명세 중 하나를 포기해야 한다.

## 남은 우선순위

- P0: 한 버튼의 화면 이동과 비시각 결과·조건을 함께 보존해야 한다. 적어도 `Describe outcome`이 기존 navigation을 대체한다는 점을 저장 전에 명확히 알려야 한다.
- P1: 별도 상태 Screen을 만들 때 기존 Screen을 복제하거나 상태 변형을 빠르게 만드는 경로가 필요하다.
- P1: 로그인 여부, 성공, 실패 같은 조건별 결과를 구분해 Flow와 Spec에서 확인할 수 있어야 한다.
- P2: 별도 상태 Screen 안내를 `Go to screen` 선택 전에도 발견할 수 있게 하고, 상태 화면용 이름 제안이나 기본값을 제공하면 목적지 선택 부담이 줄어든다.
