# 김서윤 — Product Designer 독립 재검증

## 참가자

- 이름: 김서윤
- 역할: B2C 모바일 Product Designer
- 배경: Figma로 화면과 프로토타입을 만들지만 개발 명세 도구는 처음 사용한다. 상태는 보통 Variant로 관리한다.
- 검증 범위: 현재 `src`에 구현된 Build / Flow / Spec UI와 플러그인 반응만 확인했다.
- 측정 방식: 아래 수치는 실제 소요 시간이 아니라, 구현을 따라 과업을 끝낼 때 예상되는 컨트롤 활성화(클릭)와 UI↔플러그인 상태 왕복 횟수다. 네이티브 select를 펼치고 옵션을 고르는 물리 클릭 차이는 세지 않고 한 번의 선택으로 센다. 텍스트 입력의 키 입력도 제외한다.

## 워크스루 1 — 4화면 선형 모바일 플로우

과업: `상품 목록 → 상품 상세 → 주문 확인 → 완료` 화면을 만들고 앞의 세 화면 버튼을 다음 화면에 연결한다.

### 예상 진행

1. 기본 설정이 Mobile이므로 설정을 열지 않고 `+ Screen`을 네 번 누른다.
2. 각 화면의 `Screen details`를 열어 이름과 Purpose를 입력한다. 저장 버튼은 없고 입력칸 밖을 클릭할 때 저장된다.
3. 앞의 세 화면을 Screens 선택기로 차례로 고르고 `Button`을 추가한다.
4. 선택된 버튼의 `What happens?`에서 `Go to screen`을 고른 뒤 `Destination`에서 다음 화면을 고른다.
5. Flow 탭에서 연결을 확인하고, 필요하면 화면 이름 버튼으로 캔버스 화면을 다시 선택한다.

### 인지적 워크스루

- 시작 가능성: `Screens`, `+ Screen`, 기본 Mobile 프리셋은 처음 보는 사람도 시작점을 찾기 쉽다. 새 화면은 캔버스에 만들어지고 곧바로 선택된다.
- 화면 구성: `Add something`의 블록 선택은 명료하다. 다만 화면 이름과 Purpose가 접힌 `Screen details` 안에 있고 저장이 blur에 의존한다. 명시적 저장 피드백이 없어 입력 후 바로 다른 탭으로 가도 저장됐는지 확신하기 어렵다.
- 연결 이해: `Go to screen`은 프로토타입 이동이라는 뜻으로 곧바로 이해된다. 선택 직후 `For a visible state, create a separate screen and link to it` 안내와 Destination이 나타나므로, 먼저 목적 화면을 만들어야 한다는 규칙도 발견 가능하다.
- 오류 예방: Destination 없이도 기능 레코드가 저장되고 Flow에는 `Choose destination / not linked`, Spec에는 `Destination not selected`가 나온다. 복구 경로는 보이지만 미완성 연결을 만드는 순간의 경고는 없다.
- 결과 확인: Flow는 `출발 화면 — 버튼 이름 — 도착 화면`을 보여 주고 캔버스에도 커넥터가 그려진다. 단, 현재 선택 화면과 관련된 연결을 위에 한 번 더 노출해 같은 연결이 중복처럼 보일 수 있다.

### 예상 측정값

- 최소 기능 플로우(기본 이름 유지): 컨트롤 활성화 16회 — 화면 생성 4, 소스 화면 선택 3, 버튼 추가 3, 액션 선택 3, 목적지 선택 3.
- 의미 있는 이름/Purpose와 버튼 이름까지 작성: 약 32회 — 위 16회에 Screen details 열기 4, 화면 이름 입력 진입/blur 8, Purpose 입력 진입/blur 8, 버튼 이름 입력 진입/blur 6 중 작업 순서에 따라 겹치는 blur 클릭 약 10회를 상쇄한 예상치다. 정확한 물리 클릭 수가 아니라 구현 기반 조작 규모다.
- UI↔플러그인 상태 왕복: 기본 이름 플로우 13회(화면 생성 4 + 버튼 추가 3 + 액션 저장 3 + 목적지 저장 3). 이름 7개와 Purpose 4개를 모두 바꾸면 최대 24회다. 화면 선택은 캔버스 selectionchange를 통해 추가 STATE 왕복이 생길 수 있다.

## 워크스루 2 — 선택/빈/오류 상태와 비시각 저장 행동 추가

과업: 기존 기획에 `선택 전`, `선택 후`, `빈 상태`, `오류 상태`를 표현하고, `저장`은 화면 전환 없이 명세로만 남긴다.

### 예상 진행

1. `선택 전`, `선택 후`, `빈 상태`, `오류 상태`를 각각 별도 Screen으로 만든다.
2. 선택 전 화면에 버튼을 추가하고 `Go to screen → 선택 후`로 연결한다.
3. 빈 상태와 오류 상태로 진입시키는 기존 화면 버튼도 각각 같은 방식으로 연결한다.
4. 저장 버튼을 선택하고 `What happens? → Describe outcome (spec only)`을 고른다.
5. 나타난 Outcome에 `선택 항목을 저장하고 성공 알림을 표시한다` 같은 문장을 입력한 뒤 바깥을 클릭한다.
6. Flow와 Spec에서 시각 상태 이동 및 저장 명세를 확인한다.

### 인지적 워크스루

- 별도 Screen 상태 전략: 안내 문장은 짧고 구체적이며 Figma 플랜 제약까지 설명해, Variant 없이도 “보이는 결과는 복제된 화면으로 만들고 연결한다”는 규칙 자체는 이해할 수 있다. 특히 선택 전/후, 빈 상태, 오류 상태처럼 전체 화면 구성이 달라지는 경우에는 명확하다.
- 남는 모호성: 무엇을 별도 Screen으로 만들지, 원본 화면을 어떻게 복제할지, 상태 화면끼리 공통 요소를 어떻게 유지할지는 제품이 안내하거나 자동화하지 않는다. `+ Screen`은 빈 프레임만 만들며 복제 기능이 없다. 작은 선택 변화도 전체 화면을 다시 구성해야 하므로 Variant 경험이 있는 디자이너에게는 중복과 동기화 위험이 크게 느껴진다.
- `Go to screen`: 실제 프로토타입 reaction과 커넥터를 만들며 Destination을 요구하므로 “클릭 후 보이는 다른 상태/화면”에 적합하다는 의미가 분명하다.
- `Describe outcome (spec only)`: 화면 전환이 없는 저장, 분석 이벤트, 백그라운드 갱신처럼 시각 목적지가 없는 행동으로 해석할 수 있다. `not prototyped` placeholder와 Flow의 `spec only` 표시는 프로토타입이 생성되지 않음을 보강한다.
- 중요한 혼동: Outcome은 feature 전용 필드처럼 보이지만 실제로는 버튼 element의 `description`에 저장된다. 별도의 Save 버튼 없이 blur 때 저장되고, Flow/Spec에 나타나기 전 성공 피드백도 없다. 액션을 `Go to screen`으로 바꾸면 설명은 데이터에 남아 기능 description에도 따라갈 수 있어, 사용자가 현재 활성 명세와 잔존 텍스트의 관계를 알기 어렵다.
- 오류 상태 표현: “앱에서 발생할 오류 화면”은 별도 Screen으로 표현 가능하다. 반면 Sketchy 조작 자체의 오류는 상단 role=alert 한 줄뿐이고, 사용자가 그 오류를 기획 상태로 재사용할 수 있는 것은 아니다. 두 종류의 오류를 구분해야 한다.
- 결과 확인: Flow에서 describe 행동은 목적 화면 대신 Outcome과 `spec only`로 표시되고, Spec은 `Click 저장 → 결과` 문장으로 보여 준다. 따라서 비시각 행동이 프로토타입 연결이 아니라 명세라는 결과는 확인 가능하다.

### 예상 측정값

- 네 상태 Screen 생성 및 이름 지정: 약 16회(생성 4, details 열기 4, 이름 입력 진입/blur 8), 상태별 실제 콘텐츠 구성은 필요한 블록 수만큼 추가된다.
- 선택 전→후, 빈 상태, 오류 상태의 이동 3개를 버튼 신규 추가부터 연결: 12회(소스 화면 선택 3 + 버튼 추가 3 + Go to screen 3 + Destination 3).
- 비시각 저장 행동: 버튼이 이미 있으면 3회(버튼 선택, Describe outcome 선택, Outcome blur 저장). 버튼 신규 추가부터면 소스 화면 선택과 버튼 추가를 포함해 5회다.
- UI↔플러그인 상태 왕복: 상태 Screen 생성/이름 지정 8회, 이동 3개는 버튼 신규 추가 기준 9회, 비시각 행동은 기존 버튼 기준 2회(액션 저장 + Outcome 저장). selectionchange에 따른 STATE 왕복은 별도 추가될 수 있다.

## 판정

**상태 전략 판정: 부분 통과**

처음 보는 사람도 `Go to screen`과 안내 문장을 통해 보이는 상태를 별도 Screen으로 연결하는 모델을 이해할 수 있고, `Describe outcome (spec only)`도 비시각 행동을 명세로만 남기는 선택으로 구분할 수 있다. 그러나 상태 화면 복제/동기화 지원이 없고, blur 저장과 미완성 Destination 허용 때문에 여러 상태를 안정적으로 구축했다는 확신은 약하다. 전체 화면 수준 상태에는 쓸 수 있지만 잦은 부분 상태를 Variant 없이 관리하는 전략으로는 아직 충분히 명확하거나 효율적이지 않다.

### 남은 우선순위

- P0: 없음. 두 액션 모두 생성·저장·Flow/Spec 확인 경로가 있고, 잘못된 대상은 플러그인 오류로 노출된다.
- P1: 별도 상태 Screen을 원본에서 복제하는 클릭 우선 경로와 출발/상태 관계 표시. 현재 빈 Screen부터 재구성해야 해 선택 전/후의 구조 일관성을 보장하기 어렵다.
- P1: 이름, Purpose, Outcome의 blur 저장에 저장 완료 표시를 제공하거나 명시적 저장 동작을 일관되게 제공. 현재 탭 이동/선택 변경 시 저장 여부를 예측하기 어렵다.
- P1: Destination 미선택 상태를 액션 선택 시 즉시 명확히 경고하고, Flow의 `not linked`에서 바로 목적지를 정할 수 있는 복구 경로 제공.
- P2: 별도 Screen이 적합한 상태와 `spec only`가 적합한 행동의 짧은 예시를 What happens 영역에 함께 제시.
- P2: 선택 화면 관련 Flow와 Project flow의 중복 연결을 구분하거나 접어, 같은 연결이 두 개인 것으로 오해하지 않게 하기.
- P2: 액션 유형 변경 시 남아 있는 Outcome 설명을 보존할지 제거할지 사용자에게 명확히 알리기.
